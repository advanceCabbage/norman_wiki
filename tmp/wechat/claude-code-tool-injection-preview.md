# Claude Code 为什么不把所有工具都塞给模型？一文看懂它的工具注入机制

很多人会默认认为：

> 用户问什么，Claude Code 就把与这个问题相关的工具发给模型。

这个理解听起来合理，但并不准确。

Claude Code 的做法不是“按本轮意图挑工具”，而是把工具分成两层：**每轮固定发送的核心工具**，以及**需要时才发现和执行的延迟工具**。

这样设计的目标很朴素：既不能让工具说明把上下文撑大，也不能让每一轮请求都因为工具清单变化而损失 Prompt Cache。

理解这件事，关键不在于记住两个工具名，而在于先回到一个第一性原理。

---

## 一、工具越多，模型的“说明书”越长

模型不能直接操作文件、调用 MCP 服务，或创建团队任务。它只能根据客户端随请求发送的工具定义，决定要不要发起一次结构化调用。

一个完整工具定义通常至少包含：

- 工具名称；
- 它能做什么、何时使用；
- 参数的 JSON Schema；
- 参数约束、示例和边界说明。

当工具数量很少时，把所有定义都放进 API 的 `tools` 数组很直接。

但 Claude Code 是一个可扩展的 Agent：用户可以连接 MCP Server、安装扩展，工具池会持续变大。若每轮都发送全量 schema，问题随之出现：

1. **上下文成本上升**：模型要先阅读大量本轮根本用不到的说明书。
2. **推理注意力被稀释**：真正要用的能力，被一堆低频工具定义淹没。
3. **缓存更难命中**：只要工具池发生变化，请求中靠前且体积很大的 `tools` 数组就会变化。

所以，问题不是“工具能不能提供给模型”，而是：**怎样让模型始终找得到能力，又不必每次背下所有能力的完整用法？**

---

## 二、它不是按用户意图临时挑工具

先排除一个常见误解。

Claude Code 不会因为用户这轮说“帮我改文件”，就只发送 `Read`、`Edit`、`Write`；也不会因为用户说“帮我查网页”，才临时把 `WebFetch` 加进来。

这种“按自然语言意图挑工具”的方案，表面上很省，但会引入一个更棘手的问题：

> 谁来保证意图判断没有漏掉后续推理真正需要的工具？

一次任务往往会在执行中转向：先读文件，再搜索，再请求用户确认，最后可能调用外部服务。如果客户端预先猜错，模型连“我还能用什么”都不知道。

因此，Claude Code 选择了更稳定的分层策略：

```text
所有候选工具
        │
        ├── 核心工具：每轮固定发送完整定义
        │
        └── 延迟工具：先只告知名称，需要时再取定义
```

这不是“本轮相关工具注入”，而是**稳定入口 + 按需加载细节**。

---

## 三、第一层：核心工具每轮固定在场

当 Tool Search 功能开启时，Claude Code 会固定发送一组核心工具的完整 schema。它们覆盖了 Agent 最常见、最基础的工作路径，例如：

- 文件与 Shell：`Bash`、`Grep`、`Glob`、`Read` 等；
- Agent 与用户交互：`Agent`、`AskUserQuestion`；
- 任务管理：`TaskCreate` 等；
- 规划：`EnterPlanMode` 等；
- 网络：`WebFetch` 等；
- 代码智能：LSP；
- Skill：`Skill`；
- 工具发现与执行：`SearchExtraTools`、`ExecuteExtraTool`。

这里最后两个工具尤其关键：

- `SearchExtraTools`：搜索延迟工具，并取回它的定义；
- `ExecuteExtraTool`：按工具名称和参数，执行已发现的延迟工具。

也就是说，模型每轮都拥有一把稳定的“工具目录检索器”和“通用执行器”。

这正是后续可以延迟加载其他工具的前提。

---

## 四、第二层：延迟工具只先发送名字

非核心工具不会一开始就把完整 schema 塞进 `tools` 数组。

例如，读取或列举 MCP 来源的工具、`TeamCreate`，以及某个 MCP Server 带来的 `mcp__slack__send_message`，都可能属于延迟工具。

模型最初看到的不是它们的完整定义，而是一段轻量的系统提醒，逻辑类似这样：

```text
<available-deferred-tools>
CronCreate
TeamCreate
mcp__slack__send_message
...
</available-deferred-tools>

这些工具目前不在 tools 列表中。
若要使用，必须先调用 SearchExtraTools 发现其定义，
再调用 ExecuteExtraTool 执行。
```

这份清单每行只有一个**工具名称**。

它不携带完整 description、参数 schema，也不携带 `searchHint`。它传达的只是：

> “这里有一个叫 `CronCreate` 的能力；如果你需要，去查询它的用法。”

从信息量看，这就像应用商店的索引，而不是把每个应用的安装包都预装进内存。

---

## 五、模型实际如何发现并调用一个延迟工具？

以 `CronCreate` 为例，完整链路分为四步：

```text
模型看到工具名称 CronCreate
        │
        ▼
调用 SearchExtraTools({"query": "select:CronCreate"})
        │
        ▼
获得 CronCreate 的说明与参数定义
        │
        ▼
调用 ExecuteExtraTool({"tool_name": "CronCreate", "params": {...}})
```

重点在第三步。

`CronCreate` 的完整定义不是重新加入 API 的 `tools` 数组，而是作为一次按需查询的结果，交给模型理解；真正的执行仍然经过固定存在的 `ExecuteExtraTool`。

于是模型获得了两种能力：

- 平时知道“有哪些额外能力存在”；
- 需要某项能力时，再获取足以正确调用它的细节。

这个设计也让工具使用具备可恢复性：模型不需要事先记住所有 MCP 参数，只要知道自己可以搜索，就能在运行中补齐知识。

---

## 六、Tool Search 关闭时，会发生什么？

当 Tool Search 关闭时，Claude Code 会回到更传统的方式：向模型发送**全量工具 schema**。

两种模式的差异可以这样看：

| 模式 | API `tools` 数组 | 非核心工具的使用方式 |
| --- | --- | --- |
| Tool Search 关闭 | 全量工具 schema | 模型直接调用具体工具 |
| Tool Search 开启（默认） | 固定核心工具 schema | 先搜索定义，再用通用执行器调用 |

因此，Tool Search 并不是“少给模型工具”。

更准确地说，它把“直接拥有每把钥匙”改成了“始终拥有钥匙柜的目录和取钥匙的流程”。

---

## 七、为什么这能改善 Prompt Cache？

Prompt Cache 的核心不是“整份请求必须一字不变”，而是尽可能复用请求中已经稳定的前缀。

对 Claude Code 而言，最值得稳定下来的部分包括：

- System Prompt；
- 核心工具的 schema；
- 对话中较早、相对稳定的消息前缀。

如果每轮都将全量工具 schema 放入 `tools` 数组，那么只要用户安装了新的 MCP、某个 MCP Server 在会话中连接成功，工具数组就可能变化。这个大而靠前的变化，会影响缓存复用。

而 Tool Search 开启后：

1. API `tools` 数组始终是核心工具，结构稳定；
2. 新出现的延迟工具只以名称清单的形式补充；
3. 只有需要时，才把某个工具的详细定义带入当前推理链路。

即使延迟工具池变化，系统也仍能复用前面稳定的缓存前缀；变化的只是后面一小段轻量目录信息，而不是整套工具 schema。

这就是它同时实现“工具上下文更少”和“Prompt Cache 更友好”的原因。

---

## 八、这套机制真正解决的是什么？

从第一性原理看，Claude Code 在平衡三件互相拉扯的事：

- **能力完整性**：不能因为省 token，就让模型不知道某个工具存在；
- **上下文效率**：不能把所有低频工具的长说明每轮都塞进去；
- **请求稳定性**：不能让扩展工具的频繁变化持续破坏缓存前缀。

它给出的答案是：

> 用固定核心工具保证基本行动能力；用名称目录保证能力可发现；用按需查询保证细节只在需要时出现；用稳定的工具数组换取更好的缓存复用。

所以，Claude Code 的 Tool Search 不是一个简单的“搜索工具”功能。

它本质上是一层**工具能力的延迟加载协议**：让模型在工具数量不断增长的情况下，依旧能以较小的上下文成本、较稳定的请求结构，持续找到并调用正确的能力。

当你下一次看到 `SearchExtraTools` 和 `ExecuteExtraTool` 时，可以把它们理解为：

> 它们不是两个普通工具，而是 Claude Code 为整个工具生态准备的“发现机制”和“统一入口”。
