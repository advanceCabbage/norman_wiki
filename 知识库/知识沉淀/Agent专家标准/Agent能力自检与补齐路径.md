## 一、怎么用这份文件

1. **自检清单**每两周过一遍，只勾"能对着人讲清楚"的，不勾"看过"的。

## 三、自检清单

> 勾选标准：**能对着面试官讲清楚"怎么做、为什么、代价是什么"**，而不是"我看过"。

- [ ] 能解释长上下文注意力衰减对上下文排布的实际约束 🟡

- [ ] 能区分幻觉的三种来源，并给出三种不同解法 🟡

- [ ] 能说清结构化输出/约束解码对推理质量的影响 🟢

**L1 单 Agent 内核**
- [x] 能不依赖框架讲清一个可靠 Loop 的构成与终止条件
- [x] 能讲清多层上下文压缩策略，以及压缩后运行时状态如何重建

**L2 检索与知识**

**L3 多 Agent**

## 五、补齐路径

### 主线一：Eval 体系 🔴🔴（当前第一优先级）

**为什么第一**：它同时解决三件事——面试最高频深挖点、简历量化指标缺失（那些 XXX 占位符）、以及"能证明系统有效"这个专家判别式。

**做什么**
1. 给三个项目各写一套评测方案（不用真跑，先把方案写出来）：
   - [[智能客服机器人]]：检索层 recall@k / 答案有用性 judge / 线上拦截率与重问率
   - [[文档代码一致性智能检测工具]]：**天然有 ground truth**（人工确认过的文档差异），这是最容易做出漂亮指标的一个
   - 测试工作流：用例有效性、误报率
2. 挑一个真跑：建 50–100 条黄金集，跑一次基线，写 judge，做一次人机一致性校准
3. 补一套 prompt 变更的回归脚本

**产出物**：`Agent Eval 体系.md` + 一份可运行的评测脚本
**完成判定**：简历里所有 XXX 被真实数字替换；能在面试中用 3 分钟讲完"我怎么衡量它好不好"

---

### 主线二：Agent 有状态运行时架构 🔴

**为什么**：这是"能不能独立负责一个 Agent 平台"的分水岭，也是我最大的空白；而且我已有真实素材（Serena 多实例改造）可以往上挂。

**做什么**
1. 把 Serena 那次改造重新复盘，补齐当时没考虑的：会话亲和、drain、冷启动、并发槽位
2. 系统补 C 类七项：状态分层、幂等键、流式转发、容量模型、drain/checkpoint、断点续跑、语义缓存
3. 画一张完整的 Agent 平台部署架构图，每个组件标注"为什么不能用 Web 服务的做法"

**产出物**：`Agent 服务的有状态运行时架构.md`（含架构图）
**完成判定**：能回答"你的 Agent 服务怎么扩容 / 发版时正在跑的任务怎么办 / 工具执行到一半挂了怎么办"

---

### 主线三：激活交互设计这张牌 🔴

**为什么**：Agent 现在真正的瓶颈不在模型而在产品化——怎么让人信任它、看懂它、随时打断它、出错时接管。这些恰好是前端的领域，算法背景和纯后端都做不了。**这是我唯一的不可替代项，却一直被当成"我只是前端"。**

**做什么**
1. 把 [[CC 实现修改文件的 approve、reject及代码回退]] 从"源码笔记"重写成"Agent 交互设计方法论"
2. 补齐维度：中断与转向、审批粒度分级、进度可见性、可撤销、降级到人工、流式渲染与断流重连
3. 做一个小 demo 或写一篇公众号，把这个标签立住

**产出物**：`Agent 人机交互设计.md` + 一篇文章
**完成判定**：面试自我介绍时能自然说出"我擅长 Agent 的交互与产品化"，并有作品支撑

### 排期建议

考虑到目前在面试进行中，分两条时间线：

| 时间线 | 重点 | 理由 |
| --- | --- | --- |
| **面试期（当下 ~2 周）** | 主线一的**方案部分** + Gap 3（鼻炎药归因）+ Gap 5（安全）| 全是已被问到或必被问到的，纯输出型，见效快 |
| **中期（1–2 个月）** | 主线一的实操 + 主线二 + 主线三 | 需要动手，是长期能力资产 |

面试期原则：**优先把已有经历翻译成能力标签**（见第六、七节），比学新东西 ROI 高得多。

## 七、话术转换表

同一件事，两种讲法的层级差距：

| 问题 | B 层答法（会用） | C/A 层答法（专家） |
| --- | --- | --- |
| Redis 在你项目里干嘛？ | 做缓存 | 会话热状态 + 工具重试的幂等键 + 并发槽位配额 + 多实例流式转发 |
| 你的 Agent 怎么部署？ | 部了几台机器 | Agent 是有状态长任务，容量按并发槽位不按 QPS；发版要 drain，任务带 checkpoint 续跑；工具侧靠幂等键防副作用重放 |
| 你怎么知道效果变好了？ | 用户反馈变好了 | 分层指标：检索 recall@k、工具调用准确率、端到端完成率；judge 与人工做过一致性校准；每次 prompt 变更跑回归 |
| 用了 ReAct 吗？ | 用了 ReAct 框架 | ReAct 是 function calling 之前的产物，现在原生 tool use 已内化了它；我们的重点是给 Agent 造可验证闭环，比推理范式的收益大得多 |
| 检索不准怎么办？ | 调了下 top-k、换了 embedding | 先分层归因：是没召回（索引/embedding 领域适配）、召回了没排上去（rerank/权重）、还是 query 没被正确展开（术语归一/意图识别）。不同层不同解法 |
| 怎么保证安全？ | 加了权限校验 | 威胁模型是间接 prompt injection——工具返回内容里藏指令，输入过滤解决不了；靠权限分级 + 沙箱 + 高危确认 + 审计，加上 Skill/MCP 的供应链治理 |
| 多 Agent 用了吗？ | 用了 subagent | 大多数场景不该上。上的动机是上下文污染、成本、缓存复用三者之一；最难的不是拆，是结果合并和部分失败 |
