# Agent 专家能力全景

> **这不是学习清单，是判别标准。**
> 用来回答两个问题：什么样的人算 Agent 专家；某项技能属于哪一类、该学到什么深度就停。
> 学习清单见 [[Agent能力自检与补齐路径]]。

---

## 零、先立一把尺子：A / B / C 三类能力

讨论"要不要学 Redis / Python / 分布式"之所以容易吵不清楚，是因为把三类性质完全不同的能力混在一起谈了。

| 类别 | 是什么 | 举例 | 作用 |
| --- | --- | --- | --- |
| **A 类：Agent 专有能力** | 只在这个领域存在的东西 | Context 工程、Eval 体系、Loop 设计、工具治理、Memory 分层 | **专家的判别式**。有 = 专家，没有 = 不是 |
| **B 类：通用工程底座** | 任何后端/平台工程师都该有的 | Python、Redis、MQ、DB、K8s、分布式基础 | **入场券，不是奖杯**。有了不加分，没有直接卡死 |
| **C 类：交叉地带** | 通用技术在 Agent 场景下的*特殊形态* | Agent 的状态层设计、有状态运行时、语义缓存、幂等重放 | **最容易被忽略、也最容易拉开差距** |

三条推论：

1. **B 类是隐性门槛。** 没人会在 JD 里写"要会 Redis"，但架构评审时说不出话，对方立刻知道你只做过应用层。对前端/客户端转型的人，这是最现实的卡点。
2. **B 类补到能进 C 类就停。** 目标是"能独立设计并交付一套 Agent 服务架构"，不是成为后端专家。
3. **面试的区分度几乎全在 A 和 C。** 同一个问题——"Redis 在你项目里干嘛"——答"缓存"是 B 层，答"幂等键 + 并发槽位 + 流式转发"是 C 层。

## 一、市场分层：不存在统一的"AGI 专家"

"AGI 专家"是招聘与自媒体的包装词，没有对应的能力标准。真实存在的是四类岗位，能力模型几乎不重叠：

| 类型 | 核心能力 | 门槛 | 备注 |
| --- | --- | --- | --- |
| **模型侧**（预训练/后训练/推理优化） | 分布式训练、数据配比、RL、算子优化 | 科班算法，多数要博士或大厂算法履历 | 工程转型者不建议追 |
| **Agent 应用与平台工程** | Loop / Context / Tool / RAG / Eval / 生产落地 | 强工程 + 系统性理解 | 工程转型者的主战场 |
| **AI 产品 / 解决方案** | 场景拆解、指标设计、交付闭环 | 业务理解 | 可作副线 |
| **AI 全栈（创业公司）** | 端到端出活，什么都得干 | 广度 + 速度 | 对广度要求高 |

**判断原则：不要用自己的短板去撞别人的长板。** 工程背景的人去卷预训练，等于放弃自己的差异化。

## 二、能力六层模型

每层给出「及格线 / 专家线 / 该停在哪」。

### L0 模型底座（不是训模型，是作为使用者的必要理解）

- **及格**：知道 token、上下文窗口、温度、function calling 怎么用。
- **专家**：能解释*为什么*模型会在某处坏掉——
  - 长上下文中的注意力衰减（lost in the middle），以及它对上下文排布的实际约束
  - 结构化输出的约束解码原理，为什么强 schema 有时会降低推理质量
  - function call 是后训练教出来的行为，因此对工具描述、参数命名有分布偏好
  - KV cache / prefix caching 决定了 prompt 该怎么排序（稳定内容前置）
  - 幻觉的三种来源需要三种解法：知识缺失 → RAG；检索污染 → 检索治理；指令冲突 → prompt 结构
- **该停在哪**：微调懂到「决策级」——什么时候 prompt/RAG 解决不了必须微调、数据怎么造、怎么评估有没有退化。**预训练、分布式训练、算子优化、scaling law 细节，不碰。**

> 关联：[[Function Calling、Skill、MCP 这三个有什么区别]]、[[提示词工程]]

### L1 单 Agent 内核

- **及格**：能用框架搭出一个能跑的 Agent。
- **专家**：能不用框架手写一个可靠的 Loop，并说清每个设计的代价。
  - **Loop**：终止条件、死循环防护、overflow 重试上限、steering 与 follow-up 队列
  - **Context 工程**：预算分配、大工具结果外置、snip / microcompact / full compact 的分层、**压缩后如何重建运行时状态**（这是最容易翻车的点）
  - **Tool 设计**：schema 即 prompt；错误信息写给模型看而不是给人看；幂等与并发安全；工具粒度的取舍
  - **Memory**：短期 / 长期 / 情景 / 事实的分层，以及"什么时候不该记"
  - **Session**：可恢复性、事件溯源、分支与 fork
- **该停在哪**：这一层没有上限，是专家的主战场。

> 关联：[[CC主循环Loop机制]]、[[CC 上下文压缩机制]]、[[CC工具机制]]、[[CC 记忆机制]]、[[三大 Agent 框架横向对比与面试框架]]

### L2 检索与知识

- **及格**：会切片、会 embedding、会向量检索。
- **专家**：知道检索失败的每一种成因，并有对应手段。**核心能力是分层归因。**

| 层 | 失败形态 | 手段 |
| --- | --- | --- |
| Query 侧 | 用户表述与语料术语不在一个空间 | 意图识别、query 改写/扩展、多路 query、实体与领域术语归一 |
| 索引侧 | 切片破坏语义完整性 | 结构化 vs 语义切片、父子块、Q&A 双通道、元数据 |
| 召回侧 | 召回了但排不上去 | 向量 + BM25 混合、RRF 融合、rerank |
| 生成侧 | 检索对了但答错 | 上下文排布、引用约束、拒答机制 |
| 评估侧 | 不知道坏在哪 | recall@k / MRR 与端到端指标分离归因 |

- **该停在哪**：不需要自己训 embedding，但要能判断「什么时候通用 embedding 在领域语料上不够用」。

> 关联：[[RAG常见问题]]、[[混合检索结果融合与排序方法]]、[[Agentic RAG]]、[[向量检索优化手段之-创建向量索引]]

### L3 多 Agent 与编排

- **及格**：知道 subagent、知道 MCP。
- **专家**：**首先知道大多数场景不该上多 Agent。** 然后能说清：
  - 上下文隔离的三个真实动机：污染、成本、缓存复用
  - 编排模式的适用与失败模式：pipeline / supervisor / map-reduce 并行 / 辩论
  - 最难的部分——状态传递、结果合并、**部分失败怎么办**
  - 协议层：MCP（工具接入）与 A2A（Agent 间通信）解决的不是同一个问题
- **该停在哪**：能编排 + 能说清代价即可，不必追新框架。

> 关联：[[CC 多Agent机制]]、[[A2A 协议开发者入门]]

### L4 生产工程（**最大的分水岭**）

- **及格**：能上线，有日志。
- **专家**：四件事都成体系。

**① Eval 体系**
- 离线黄金集：怎么建、怎么覆盖长尾、怎么持续更新
- 分层指标：检索层 / 工具调用层 / 端到端任务完成率，能分离归因
- LLM-as-judge：**judge 本身必须与人工标注做一致性校准**，否则是拿一个没校准的尺子量东西
- 回归测试：改一版 prompt，怎么证明没有退化

**② 可观测性**
- 全局 TraceID 串联
- 分层全量记录：会话层 / RAG 层 / 调度层 / 工具层 / 模型层
- 目标是「能定位到是哪一层坏的」，而不是「有日志」

**③ 成本与延迟**
- prefix caching 命中率的 prompt 排布
- 模型路由：简单任务降级小模型
- 上下文预算分配
- 首 token 延迟 vs 总时长的体验取舍

**④ 安全**
- 权限分级、沙箱、高危操作确认、审计溯源
- **间接 prompt injection**（见第六节，这是 Agent 独有的威胁模型）
- 供应链：MCP / Skill 的来源审计、最小权限、出网管控

> 关联：[[Agent相关面试题]]、[[openclaw权限控制机制]]

### L5 业务闭环

- **及格**：做出来了。
- **专家**：完整闭环——人力/业务成本 → 可量化目标 → 系统设计 → 上线指标 → 迭代归因。
- 并且能说清：**为什么这样设计、代价是什么、什么情况下这个方案不成立。**

> 关联：[[智能客服机器人]]、[[文档代码一致性智能检测工具]]

## 三、三条分水岭

抛开所有知识清单，区分"会用"和"专家"的只有三件事：

**1. 能量化 Agent 的好坏。**
这是 90% 的人的天花板。大多数人只能说"感觉变好了"。专家能说："这版改动让工具调用准确率从 78% 到 89%，端到端任务完成率没变，因为瓶颈在检索层。"

**2. 对失败模式有直觉。**
看一眼需求就知道这东西会在哪坏：上下文会爆、工具会被误调、多轮会漂移、用户会问出你没想到的表述。这个直觉只能从踩坑来，但可以通过系统复盘加速。

**3. 知道什么时候不该用 Agent。**
能确定性解决的用代码 → 能 workflow 固化的不用自主 Agent → 能 prompt 解决的不上 RAG → 能 RAG 解决的不微调。**敢说"这个场景不该做 Agent"的人，比什么都想做 Agent 的人值钱得多。**

## 四、C 类展开：通用技术在 Agent 场景的特殊形态

### 4.1 状态层设计（Redis 只是载体）

Redis 的 API 两天学完。真正的能力是知道 **Agent 系统需要哪些状态、各自放哪、为什么**：

| 用途 | 说明 | 类别 |
| --- | --- | --- |
| 会话热状态 | 当前上下文、工具调用中间态；冷数据落 JSONL / 对象存储 | B |
| 分布式锁 | 同一 session 并发进消息、同一任务被多 worker 抢占 | B |
| **幂等键** | 工具重试时防止副作用重复执行（发消息、写文件、变更数据） | **C** |
| 配额与限流 | 单用户 token 预算、并发槽位、模型 QPS 分配 | B/C |
| 任务队列 | Agent 跑数分钟不能挂在 HTTP 上，必须异步化 | B |
| **Pub/Sub 转发流式输出** | 多实例下 SSE 连在 A 实例、任务跑在 B 实例，流怎么转过去 | **C** |
| **语义缓存** | query embedding 相似度超阈值直接返缓存，省一次完整 Agent 调用 | **C** |

### 4.2 运行时与部署：Agent 服务不是 Web 服务

> **Agent 服务的运维模型更像游戏服务器 / 批处理，不像无状态 Web 服务。**

传统 Web 是无状态、毫秒级、按 QPS 扩容。Agent 服务是**有状态、分钟级、流式、可能带沙箱**——几乎每条都反着来：

| 问题 | Web 服务 | Agent 服务 |
| --- | --- | --- |
| 容量模型 | QPS × 平均耗时 | **并发槽位**（单请求占数分钟，QPS 模型失效） |
| 扩缩容 | 随便杀 pod | 杀 pod = 杀掉跑了几分钟的任务，需要 checkpoint / drain / 优雅退出 |
| 会话亲和 | 无状态随便路由 | 流式连接 + 会话状态 → 要么亲和路由，要么状态外置 |
| 冷启动 | 秒级 | 拉代码仓、建索引、装依赖，可能数分钟 |
| 隔离 | 进程级 | **任务级沙箱**：每个 Agent 任务一个容器/工作区 |
| 失败恢复 | 重试整个请求 | 重试会重放副作用 → **断点续跑 + 幂等** |
| 灰度 | 按流量比例 | 还要考虑 prompt 版本、模型版本、工具集版本的组合 |

**这一段是「能不能独立负责一个 Agent 平台」的分水岭。**

### 4.3 语言与生态：补到哪、守住哪

| | 定位 | 补到什么程度 |
| --- | --- | --- |
| **Python** | 刚需但有边界 | 能独立完成：Eval 脚本、数据处理、向量库操作、微调实验、notebook。**不必成为 Python 工程师** |
| **TypeScript** | 差异化资产 | Agent **产品化**大量在 TS 生态（Claude Agent SDK、Vercel AI SDK、Mastra、LangGraph.js），懂的人比 Python 少得多 |
| **框架** | 心智模型即可 | LangGraph 的状态机模型值得理解；不必通读 LangChain 源码 |

## 五、推理范式谱系（含诚实的过时标注）

| 范式 | 现状 | 什么时候还该用 |
| --- | --- | --- |
| CoT / Zero-shot CoT | 已被推理模型内化 | 非推理模型上仍有效 |
| **ReAct** | **已被原生 function calling 取代** | 讲技术演进史时用；不要再手写 Thought/Action/Observation 去和模型的后训练行为对抗 |
| Plan-and-Execute | 仍有价值 | 长任务、需要中途给人看计划、需要预算控制 |
| Reflexion / Self-Refine | 成本翻倍 | 只在有明确评判标准时值得 |
| ToT / MCTS | 学术热，生产几乎不用 | 基本不用 |
| Extended thinking / thinking budget | **当前主线** | 要知道何时该开，以及**开了反而更差**的场景：简单指令、强格式约束 |

**面试提示**：ReAct 会被问，但考的是能不能讲清演进链条——
`ReAct（prompt 硬套格式）→ 原生 function calling → 并行工具调用 → 推理与工具调用交织`。背定义没有区分度。

### 比所有范式都重要的一条判断

> **能验证的闭环 > 更聪明的提示词。**

写代码 → 跑测试 → 看报错 → 改，这个循环带来的提升超过任何 prompt 范式。

因此「**给 Agent 造一个能自我验证的环境**」是比调 prompt 高一个数量级的杠杆：单元测试、linter、类型检查、Diff 对比、模拟器、可执行的 schema 校验。

设计新 Agent 时的第一个问题应该是：**这个任务的"正确"能不能被机器判定？** 能，就先把判定器造出来。

## 六、常被忽略的八项能力

按重要性排序。

### 1. Agent 的人机交互设计（最被低估）
中断与转向（steering）、审批粒度、进度可见性、可撤销（checkpoint / rollback）、失败时优雅降级到人工。
**Agent 的 UX 是当前行业最没解决好的问题之一**——算法背景的人做不了，纯后端也做不了。前端/客户端背景在这里是资产而非短板。

> 关联：[[CC 实现修改文件的 approve、reject及代码回退]]

### 2. 数据飞轮
上线日志 → bad case 挖掘 → 标注 → 评测集 → 迭代。
和 Eval 是一体两面：**Eval 是尺子，飞轮是让尺子持续更新的机制。**

### 3. Prompt / Skill 的资产化管理
版本、灰度、A/B、回滚、变更审计。大多数团队 prompt 散落在代码里，改了没法回滚——普遍痛点，能讲清就是亮点。

### 4. 安全与对抗（企业落地硬门槛）
重点是 **间接 prompt injection**：工具返回内容、网页、文档里藏的指令。这和传统 Web 安全是两套威胁模型——**"数据即指令"是 LLM 的原罪**，输入过滤解决不了。
配套：供应链治理（MCP / Skill 来源审计、最小权限、出网管控、内网 registry）。

### 5. 工具的规模化治理
10 个工具好办，500 个工具怎么办：动态发现、tool search、按需加载、命名空间冲突、**工具描述质量对选中率的影响**。

### 6. 模型选型的持续实操
新模型发布后两天内判断能不能换：小规模评测集、行为差异摸底（指令遵循、工具调用倾向、格式稳定性、长上下文衰减点）、迁移成本估算。
**这是持续能力，不是一次性知识。** 有固定流程的人和"当时试了几个模型"的人不是一个层级。

### 7. 成本建模
不是省钱技巧，是能回答：这功能上线后每月多少钱、单位业务价值的成本是多少、什么时候会不划算。

### 8. 合规与数据边界
数据出境、模型侧留存策略、审计留痕。金融/政企/中大厂场景直接决定方案能不能过审。

## 七、如何证明自己是专家

市场判断你是不是专家，不看你懂多少，看三件事：

1. **有没有跑在线上、有真实用户、有量化指标的系统**
2. **能不能讲清设计动机和代价**——"为什么这样做、代价是什么、什么时候不成立"
3. **有没有公开的技术影响力**——文章、开源、分享

第 2 条是面试的核心。所有深挖题本质都在问同一件事：**你是抄的还是想明白的。**

## 八、明确不必补的

反清单同样重要，避免把时间花在低杠杆的地方：

- 预训练、分布式训练、算子优化、scaling law 细节 —— 除非转模型岗
- 通读 LangChain 源码 —— 理解 LangGraph 的状态机心智模型即可
- 追每一个新出的 Agent 框架 —— 底层机制同构，读透 2–3 个足够
- 手写 ReAct prompt 模板 —— 已过时
- ToT / MCTS 等学术范式的实现细节 —— 知道存在即可
- 成为 Python 后端专家 —— 补到能独立做 Eval 和数据处理即可
