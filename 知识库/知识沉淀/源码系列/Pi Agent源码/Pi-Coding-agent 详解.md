## 一、开篇点题
前两篇我们讲了 pi-ai 和 pi-agent-core，本篇讲 pi-coding-agent 的扩展机制
三层递进：
- pi-ai ： 统一多 provider 的 LLM 调用与流式传输
- pi-agent-core ： agent 循环 + AgentHarness 编排（状态分层、快照隔离、phase 状态机）

## 三、AgentSession 会话编排核心
###### 3.1 上下文压缩的七层防御
读这段的收获：所谓"自动压缩"看着是一句 if (tokens > threshold) compact()，真实实现里有 7 层防御，全是"防止误触发"和"防止死循环"。这段代码本身就是很好的面试素材——说明生产级 agent 的难点不在主流程，在边界。
在真正发起大模型调用前，执行 _checkCompaction 函数，并实现七层防御机制
- 第一层：用户主动中断的响应不该触发压缩
- 第二层：换模型后，旧模型的 overflow 不该影响新模型。场景：用户从小上下文模型（opus 200k）切到大上下文模型（codex 1M），
- 第三层：消息早于最近一次压缩边界时直接跳过。 否则刚压缩完，压缩前那条带着旧（大）usage 的消息会立刻再次触发压缩，形成死循环
- 第四层：如果响应已经正常完成（stop），进行压缩时但不能再将已经完成的消息再发一次
- 第五层：“压缩+重试”整轮只允许一次。压完还溢出说明压缩救不了，再来一遍只会无限循环，直接报错让用户换大模型或减少上下文
- 第六层：假设调用大模型已经在报错 529，此时大模型没有返回当前会话的 token 数量，无法通过大模型返回的字段判断是否超过 token 预算，此时从历史消息中自动计算是否是上下文超出限制导致的
- 第七层：假设通过历史消息基准是早于压缩边界的，令可不压缩，等下次消息成功后判断是否需要压缩。仅在「 **压缩刚完成，还一次成功响应都没有，就又失败了」的场景下**，第七层才生效。不写它，99% 的时候没事；写它，那 1% 不会变成烧钱的死循环
#### 3.2 Loop 循环由 Pi-agent-core 和 Pi-coding-agent 共同完成
Pi-coding-agent 的内层循环是调用的 Pi-agent-core 的 Loop 循环能力，外层循环调用的是 Pi-coding-agent 自己封装的能力。
Pi-agent-core 每结束一轮循环会产生一条「agent_end」消息，但最终判断循环是否结束是通过 Pi-coding-agent 最后产生的「agent_settled」消息

**两层循环分工**

|     | 主包              | 负责内容                              |
| --- | --------------- | --------------------------------- |
| 内层  | pi-agent-core   | 一次 run 内：模型回复 → 工具执行 → 结果回灌 → 再回复 |
| 外层  | pi-coding-agent | 跨 run：要不要重试 / 压缩 / 消费扩展新排的消息      |

**注入的：四个扩展点**
agent-core 提供循环骨架，coding-agent 通过钩子填行为，本质是模板方法模式：

| 注入时机                                             | coding-agent 做了什么                        |
| ------------------------------------------------ | ---------------------------------------- |
| 每次模型请求前，convertToLlm 之前；操作的还是 AgentMessage[]     | 转发给扩展的 context 事件，让扩展在消息转成 LLM 格式前增删改上下文 |
| 紧接 transformContext，把 AgentMessage[] → Message[] | 自定义消息转换（如禁用图片时过滤图片块）                     |
| 工具执行前后                                           | 扩展的 tool_call / tool_result 钩子           |
| 模型调用请求结束                                         | turn 边界刷新 systemPrompt / tools / model   |
**顺带澄清：AgentHarness 没被用**，coding-agent 用的是 agent-core 里的 Agent，不是 AgentHarness。两者在 agent-core 里是并行的两套编排层：
packages/agent/src/
├── agent-loop.ts        ← 内层循环，两者共用
├── agent.ts             ← Agent：coding-agent 在用
└── harness/
    └── agent-harness.ts ← AgentHarness：新的，直接调 runAgentLoop，绕过 Agent

#### 3.3 AgentSession prompt 的 七道关卡
- 关卡 1：扩展命令拦截（/mycommand）—— 即使在流式中也立即执行
- 关卡 2：input 事件 —— 扩展可以拦截/改写用户输入
- 关卡 3：展开 skill 调用（注入 skill 的 name、description、文件路径）
- 关卡 4：并发守卫（整个类最关键的一道闸）。同一时刻只允许一次 agent run。运行中再发 prompt 必须显式声明排队方式，否则直接抛错。正因为这一条，事件流天然是单一有序的，agent/turn/message 事件才不需要携带 run 级别的 id 去做关联。
- 关卡 5：校验模型是否存在，是否具备模型调用权限（目的是尽早发现未选模型、未配置 Key 或未登录等确定性问题，OAuth：检查本地过期时间；或请求 Token 刷新接口。刷新成功可证明登录态仍基本有效）
- 关卡 6：发送前先检查是否需要压缩（捕获上一轮被中断的响应），**对应 3.1 的上下文压缩 七层防御**
- 关卡 7：组装消息 + before_agent_start 钩子执行

## 4. Tools 工具编排层
#### 4.1 工具并发执行两个层次
- **工具批次并发**
	- 默认工具是并发执行，仅两种情况下工具串行即全局配置串行sequential 或批次里任一工具声明了串行
	- 顺序细节：并行模式下 `tool_execution_end` 按**完成顺序**发，而 tool-result 消息按 assistant **源顺序**发（保证喂回模型的上下文顺序稳定）
- **同文件写串行**
	- 即便工具批次并发，对同一文件的写/编辑必须串行
	- 确保修改文件时使用文件的绝对路径
		- 使用 resolve 将相对路径转为绝对路径
		- 使用 realpath 将符号链接到真实物理路径
	- 使用进程内的 Map<key, Promise>保证对同一个文件多次修改的锁机制，但仅能在单个 Pi 进程内生效，不能跨进程文件锁
	- registrationQueue 在注册文件修改阶段串行化注册，因为 realpath 是异步的，避免两个调用同时算 Key，再抢 Map 会存在竞态

#### 4.2 工具 result 超长的三种截断方式

**每个工具按语义在代码里写死**，不是运行时参数，**三个函数是「三个正交维度」，不是「三选一的模式」**

| 函数           | 语义               | 谁在用               | 语义映射                                                | 参数                |
| ------------ | ---------------- | ----------------- | --------------------------------------------------- | ----------------- |
| truncateHead | 保留**开头** N 行/字节  | read、grep、find、ls | read 用 head——看文件要从头看                                | 默认 2000 行 / 50 KB |
| truncateTail | 保留**结尾** N 行/字节  | bash              | bash 用 tail——命令输出的**错误和最终结果在末尾**，所以留尾巴              | 默认 2000 行 / 50 KB |
| truncateLine | **单行横向**截断到 N 字符 | grep 每条匹配行        | grep 额外用 line——一条 minified JS 匹配行可能几十 KB，横向截断防止一行撑爆 | 500 字符            |
#### 4.3 默认激活工具模式
**首先**默认激活四个工具：read、bash、edit、write
**然后**调用大模型时会将四个工具的 schmea 发送给大模型
**其次**假设在 agent 运行途中，调用 setActiveTools 激活新工具，此时会在下一轮工具调用结束便更新为最新的工具集合

更新为最新的工具集合便不在复用大模型 API 端的 prompt cache 能力。Anthropic 风格把 `cache_control` 打在三处——**① 系统提示词末尾、② 最后一个工具定义（`anthropic-messages.ts:1282`）、③ 最后一条会话消息**。而 Anthropic 是**前缀缓存**，请求前缀顺序是 `tools → system → messages`。tools 数组变了，工具级断点失效，不再复用缓存逻辑

#### 4.3.1 用户自定义工具 & 有谁来激活工具

**内置工具走"精选默认激活"，自定义/扩展工具走"全量默认激活"；两者一开始都进 `state.tools`、都从第一次请求发给模型；模型只能用活跃集里的，无权自行激活——动态激活始终是扩展代码编排出来的，模型至多是那段代码的触发器。**
唯一的"动态激活"是代码驱动的，不是模型决策**，存在一条链路让工具集在运行中扩充，但**发起者是扩展代码，不是模型**，模型的作用仅限于"调用了工具 A"；"顺带把 B 激活"这个逻辑是 A 的作者写死在代码里的


## 5. 会话持久化与树形导航
#### 5.1 为什么选择 JSONL：本地优先的追加事件存储
- 功能：一个会话对应一个 JSONL 文件；首行保存会话头信息，后续每行追加一条 Entry。
- Entry 可记录消息、工具结果、模型切换、思考等级、压缩、标签、名称、分支摘要等。
- 优势：
    - 追加写入简单，避免频繁重写整份历史；
    - 崩溃时通常只影响末尾不完整行，历史记录仍可读取；
    - 人可读、便于导出、导入、调试和分享；
    - 不依赖数据库，适合 CLI 的本地优先场景
面试可补充：JSONL 的代价是查询和复杂索引能力较弱；Pi 通过“单文件单会话 + 按需重放”接受这一取舍。
#### 5.2 会话树模型：`id + parentId + leaf`
- 功能：每个 Entry 有唯一 `id` 和 `parentId`；当前 `leaf` 指向用户正在使用的分支末端。
- 当前上下文不是读取整个文件，而是从 leaf 沿 `parentId` 回溯到根，再反转得到当前分支路径。
- 优势：
    - 历史不会被回退或改写操作破坏；
    - 同一 Session 文件可保留多个分支；
    - 能在任意历史节点继续工作，同时保留原来的未来路径。

这是这部分最重要的设计点：**存储是树，模型上下文是当前树路径的投影**
#### 5.3  Fork、Clone 与 Tree 导航的区别

| 操作      | 语义                         | 存储结果                                |
| ------- | -------------------------- | ----------------------------------- |
| Tree 导航 | 在同一 Session 树中切换到历史节点或其他分支 | 不新建文件，移动 leaf + 写入一条 branch_summary |
| 从历史节点继续 | 以旧节点为父节点追加新 Entry          | 同文件形成新分支                            |
| Fork    | 从历史用户消息创建独立会话              | 新建 JSONL 文件，复制选中节点之前的路径，并记录父会话      |
| Clone   | 在当前节点完整复制会话                | 新建 JSONL 文件，从当前状态开始独立演进，并记录父会话      |
#### 5.4 分支摘要的作用
- 功能：切换到历史分支后，branch_summary 是**对"被放弃的那条分支"的单边摘要**。
- 它不是删除历史，而是为模型补充“为什么从这里分出去、此前做了什么”的连续性信息。
- 优势：避免模型仅看到某条旧路径时，丢失后续任务目标或关键决策。

可与上下文压缩区分：
- `compaction`：解决长上下文 Token 限制；
- `branch_summary`：解决切换分支后的任务连续性问题

#### 5.5 会话恢复与工作目录绑定
- 默认按工作目录组织会话文件，目录通常位于 `~/.pi/agent/sessions/` 下，并使用编码后的项目路径分组。
- 会话头记录创建时的工作目录等元数据；恢复时据此发现、分组和重建会话。
- 恢复不仅恢复消息，也会恢复当前分支，以及模型、思考等级等会话配置。
- 优势：
    - 避免不同项目的会话混杂；
    - 工具执行更容易回到正确的项目语境；
    - 支持 `/resume`、继续最近会话、导入外部会话等体验

## 6. 上下文管理与压缩
和 [[Pi-agent-core详解]] 中的上下文压缩一致，上下治理需要算上第四章节的工具 result 过长处理。

Pi 的上下文管理采用分层治理：工具层先限制单次输出体积，Session 层保存完整历史，Context 层仅投影当前分支；当 Token 接近模型窗口时，以“结构化摘要 + 最近原始尾部”替换旧历史。对于会话树导航，则通过分支摘要保留被离开分支的关键进展。最后结合真实 usage、成本和缓存命中统计，实现长任务的连续性、可控成本和可观测性


上下文管理分两条线。**压缩**解决 token 上限：触发是 `用量 > 窗口−16k`，计量用**最后一条真实 usage + 尾部估算**；切点从最近往回留 20 k、按 turn 边界切、绝不拆散 toolCall/toolResult，单 turn 过大就'前缀摘要+后缀保留'；反复压缩是**增量更新**旧摘要而非重摘。**分支摘要**解决切分支后的连续性：摘要'旧 leaf 到公共祖先'这段被放弃的路，挂到新位置。两者都产出一段结构化检查点摘要替换真实历史，但真实 entry 始终在 JSONL 里不丢。此外有一套**缓存浪费统计**（把 idle/切模型造成的 cache miss 折成美元）和**按模型的成本归集**。一个关键坑是**压缩后旧 usage 失效**——footer 用量和自动触发都要判断'压缩点之后有没有新回复'，否则会误判占用、甚至压缩死循环。

## 7. 扩展系统（这一层最大的可扩展面）

它是 `pi-coding-agent` 的动态架构层。核心 Agent Loop 保持稳定，扩展在运行时通过受控 API 注册能力、订阅生命周期事件，并影响 UI、工具、模型请求和 Session 行为

#### 7.1 扩展加载链路：发现 → 信任 → 注册 → 运行
- 功能：扩展不直接修改核心代码，而是通过 `ExtensionAPI` 声明能力。
- 优势：核心稳定、能力可按项目或用户环境动态加载、支持热重载。
- 关键点：扩展是运行在 Pi 进程内的代码；`wrapper.ts` 主要是接口适配、生命周期包装和错误处理，**不是安全沙箱**。
#### 7.2 ExtensionAPI：扩展能力边界
扩展可注册：
- 自定义工具；
- Slash Command；
- Provider 和模型配置；
- UI 组件、Widget、Dialog、Footer；
- 快捷键、编辑器工厂、自动补全；
- 自定义消息、Session Entry 渲染器；
- 生命周期 Hook。
优势是把“能力注册”与“业务实现”分离：扩展只声明自己提供什么，宿主统一决定何时加载、如何展示、如何进入 Agent Loop

#### 7.3 Hook 体系：观察与干预分离
| Hook 类别    | 典型能力                         |
| ---------- | ---------------------------- |
| 会话类        | 切换、Fork、压缩、树导航、关闭前拦截或注入行为    |
| Agent 运行类  | Agent/Turn 开始、结束、稳定状态通知      |
| 消息类        | 观察或修改流式消息生命周期                |
| 工具类        | 拦截工具调用、阻止执行、改写工具结果           |
| Provider 类 | 修改请求、请求头、观察响应状态              |
| Context 类  | 在模型调用前转换上下文                  |
| 输入与资源类     | 拦截用户输入、动态发现 Skill/Prompt 等资源 |
| 信任类        | 对项目扩展、资源加载给出信任决策             |
- 功能：在核心流程的确定边界提供扩展点。
- 优势：鉴权、审计、内容过滤、模型路由、上下文注入、成本控制等横切能力无需侵入核心逻辑

#### 7.4 Hook 的干预能力
部分 Hook 不只是通知，而可返回控制结果，例如：

- 阻止某次工具调用；
- 改写工具结果；
- 修改 Provider 请求头；
- 替换或取消压缩；
- 取消 Fork、切换 Session 或树导航；
- 修改模型调用前的 Context。

优势是扩展能改变行为，而不是只能做日志。

面试中可强调：**事件系统本质上是 Pi 的依赖倒置机制**。核心定义事件契约，扩展实现策略

Pi 将扩展系统设计为基于类型化 ExtensionAPI 和事件 Hook 的动态能力平台。Loader 负责加载与信任控制，Runner 统一管理注册项和生命周期分发，Wrapper 将扩展工具适配进标准 Agent Tool 执行链。扩展能够在不修改 Agent Loop 的情况下注册工具、Provider、命令和 TUI 组件，并在上下文、模型请求、工具调用、会话压缩和树导航等关键边界进行观察或干预。这使 Pi 的核心保持稳定，而产品能力能够按项目和运行时环境动态组合
## 8. 生态与集成

Pi 的生态层将核心 Agent 能力产品化：Package Manager 负责多来源资源分发与优先级治理；SDK 提供 Node.js 进程内嵌能力；RPC 用严格 JSONL 协议支持跨语言和 IDE 集成；导出与 secret gist 分享将 Session 变成可移植的协作资产；版本检查、遥测开关和 Windows 更新兼容则保证 CLI 在真实用户环境中的可维护性
## 9. 平台与工具类

Agent 的工具输出不是天然安全可展示的文本。Pi 在进入 TUI、Session 或 HTML 导出前，需要处理 ANSI、二进制内容、Unicode 宽度和 MIME 类型，避免展示层被非预期输出破坏
