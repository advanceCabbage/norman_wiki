## 一、主循环 Loop
#### 1.1 双层 while 循环设计
支持两种模式 steering 和 follow-up，用于处理当前有任务在执行时，应该追加消息还是等待上一轮结束再执行下一轮消息。steering 在**当前工具批次结束或下一次请求模型之前**注入新消息，follow-up 在上一轮消息完成结束后再继续处理新消息

- 外层 While 循环用于处理follow-up 类型的消息，假设存在follow-up 模式消息，则等上一轮完全结束（即内层 While 结束）再进行处理follow-up 消息；假设不存在follow-up 模式消息，则直接退出无任何负作用逻辑
- 内层 While 循环用于处理 agent Loop，内部接收steering 类型的 message 并且在当前工具批次结束或下一次请求模型前注入新消息
#### 1.2 调用模型前的上下文处理
- 对上下文进行可选转换与消息格式转换，生成 LLM 所需的 `Context`
- 为上层应用预留扩展点，可用于：**裁剪、替换或压缩上下文**

```typescript
if (config.transformContext) {
  messages = await config.transformContext(messages, signal);
}
```

#### 1.3 消费 Pi-ai 生产的流式事件
使用 message_update 事件不断将模型返回的流式消息返回给前台，包括：
- text_start（开始一个文本内容块）
- text_delta（收到一段回答正文）
- thinking_start（开始一个思考内容块）
- toolcall_start（模型开始生成一个工具调用）
- 等等
#### 1.4 工具调用执行流程
- 找到工具
- 处理工具参数
- 验证工具参数
- 执行 beforeToolCall
- 执行 tool
- 执行 afterToolCall
工具执行默认是并发执行，除非 全局配置串行或当前某个工具只能串行

#### 1.5 重要保护逻辑
- **工具参数被截断时不执行**：若模型因输出 Token 上限而以 `stopReason === "length"` 结束，所有工具调用都会被标记为错误，不会执行
- **工具错误也进入上下文**：找不到工具、参数校验失败、工具抛异常、被 Hook 拦截，都会变为 `ToolResultMessage(isError: true)`，再交给模型下一轮处理，而不是让整个 Agent 直接崩溃
- **`terminate` 是批次级终止**：只有当前批次中**所有**工具结果都设置 `terminate: true`，Loop 才停止；单个工具要求终止不会阻止同批其他工具结果进入上下文

## 二、Agent 状态管理
#### 2.1 三类状态类别
- **配置状态**：`systemPrompt`、`model`、`thinkingLevel`、`tools`，决定下一次模型调用如何执行；**生效时间：第一次调用；内层循环每完成一轮（批次工具执行完成或模型输出完成）**，总结来说你在一轮对话中途换模型，是可能生效的
- **对话状态**：`messages` ，已完成、可复用的会话历史
- **运行状态**：`isStreaming`、`streamingMessage`、`pendingToolCalls`、`errorMessage`，当前一次 Agent Run 的临时状态
#### 2.2 设置全局运行状态的优势
- **UI 与执行逻辑解耦**：Loop 只负责执行和发事件；TUI 只订阅状态/事件并渲染，不需要理解 SSE 或工具执行细节
- **保证上下文正确** ：`streamingMessage` 存未完成回复，`messages` 只存已完成消息。下一轮请求模型时，不会把半截 JSON 工具参数或半截回答当成正式历史
- **管理并发和用户操作** ：`isStreaming`、`pendingToolCalls` 让上层知道此时是否能发新 prompt、应当 steer 还是 follow-up、哪些工具仍在运行
- **统一收尾**：不论正常结束、模型异常、用户取消，最终都会通过生命周期逻辑清理 `streamingMessage`、工具集合和运行标志，减少“界面一直转圈”之类的问题
- **易测试、易扩展**：可以单独输入 `message_start`、`tool_execution_start`、`message_end` 等事件，验证状态是否正确；未来增加新 UI、RPC 或日志系统时，只需订阅事件，不必改 Agent Loop

## 三、工具定义、抽象
#### 3.1 内置抽象工具合集

Pi-agent-core 内部默认实现了系列工具，例如：bash、edit、read、write 等工具的基础实现层，值得注意的是这系列工具都需要使用方传入：执行环境（必选）、工具预处理（可选）。因此 Pi-agent-core 提供的工具实际上是方便用户可插拔的 harness 设计，不绑定固定的执行环境。总结来看 harness 版本是协议/接口

另外 Pi-coding-agent 中也提供了相同的工具实现，但 Pi-coding-agent 是为 Pi 本地交互式终端提供的工具，因此是具体的实现，也可理解为 Pi-coding-aget 的工具是在 Pi-agent-core 协议基础上的扩展、具体实现
#### 3.2 工具可插拔设计

- **工具集合本身可插拔**：支持传入任何工具数组，只要满足于 AgentHarnessTool 接口的对象都支持注册为工具（AgentHarnessTool 结构：name、label、description、parameters、prepareArguments?、executionMode?等）

- **工具集合可以动态调整**：提供 setTools、setActiveTools 等方法，可以在运行时追加/替换工具，或切换当前激活的工具子集（激活的工具子集如何理解？）
	- 假设完整的工具注册列表为： read, bash, write, deploy, delete_user
	- 假设此时激活的工具列表为：read，bash
	- 此时模型看到的是激活的工具列表定义，模型仅能看到 read、bash 为可用工具，其余的看不到
	- 仅激活工具子集的优势：
		- **最小权限**：只读分析阶段禁用写文件、部署等高风险工具；
		- **降低模型选择错误**：工具越多，模型越容易错误选择相近工具；
		- **节省上下文**：每个工具的 JSON Schema 与描述都会进入请求；
		- **动态工作流**：规划阶段只启用读取工具，获得确认后才启用编辑工具；
		- **可复现**：激活工具名称会作为会话状态记录

- **单个工具内部的行为定制**：所有工具都支持调用方扩展工具上下文字段

- **工具的底层执行后端可替换**：目前默认工具是支持 NodeExecuteEnv 方式，但调用方可以自定义工具的执行后端

- **工具调用生命周期的拦截**：对应于 CC 的 pre_tool_use 和 post_tool_use 工具执行生命周期

## 四、session 会话与持久化
#### 4.1 会话分叉存储机制
正常连续对话是线性的；当用户把当前会话指针回退到某个历史节点，再从那里继续输入时，就会在同一棵会话树中形成新分支。显式 Fork 则会创建一个新的会话文件，并复制被选中节点之前的路径，同时记录其父会话关系。两者都属于分支能力，只是前者在同一会话树内，后者是独立会话

#### 4.2 会话存储的方式和路径
Pi TUI 默认将持久化会话存为 JSONL，而非数据库。每个会话一个 JSONL 文件（多轮对话属于同一个 JOSNL 文件，仅在/new、/resume、/fork 才新建 JSONL 文件），默认位于：
`~/.pi/agent/sessions/--当前项目路径编码--/` 
可通过 `PI_AGENT_DIR` 改变根目录。项目也提供抽象允许替换为 SQLite 存储实现，作为 `SessionStorage` 的可选后端；但标准 `pi-coding-agent` / Pi TUI 默认没有使用它。内存存储也是可选实现，且禁用会话持久化时不会落盘

#### 4.3 压缩后的摘要如何存储及如何区分是摘要或原始记录
默认 JSONL 存储中，压缩记录、压缩摘要和原始会话消息都追加在同一个会话文件里，每一行都是一条带 `type` 字段的 Entry，因此通过类型区分：
- `type: "message"`：原始消息，包括用户输入、模型最终输出、工具结果等。
- `type: "compaction"`：压缩记录，其中包含摘要文本、压缩边界、压缩前 Token 信息等。
- 其他类型还包括模型切换、思考等级切换、标签、分支摘要等
压缩不会把旧 `message` 行替换或删除。构建下一次模型上下文时，系统沿当前分支查找最近的 `compaction` 记录，将其摘要作为旧历史的代表，并依据压缩边界跳过对应的原始消息

#### 4.4 会话历史保存哪些信息
- 会话树结构：Entry ID、父 Entry ID、当前分支叶节点、时间等。
- **用户消息**：文本、图片等多模态内容。
- **模型最终回复**：文本、思考内容（若模型返回）、工具调用请求、停止原因、模型信息、Token 与费用统计等。
- **工具结果**：工具调用 ID、执行结果内容、错误结果等；通常保存最终结果，不保存界面上的每一次流式增量刷新。
- **配置变更**：模型切换、思考等级切换、激活工具集合变化等。
- **上下文压缩**：摘要、压缩边界、压缩前 Token 信息。
- 分支信息：分支摘要、Fork 的父会话关系。
- 扩展与界面附加信息：自定义消息、标签、会话名称、会话元数据等
核心特点是“追加式事件历史 + 当前叶节点”。这让 Pi 能恢复会话、回退、分支、压缩上下文，并保留可追溯的原始记录

#### 4.5 会话记录的粒度
- 持久化的是最终消息和最终工具结果，不是每一个流式 delta。这样文件更稳定、可恢复，也避免把 UI 刷新细节当作业务历史。
- 模型、思考等级、激活工具等变更要记录，否则恢复会话后无法可靠复现当时的执行条件

## 五、上下文压缩

#### 5.1 三种触发压缩场景
- 手动压缩：用户执行 `/compact`。可提供额外指令，要求摘要重点保留某类信息。
- 阈值自动压缩：当前上下文 Token 接近模型窗口上限时触发。判断条件是：当前上下文 Token > 模型上下文窗口 - reserveTokens（默认 16384）
- 溢出恢复：模型已经返回“上下文超限”错误时，Pi 先压缩，再自动重试一次原请求；若第二次仍溢出，则不再无限重试。
#### 5.2 预估 token 数量的计算方式
- **文本长度约按 字符数 / 4 估算**（字符数来自 JS 字符串长度，也就是 string.length，**Claude code 也是同样的处理逻辑**）
	- 英文、数字、标点：通常一个字符计为 1
	- 常见中文：通常一个汉字也计为 1
	- `/4` 是一种不依赖具体模型 tokenizer 的粗略经验估算：英文代码、英文自然语言中，一个 Token 平均常覆盖约 3～4 个字符，因此用它来快速决定是否需要压缩，因此也不是 100%准确
- **图片固定按 `4800` 个字符估算，再经过 /4**，一张图片约估算 1200 Token（**Claude code 统一一张图片算 2000 Token**）。（也是预估未找到逻辑关系）
#### 5.3 扩展机制介入点
压缩前会触发 `session_before_compact` 事件。扩展可以：
- 取消本次压缩；
- 读取即将压缩的消息和边界；
- 提供自定义摘要结果；
- 增加结构化的附加数据。
压缩成功后会发出 `session_compact` 事件，供 UI、索引或其他扩展更新状

#### 5.4 压缩的提示词是什么

```
System Prompt：
你是上下文摘要助手。
读取用户与 AI 的对话，按要求输出结构化摘要。
不要继续原对话，也不要回答原对话中的问题。
只输出结构化摘要。
```

用户消息大致为：
```
<conversation>
待压缩的对话文本
</conversation>

[若此前已压缩]
<previous-summary>
旧摘要
</previous-summary>

请按固定格式总结：
- Goal
- Constraints & Preferences
- Progress
  - Done
  - In Progress
  - Blocked
- Key Decisions
- Next Steps
- Critical Context
```
#### 5.5 压缩后的恢复机制（哪些内容会原样进入后续对话）

不是按“最近 N 条用户消息”保留，而是按“最近约 N 个 Token 的上下文”保留，默认为 20000 Token，假设在 20000 Token 内的任何信息算为待「保留尾部」部分，因此任何在最近 20000 Token 内的内容都会保留，**这里的逻辑和 Claude Code 相差很大**
- 最近的用户消息；
- 最近的 Assistant 回复；
- 最近的工具调用；
- 对应的工具最终结果；
- 最近的扩展 `custom_message`；
- 压缩之后新产生的所有消息
- skill 等等

## 六、Skills

#### 6.1 Skill 解析后的对象结构

```ts
{
  name,                    // 稳定名称
  description,             // 给模型看的用途说明
  content,                 // SKILL.md 正文
  filePath,                // Skill 文件绝对路径
  disableModelInvocation,  // 是否对模型隐藏
}
```
其中最重要的是分层使用：
- `name + description + filePath`：适合放入 System Prompt，供模型发现。
- `content`：Skill 完整正文，只在显式调用时注入，或由模型使用 `read` 工具按路径读取。
这避免每轮请求都注入所有 Skill 全文

#### 6.2 发现与加载 skill
它的 `loadSkills(env, dirs)` 由宿主传入一个或多个目录后再扫描，因此它不知道“用户目录”或“项目目录”的业务概念。传入哪些目录、各目录的优先级，由 `pi-coding-agent`、SDK 宿主或其他应用决定。

加载时会：
- 递归扫描传入目录；
- 将发现的 `SKILL.md` 作为 Skill；
- 将传入根目录下的普通 `.md` 文件也作为 Skill；
- 遵循忽略文件规则

#### 6.3 skill 权重、重名取舍
`pi-agent-core` 没有“多个 Skill 的逻辑权重”或“冲突优先级”机制，原因是核心层只负责：
- 加载 Skill；
- 生成模型可见的目录；
- 显式注入某个 Skill 正文。

## 七、高阶 Agent Harness

#### 7.1 Agent Harness 与 Agent Loop 的关系
- **Agent Loop**：执行一次 Agent 推理循环：调用模型、接收流式消息、执行工具、把工具结果继续喂给模型、处理 steering / follow-up
- **Harness**：准备并治理 Loop 运行：构建上下文、维护 Session、注入工具上下文、管理模型和资源、处理 Hook、持久化事件、压缩、分支、取消与重试

```
一次调用关系简化版本：

Harness.prompt()
→ 创建本轮配置快照
→ 构造 AgentContext 和 AgentLoopConfig
→ 调用 runAgentLoop()
→ Harness 接收 Loop 事件
→ 保存消息 / 更新 Session / 触发 Hook
→ 返回最终 AssistantMessage
```
- Loop 关心“这一轮如何推理和调用工具”；
- Harness 关心“这轮从什么状态开始、执行期间如何受控、结果如何保存、下一轮如何恢复”。
Harness 可以替换或扩展 Session、工具、Hook、资源等，而无需修改 Agent Loop；Agent Loop 也可以脱离 Harness 单独被低层 SDK 或测试代码调用

#### 7.2 Pi Agent Harness 设计都有哪些内容
Pi 的 Harness 可以在面试中概括为：**将底层 Agent Loop 封装为可嵌入产品、可治理运行状态的高阶 Agent 运行时。**
- **统一编排底层能力**
    - 功能：聚合 Agent Loop、模型、工具、Session、资源、事件、队列、压缩和重试。
    - 优势：应用层不必重复实现复杂的胶水代码，可直接通过 `prompt()`、`skill()`、`compact()` 等高阶接口驱动 Agent。
- **Turn Snapshot：每轮执行配置快照**
    - 功能：每次 Turn 开始时，快照化上下文、System Prompt、模型、思考等级、工具、Skill 和请求参数。
    - 优势：避免执行过程中外部配置变更影响已开始的请求；同时可在下一轮模型调用前刷新快照，让模型切换、工具切换及时生效。
- **Session 驱动的可恢复执行**
    - 功能：将用户消息、模型最终输出、工具结果、配置变更、压缩和分支以追加式会话树保存。
    - 优势：支持恢复、审计、分叉、回退和上下文压缩；完整历史与实际模型上下文解耦。
- **工具注册与激活分离**
    - 功能：维护完整工具注册表，并为每个 Turn 选择实际暴露给模型的激活工具集合。
    - 优势：减少工具 Schema Token、降低模型误调用风险，并可按权限、任务阶段动态收缩工具能力。
- **工具上下文注入**
    - 功能：工具定义保持通用；执行时由 Harness 注入宿主上下文，例如用户身份、项目路径、数据库连接或权限策略。
    - 优势：模型协议层与业务运行环境解耦，利于复用、测试和权限隔离。
- **事件与 Hook 扩展点**
    - 功能：提供模型请求前、原始请求体、工具调用前后、上下文转换、压缩前后、会话树切换等 Hook。
    - 优势：扩展可做鉴权、审计、脱敏、内容拦截、请求路由和自定义压缩，而无需修改核心 Loop。
- **统一的消息队列语义**
    - 功能：区分 steering、follow-up、next-turn 三类消息注入时机。
        - follow-up 是“当前 Loop 收尾时继续”；next-turn 是“下一次 Loop 启动时先注入”。
        - next-turn：下一次外部调用 `harness.prompt()` 时触发，维护在 agentHarness，下一次人工或应用触发的 prompt 预先排队消息
    - 优势：支持用户在 Agent 工作期间继续输入，同时避免 UI 层自行处理复杂的并发与上下文顺序问题。
- **上下文压缩治理**
    - 功能：根据 Token 预算将旧会话压缩为结构化摘要，保留最近原始尾部，并支持溢出后的压缩重试。
    - 优势：在模型上下文窗口有限时支持长任务连续执行，同时保留完整原始历史用于审计和恢复。
- **生命周期、并发与故障控制**
    - 功能：管理 `idle`、执行、压缩、分支摘要等阶段，提供取消、重试、失败消息持久化与安全落盘。
    - 优势：防止并发操作破坏会话树，保证异常场景下仍有可恢复的状态。
- **资源抽象**
    - 功能：统一管理 Skill、Prompt Template 等资源，并支持运行时替换。
    - 优势：把“模型能力扩展”从核心推理循环中抽离，宿主可按项目、用户或环境动态配置能力

Pi 的 Harness 不是另一个 Agent Loop，而是 Agent Loop 之上的产品化运行时。它通过 Turn Snapshot 保证执行一致性，通过 Session 管理可恢复历史，通过工具与资源抽象实现动态能力边界，再通过 Hook、队列、压缩和生命周期控制解决扩展性、长上下文和并发治理问题
