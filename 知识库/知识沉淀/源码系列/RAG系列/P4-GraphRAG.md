## 一、GraphRAG 的基本流程
##### 1.1 离线检索阶段

1. <font color="#c0504d">文档切块</font>
2. 逐块调 LLM <font color="#c0504d">抽取实体(人/组织/概念)与关系</font>，并为每个实体生成描述
	- **先定义知识图谱的 schema**，例如节点只允许 `Person`、`Organization`、`Project` 等类型，关系只允许 `WORKS_FOR`、`USES`、`PART_OF` 等明确类型
	- **然后将文档按固定大小或语义边界切成 Chunk**，逐块把“原文内容 + 可用节点类型 + 可用关系类型 + 输出 JSON 结构”**发给 LLM**，并要求它只能依据原文抽取实体、关系、实体在当前上下文中的一句话描述，以及对应的证据原句
	- **LLM 返回结构化 JSON 后**，用 JSON Schema/Pydantic 校验字段、关系两端和类型是否合法，再将实体、关系、Chunk 和证据**写入 Neo4j**
3. <font color="#c0504d">实体消歧与合并</font>("张总"/"张三"/"CEO 张" → 同一节点)，构建知识图谱
	- **规范化名称**：新抽取的实体做规则标准化，例如统一大小写、去除空格和无意义标点、拆分“张总”“CEO 张”中的姓名与职位，并将原始名称保留为 alias
	- **候选召回**：综合精确名称匹配、别名匹配、字符相似度和实体描述向量相似度筛出 Top-K，避免与全库逐一比较
	- **同一性判定**：比较候选是否属于同一组织、任职时间是否重叠、是否连接到同一项目或部门、上下游关系是否一致，并把两边的实体描述、关联 Chunk 原文和关系证据一起交给 LLM 或判别模型，要求它输出 `same_entity`、置信度、判断理由和可引用证据
	- **合并决策**：高置信度自动合并，中间置信度（如 0.75～0.95）建立 `POSSIBLY_SAME_AS` 关系并进入人工审核，低置信度保留独立节点
	- **图谱回写**：合并为规范节点，同时保留原始别名与来源
4. 社区检测(Leiden 算法)：把图切成层次化的社区(community)
	- Leiden（莱顿） 社区检测是对实体关系图做分层聚类，依据边的连接密度把强关联实体划成主题社区；再把社区作为更高层的语义单元生成摘要，从而让 GraphRAG 能回答跨文档、全局性的问题
5. 逐个社区调 LLM 生成"社区摘要报告"，形成 C 0→C 1→C 2 多层级摘要金字塔
	- 社区报告/社区摘要通常由 **LLM 总结生成**：系统先收集一个社区内的实体描述、关系描述、可选的 claims 和关联原文，再将这些内容作为上下文交给 LLM，生成社区标题、摘要、关键发现及其解释
```
C0：公司技术项目全景
├─ C1：智能客服与知识图谱
│  ├─ 张三、A 公司、智能客服、Neo4j
│  └─ 社区报告：该主题围绕智能客服项目的知识图谱建设……
└─ C1：推荐系统与向量检索
   ├─ 李四、B 公司、推荐系统、Milvus
   └─ 社区报告：该主题围绕推荐系统的向量检索架构……
```

#### 1.2 检索阶段

##### 检索方式一：局部搜索
- **问题向量化，召回入口实体，确定从图的哪里开始查**：将用户问题向量化，找出最相近的 5～20 个实体作为入口
	- 通过还会结合名称精确命中、别名匹配等条件重排或过滤
	- 推荐做成**实体名/别名关键词检索 + 实体描述向量检索**的混合召回
- **以入口实体为中心扩展局部子图，拿到图谱事实即谁和谁有关系**：通常只扩展 1～2 跳（1 跳即找实体相关的实体即可），优先保留与 query 相关度高的边，限制候选实体数、关系数，对权限、时间范围等 metadata 过滤
- **回溯到原始文本 Chunk，取得可引用证据**：这一步是 GraphRAG 能溯源的关键：**图负责扩展关系，原文负责提供细节与证据
- **补充相关社区摘要**：入口实体还会映射到其所属社区，找到对应的社区摘要
- **分组排序、过滤并控制 Token 预算**：按预算 Token 组装上下文，过滤相关度低的片段
- **LLM 基于局部证据生成答案**：LLM 基于局部图 + 原文证据回答

##### 检索方式二：全局搜索
- **选择一个社区层级并加载社区报告**：选择粗粒度还是细粒度
- **将社区报告切成多个 Map 批次**：假设有 100 个社区报告，不能把它们一次全塞给 LLM，所以会按 Token 上限拆成多个批次
- **Map：每批社区报告生成“带分数的局部结论”**
- **聚合、排序、过滤中间结论**：严格按照分数排序，删除低分、空结论
- **Reduce：LLM 汇总为最终全局答案**：Reduce 阶段只读取经过筛选的高分结论，而不是重新读取所有原始报告，它负责：将相近结论合并成主题，按重要性组织答案，输出用户需要的格式，例如“Top 5 痛点”或“多段分析报告”

## 二、传统向量数据库和图数据库的差异是什么
#### 2.1 存储数据的方式
- 仅 Milvus 存 GraphRAG 数据”并非不能实现：你可以把节点和边都存成平面行，用 ID 做关联；但它本质上是在**应用层手写图遍历和关联**
- Neo4j 则把节点、边、路径和图遍历作为数据库的一等能力。
#### 2.2 检索方式的差异
- Neo4j 可以在数据库内完成“召回实体 → 沿边扩展 → 回溯 Chunk/社区”的关联读取。
- Milvus 不是“读不到图数据”，而是所有图关联、递归扩展、去重和路径控制都要由业务代码实现。Neo 4 j 则将这些操作下推到数据库查询层。
#### 2.3 在单跳和多跳场景的区别
- 单跳：Milvus 可以通过扁平关系表实现；Neo4j 更清晰、更易过滤和溯源。
- 多跳：Neo4j 的图遍历优势明显；仅 Milvus 需要在应用层模拟 BFS/DFS，跳数越多，查询次数、代码复杂度和错误风险越高。
## 三、GraphRAG 如何选择向量数据库

**第一，数据量。** 向量索引得放进内存才快。一条 1024 维的向量是 4 KB，100 万条就是 4 GB——一台普通机器完全扛得住。所以先算清楚到底多少条，**很多团队高估了自己一两个数量级**。

**第二，用户能搜到的范围有多窄。** 如果所有人都能搜全库，那没什么讲究。但如果是 SaaS，1000 家客户各搜各的，那每个用户只能看到全库的千分之一。这时候普通向量索引会出问题——它只会在全库找最像的 20 条，等筛掉别家公司的，往往一条不剩。用户体验是'文档明明在，一加筛选就搜不到'，还不报错，很难排查。**这种情况必须用支持带条件检索的向量库，比如 Qdrant 或 Milvus。而且这个问题 rerank 救不了——rerank 只能给捞回来的排序，捞不回来的它看不见。**

**第三，图查询要走几跳。** 我会把最复杂的三个查询写出来数一下。一两跳的话，普通关系型数据库加个索引就够快了；三跳以上才值得上 Neo 4 j 这种专门的图数据库。

三个都没超标，我就用 PostgreSQL 一把梭——向量、全文、图关系都放一个库里，一条 SQL 就能查完，不用跨系统调来调去，数据一致性也是免费的。

代价我也清楚：**千万级向量它会吃力；中文分词要装扩展，而云上的托管数据库可能不让你装；图超过两跳，SQL 会写得很难看。**

最后还有一条经常比技术指标更管用的：**团队现在已经在用什么。** 如果本来就有 PostgreSQL，加个向量能力几乎零成本；要是引入一套新系统，那是从零开始的运维负担。"
