#### 一、向量化时分块的长度限制 & 最佳的切割长度
首先切块的算法不会限制字符串的长度，例如 langchain 的 `textsplitters` 对待切割和已经切割的字符串没有长度限制。但进行向量化的 embedding 模型具备上下文窗口限制，例如：
- OpenAI `text-embedding-3-small` / `large`，单条限制为**8192 tokens**
- 智谱 `embedding-3`，单条限制为**3,072 tokens**
因此分块向量化的理论长度限制是由 embedding 模型决定的。**token 数量= 字符数（JS 的 length）/ 4**，那么对于 openAI 的 embedding 模型可以一次接收约 36000 字符数。另外 
```
chunkSize: 500  // 字符，不是 token
```

#### 二、向量切割的最佳长度定义

业界并没有对于向量切片长度的最佳定义或者说需要针对不同的场景具体制定切割长度的定义。通常来说不建议将向量切块的长度大于 1000 字符。一些通用的规则定义：

- **问题是精确事实定位**：小块更好，**常落在 `200–500 字符`，80 overlap ** 或 `64–300 tokens`。
- **问题需要解释流程、条件和上下文**：中块更好，**常落在 `500–1,000 字符`，120 overlap** 或 `512–800 tokens`
- chunk 越大，向量主题更容易被稀释；chunk 越小，召回到的内容又容易缺上下文。
- 结构优先于长度：Markdown 应先按标题/段落，再对超长段落递归切分。你目前的实现正是这个方向

**短问答类**（FAQ、单条规章制度）：chunk size 300-500 字符，overlap 50 字符  
**技术文档、教程**：chunk size 800-1200 字符，overlap 100-150 字符  
**合同、法律文书**：chunk size 1500-2000 字符，overlap 200-300 字符
