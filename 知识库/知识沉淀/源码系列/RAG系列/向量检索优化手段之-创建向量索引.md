# 向量索引为什么能加速检索：以 LibSQL 与 DiskANN 为例
在 RAG、语义搜索和推荐系统中，数据通常会先被 embedding 模型转换成向量，再从大量向量中找出与用户问题最相近的 Top-K 条内容。

一个经常被简化的说法是：“给向量列建索引，查询就快了。”本文回答其背后的技术问题：索引何时创建、LibSQL 如何声明向量索引、DiskANN 在索引中保存什么，以及有无索引的查询为什么会有数量级差异。
## 1. 问题：如何从大量向量中找 Top-K

假设知识库中有 100,000 个文本片段，每个片段通过 embedding 模型转换为一个 1024 维浮点向量：

```text
文本片段 → embedding 模型 → [x1, x2, ..., x1024]
```

用户提问时，问题也会变为同一维度的查询向量 `Q`。系统要做的事情是：按照某种距离度量，找到与 `Q` 最接近的 K 个向量。

常见的距离度量包括：

| 度量                    | 适用含义                                 |
| --------------------- | ------------------------------------ |
| 余弦距离（cosine distance） | 比较向量方向是否一致，文本 embedding 中最常见。距离越小越相近 |
| 欧氏距离（L 2 distance）    | 比较空间直线距离。                            |

embedding 模型负责让语义相近的文本在向量空间中靠近；向量索引不创造语义，只负责更快地找到这些近邻。

## 2. 什么时候应该创建向量索引

向量索引通常在以下阶段创建：

1. 创建好包含向量列的表后；

2. 第一次批量导入向量之前或之后；

3. 在数据量开始使全量扫描出现可感知延迟之前。

**索引只需要创建一次。数据库会在后续 `INSERT`、`UPDATE`、`DELETE` 时自动维护索引**；**如果索引是在已有数据的表上创建，已有向量会被自动加入索引。**

索引不是搜索请求到来时临时创建的。建索引需要预处理和额外存储，目的就是把这部分成本提前支付，换取后续每次检索更快。

## 3. LibSQL 如何创建向量索引

先创建一张带向量列的表：

```sql
CREATE TABLE documents (
content TEXT,
metadata TEXT,
embedding F32_BLOB(1024)
);
```

然后创建向量索引：

```sql
CREATE INDEX documents_embedding_idx
ON documents (libsql_vector_idx(embedding, 'metric=cosine'));
```

这条语句的关键不只是 `CREATE INDEX`，而是：

```sql
libsql_vector_idx(embedding, 'metric=cosine')
```

它是 LibSQL 的专用标记，含义是：

- `embedding` 是需要建立近邻检索索引的向量列；
- 索引按余弦距离定义“相近”；
- 这不是普通 B-Tree 索引，而是由 LibSQL 内部使用 **DiskANN** 构建的近似最近邻（Approximate Nearest Neighbor，ANN）索引。

`documents_embedding_idx` 只是索引名；`metric=cosine` 决定距离度量；真正让 LibSQL 识别为向量索引的关键字是 `libsql_vector_idx(...)`。

## 4. 建索引后，数据库额外保存了什么

创建向量索引不会给原始表增加一个名为“索引”的新字段：

```text
content | metadata | embedding | embedding_index ← 不会变成这样
```

数据库会单独维护一份内部索引数据。可以把它理解成一张图：

- 每一个文档向量是图中的一个节点；
- 每个节点保存一批可快速跳转的邻居连接；
- 连接不仅服务于“相近”，还要使整张图容易被导航。

抽象示例：

```text
节点 A（文本切分） ──> B（chunk 参数）、D（重叠策略）、E（递归切分）……
节点 B（chunk 参数） ──> A（文本切分）、E（递归切分）、F（token）……
节点 C（天气） ──> H（降雨）、J（温度）、K（湿度）……
```

这是内部导航结构，不是最终检索结果。它的作用是：当查询靠近 A 时，数据库能优先检查 A 的邻居，而不是立刻比较所有节点。

## 5. DiskANN 默认会记录多少个邻居

LibSQL 的 DiskANN 索引提供 `max_neighbors` 参数，用来限制每个图节点保存的邻居数量。默认值为：

```text
max_neighbors = 3 × √D
```

其中 `D` 是向量维度。

例如，对 1024 维向量：

```text
max_neighbors = 3 × √1024
= 3 × 32
= 96
```

即每个节点默认最多保存约 96 条邻居连接。

这三个概念要区分开：

| 概念 | 作用 | 1024 维索引的典型默认值 |
| --- | --- | ---: |
| `max_neighbors` | 单个节点在索引中保存的邻居连接上限 | 96 |
| `search_l` | 一次查询最多探索的候选节点数 | 200 |
| `k` / Top-K | 最终要返回给应用的结果数量 | 由业务指定，例如 5 |

提高 `max_neighbors` 或 `search_l` 通常有助于召回更多潜在近邻，但会增加索引体积、构建成本或查询耗时。

## 6. 没有向量索引：精确但需要全量扫描

用户问题被转换为查询向量 `Q` 后，若没有索引，检索逻辑等价于：

```text
for 每一个向量 V_i，i = 1..N：
d_i = cosine_distance(Q, V_i)
按 d_i 升序排序
返回前 K 个向量
```

如果 `N = 100,000`，系统需要将 `Q` 与全部 100,000 个向量计算距离，再排序。

```text
查询向量 Q
├─ 比较 V1
├─ 比较 V2
├─ 比较 V3
├─ ……
└─ 比较 V100000
```

这种方式是精确最近邻（Exact Nearest Neighbor）：只要距离计算正确，一定能得到数学意义上的全局 Top-K。但向量数量越大，延迟越高。

## 7. 有向量索引：在图中探索少量候选

有 DiskANN 索引时，用户问题仍会被向量化为 `Q`；系统仍会计算余弦距离，但只与一小部分有希望的候选节点比较。

概念过程如下：

```text
1. 用户问题 → 查询向量 Q
2. 从索引的入口候选开始，计算 Q 与少量节点的距离
3. 找出当前较接近 Q 的节点，例如 A
4. 读取 A 在图中预先保存的邻居，例如 B、D、E……
计算 Q 与这些邻居的距离
5. 优先扩展当前距离更小的候选节点
在有限的搜索预算内反复执行
6. 从访问过的候选中选出距离最小的 K 个
```

```text
查询向量 Q
↓
入口节点 M
↓
M 的邻居：A、C、G
↓
发现 A 更接近 Q
↓
A 的邻居：B、D、E
↓
保留距离最小的一批候选，继续探索
↓
返回 Top-K
```

因此，索引并非“事先知道 A、B、C 谁最接近用户问题”。它是通过预先构建的邻居图，让查询在向量空间中沿着更接近 `Q` 的候选不断导航，从而避免与所有 `N` 个向量逐一比较。

可以把它类比成找最近的咖啡店：

- 无索引：计算你到全市每一家店的距离；
- 有索引：每家店保存了附近可继续前往的店，你沿着越来越接近目的地的路径探索少量候选。

## 8. LibSQL 中如何查询索引

LibSQL 的向量索引通过 `vector_top_k` 显式使用：

```sql
SELECT documents.content,
documents.metadata,
vector_distance_cos(documents.embedding, vector(:query_vector)) AS distance
FROM vector_top_k(
'documents_embedding_idx',
vector(:query_vector),
5
) AS candidates
JOIN documents ON candidates.rowid = documents.rowid;
```

查询的职责划分是：

| SQL 部分 | 作用 |
| --- | --- |
| `vector_top_k(...)` | 使用 DiskANN 索引，快速找出近邻对应的 `rowid`。 |
| `JOIN documents` | 根据 `rowid` 回到原表，读取正文和元数据。 |
| `vector_distance_cos(...)` | 计算候选结果的余弦距离，用于展示或排序。 |

查询向量必须和索引列具有相同的向量类型和维度。

## 9. 为什么会变快，以及代价是什么

| 方式 | 需要比较的范围 | 查询特点 | 结果保证 |
| --- | --- | --- | --- |
| 无索引 | 全部 N 个向量 | 数据量大时越来越慢 | 精确 Top-K |
| DiskANN 索引 | 图中有限数量的候选节点 | 通常显著更快 | 近似 Top-K |

DiskANN 之所以变快，是因为建索引时预先构建了邻居图，并把导航成本从查询阶段前移到了索引构建与维护阶段。

代价包括：

- 额外的索引存储空间；
- 写入向量时需要维护图，入库会比没有索引更慢；
- 结果是近似最近邻，数据量很大时可能偶尔遗漏数学上绝对最近的节点。

这是一种典型的工程权衡：用少量准确性风险和额外写入成本，换取大规模检索时更低的延迟。

## 10. 结论

向量索引加速的本质不是减少 embedding 的生成，也不是免除距离计算，而是：

> 在索引构建阶段预先把向量组织成可导航的邻居图；在查询阶段只探索少量有希望的候选节点，而不是扫描全部向量。

对于 LibSQL：

```sql
libsql_vector_idx(embedding, 'metric=cosine')
```

是声明向量索引的关键；底层使用 DiskANN 提供近似最近邻搜索，而：

```sql
vector_top_k(index_name, query_vector, k)
```

是显式使用该索引查询 Top-K 的关键。
