## 一、表格解析并入库
#### 1.1 表格分类
- MarkDown 格式表格：结构在文本里，最简单
- PDF 表格：unpdf/pdfjs 均只带坐标的文本流，行列结构已经丢了。需要专业工具解析
- Excel 表格：原生结构，使用描述+metadata，复用 summary 模式
聚焦于 MarkDown 格式的表格处理

#### 1.2 表格拆分思考点
##### 1. 表格内容与正文是否分离
- **表格与正文分离** ✅
	- 好处：表格是个完整语义单元，永远不会被腰斩，还能带专属 metadata 和专属表示法
	- 代价：引用它的正文（"如下表所示…"）和表格**物理分家**了，需要额外手段做上下文关联（比如 metadata 里记 headingPath / 表序号）
- **表格与正文不分离**：
	- 好处：表格和上下文天然黏在一起，改动最小
	- 代价：拿不到表级 metadata，也没法给表格单独选表示法，大表还会把整段撑爆

##### 2. 选表格哪个部分进行 embedding 处理
- **整张 Markdown 表格**✅
	- 优点：零额外成本、实现最简、利于关键字检索场景
	- 代价：宽表一条向量把十几个维度揉一起，**纯向量召回被稀释**
- **按表格行向量化**
	- 优点：单元格级查询召回最准
	- 代价：记录数暴涨、每行丢表头上下文、近重复向量多
- **LLM 总结后再向量化**
	- 优点：纯向量召回最好
	- 代价：**每张表一次 LLM 调用**、描述可能漏具体数值

##### 3. 整表存一条还是按 token size 严格区分 ✅
- **默认整表一条，绕开 500 字符限制**（表格不是散文，不该被字符数切）
- 加一个**兜底阈值**（比如整表字符数 > ~2500）：超了就**按行拆成多个子表，每个子表都重复"表头行 + `\|---\|` 分隔行"**

##### 4. 表格抽走后正文和表格如何处理 ✅
- **表格处理方式**
	- **表格携带标题/正文吗？** → **只携带 `headingPath` 面包屑 + 那一句 caption**（既进 embed 上下文，也进 metadata）。**不携带**该段其它正文（如结尾"综上…"或别处段落）。
- **正文处理方式**：删除表格带走的所有片段内容，不保留，保持内容的干净

##### 5. 表格格式处理的疑难点简介
- 真假表格：代码块中含 ｜--｜等符号
- 表格内含有 emoji、**blob** 等
- 超大表处理
- 单行本身超 token 等等


## 二、图片解析并入库
#### 2.1 两种方式解析图片并入库
- **方案 A——多模态同空间嵌入(true multimodal embedding)** [[多模态同空间检索]]
- **方案 B —— 图片转文本桥接(image-to-text bridge)**：**利用视觉模型给图片生成描述文本/OCR[[OCR]]**，再用 embedding-3 把这段文字向量化，图片路径/引用存 `metadata`,**命中后返回图片。**

#### 2.2 专注于方案 B -> 图片转文本
##### 2.2.1 每张图片使用 GLM-4V 应该生成什么样的派生文本
- **图片描述**：让模型输出一段自然语言描述图片内容，例如："一只金毛犬在草地上奔跑""
	- 优点：语义/场景类 query("跑步的狗""营收趋势图");
	- 代价：**图里的文字**——截图上的按钮名、图表坐标轴标签、幻灯片正文,描述往往写不全
- **纯 OCR**：只把图片里可见的文字提取出来
	- 优点：文字密集图——扫描件、PPT 截图
	- 代价：**没有文字的图**(照片、纯示意图)几乎变成空记录,完全召不回
采用 **图片描述 + 纯 OCR** 方案 ✅

##### 2.2.2 一张图产出几条记录
- **一条记录(描述＋OCR 拼在一起,一次 embed)** ✅
	- 优点：一张图 = 一条记录，操作简单
	- 代价：描述和文字**混在一个向量里**,会被 embedding-3 平均成"综合语义",两者可能轻微互相稀释(比如一张纯文字截图,"这是一张截图"那句描述会稀释掉具体文字的语义)
- **两条记录(描述一条、OCR 一条,分别 embed,都指向同一张图)**
	- 优点：两个向量各自"纯粹"——文字类 query 精准命中 OCR 记录,语义类 query 精准命中描述记录,**检索精度上限更高**
	- 代价：记录数翻倍、同一张图可能在结果里出现两次

##### 2.2.3 内嵌图片的派生文本，哪些拼进候选上下文，共五部分进入上下文 ✅
1. **标题层级**：图片所在章节面包屑标题
2. **alt 文本**：作者为图片写的描述，想象 image 标签中的 alt 字段
3. **图片相邻的片段**：图片上下方都取一小段非空行
4. **GLM-4V 生成的图片描述**
5. **GLM-4V 抽的 OCR 文字**

##### 2.2.4 向量化存储图片的字段设计 ✅
- **imagePath**：图片位置(相对路径/引用)——命中要"返回的原物"
- **imageIndex**：同一文档内第几张图,给 RRF 去重用
- **sourceKind**：单独的图片还是文章内嵌的图片
- **description**：GLM-4V 生成的描述
- **ocr**：GLM-4V 抽的图中文字(可能空)
- **alt**：作者为图片写的描述
- **caption**：图片上下方都取一小段非空行
- **headingPath**：图片所在章节面包屑标题

##### 2.2.5 其余很多情况未实现的
- SVG 图片不支持、远程 URL 图片不支持
- 幂等缓存未实现，推荐**按图片内容 hash 缓存描述**,内容没变就复用,


#### 2.3 代码实现讲解图片向量化存储

##### 2.3.1 图片向量入库
- **首先**扫描目标文档和指定文件夹下的图片，并获取图片的绝对地址
	- 指定文件夹：支持.png, .jpg, .jpeg 等常见图片
	- 目标文档：扫描文档中内嵌的图片，使用正则表达式匹配 `[]()` 特定的图片格式
- **接着**用图片绝对路径进行去重
- **其次**按图片内容计算 hash，hash 存在于缓存中则无需再次调用大模型分析
- **然后**调用智谱glm-4v-flash 视觉大模型，读取**图片描述和 OCR**
- **接下来**使用**图片描述+OCR** 作为向量化的 content，mateData 中携带以下字段：imagePath、imageIndex、sourceKind、description、OCR 等字段
- **最后**将图片向量化入库，也适用 embedding-3，并且和普通的文本在同一张表、同一个索引

##### 2.3.2 图片向量检索
- **首先**检索逻辑与普通文本一致
- **最后**将检索会来的内容返回，会返回 text、 imagePath 等字段，其中 text 选用图片描述
