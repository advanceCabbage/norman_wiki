# 从“能听会说”到自然对话：语音智能体的两种架构

对于已经做过文本 Agent 的开发者来说，语音智能体并不是一种全新的 Agent，而是在 Agent 前后增加实时音频处理能力：系统需要持续监听用户、判断用户何时说完、理解语音内容，然后尽快生成并播放语音回答。

目前实现语音智能体主要有两条路线：

1. **STT → Agent → TTS，也叫 Sandwich 架构**：先用语音识别将用户声音转换成文字，把文字交给文本 Agent，再用语音合成将 Agent 的文字回答转换成声音。
2. **Speech-to-Speech，简称 S2S**：把用户音频直接交给原生音频模型，由同一个模型理解声音并直接生成回答音频。

两者都能实现语音对话，但在延迟、可控性、语气理解、调试方式和适用场景上有明显区别。

---

## 一、Sandwich：把成熟的文本 Agent 包在语音中间

Sandwich 的基本结构是：

```text
用户麦克风
    ↓ 音频流
Speech-to-Text
    ↓ 用户文字
文本 Agent
    ↓ 回答文字流
Text-to-Speech
    ↓ 回答音频流
扬声器
```

它不是简单地执行三次普通 API 请求。要做出自然的实时体验，音频输入、STT、Agent、TTS 和播放都需要流式工作。

### 1. 如何录入用户语音

#### 浏览器采集

Web 端通常通过 `navigator.mediaDevices.getUserMedia()` 获取麦克风，浏览器采集到的音频一般是浮点采样，需要通过 `AudioWorklet` 完成：

```text
麦克风 Float32 音频
→ 单声道处理
→ 重采样到 16 kHz
→ 转成 Int16 PCM
→ 切成 20～100ms 音频块
```

`AudioWorklet` 在独立的音频处理线程中工作，比在页面主线程里处理音频更稳定，不容易因为页面渲染或 JavaScript 任务造成音频丢帧。

#### 音频传输

常见传输方式有两种：

- **WebSocket**：实现简单，适合以“音频块 + JSON 事件”组织流水线。
- **WebRTC**：更适合低延迟双向音频，内置 RTP、拥塞控制和网络抖动处理。

### 2. 如何边录音边转成文字

实时语音智能体不能等用户录完一整段语音，再上传音频文件。正确的处理方式是“边说边转”。

假设用户说：

> 帮我查询一下明天从上海到北京最早的航班。

流式处理过程可能是：

```text
0ms      用户开始说话
100ms    上传第一块 PCM
400ms    partial：“帮我查询”
900ms    partial：“帮我查询一下明天”
1600ms   partial：“帮我查询一下明天从上海到北京”
2800ms   partial：“帮我查询一下明天从上海到北京最早的航班”
3000ms   用户说完
3300ms   final：“帮我查询一下明天从上海到北京最早的航班。”
```

在用户说话的三秒钟里，STT 已经完成了大部分识别工作。用户说完后，系统只需要确认最后几个词，并判断这一轮发言已经结束。

#### Partial 和 Final

流式 STT 通常返回两类事件：

```ts
type STTEvent =
  | { type: "stt_partial"; text: string }
  | { type: "stt_final"; text: string };
```

其中：

- `partial` 是临时转写，可能随着后续音频反复修改。
- `final` 是这一轮已经确定的转写，通常才会发送给 Agent。

例如：

```text
partial: “帮我订明天”
partial: “帮我订明天去北京”
partial: “帮我订后天去北京”
final:   “帮我订后天去北京的机票。”
```

如果每个 partial 都调用一次 Agent，就可能产生重复回答、错误工具调用和会话状态污染。因此，常规做法是：

```text
partial → 只用于页面实时字幕
final   → 正式触发 Agent
```

更激进的低延迟方案可以在 STT 高概率认为用户即将说完时，提前启动一次推测性的 Agent 请求；如果用户继续讲话，就取消这个请求。这样能减少延迟，但会增加无效调用和状态管理复杂度。

#### Endpointing：什么时候算用户说完

实时 STT 的难点不只是“识别出文字”，而是判断用户什么时候真正说完。

只依赖静音并不可靠：

> “帮我查一下明天从上海到……北京的航班。”

用户中间可能只是停下来思考。如果静音阈值太短，系统会错误截断；如果阈值太长，用户说完后系统又会迟迟不回答。

因此，现代 STT 通常结合：

- Voice Activity Detection，即 VAD。
- 静音持续时间。
- 语音识别结果是否构成完整句子。
- 声学特征和语义完整度。
- 可配置的 end-of-turn 置信度。

#### 常见 STT 方案

| 方案                                    | 特点                                                                |
| --------------------------------------- | ------------------------------------------------------------------- |
| AssemblyAI Universal Streaming / U3 Pro | LangChain 示例采用的服务，支持实时转写、partial、final 和轮次格式化 |
| Deepgram Flux                           | 专门面向语音 Agent，强调低延迟和语义轮次判断                        |
| Deepgram Nova-3                         | 通用流式识别，适合会议、字幕、远场和多语言                          |
| OpenAI Realtime Transcription           | 可使用 GPT 系列转写模型提供实时字幕                                 |
| Azure Speech to Text                    | 实时识别、定制词表和企业能力成熟                                    |
| Google Cloud Speech-to-Text             | 多语言覆盖和云平台集成能力较强                                      |
| AWS Transcribe Streaming                | 适合 AWS 和电话客服技术栈                                           |
| Qwen-ASR-Realtime                       | 支持 WebSocket 实时转写，适合中文和国内部署                         |
| faster-whisper、FunASR、NVIDIA Riva     | 适合私有部署，但需要自行处理 VAD、endpointing 和扩缩容              |

需要注意，原始 Whisper 更偏向“输入一段音频、输出一段文字”，并不是天然的实时对话协议。很多所谓的实时 Whisper 实际上是通过滑动窗口不断识别音频，再对结果进行对齐和去重。

选择语音 Agent 的 STT 时，不能只看普通字错率，还要关注：

- partial 延迟。
- final transcript 延迟。
- 端点判断准确率。
- 人名、地名、金额、手机号等关键实体错误率。
- 中英文混说和方言。
- 热词与领域词汇。
- 嘈杂环境和远场麦克风表现。

### 3. 如何把文字交给 Agent

收到 `stt_final` 后，将它作为一条新的用户消息发送给 Agent：

```text
stt_final
→ HumanMessage
→ Agent
→ streaming text chunks
```

Agent 部分与普通文本 Agent 基本相同，但有两个语音相关要求。

第一，必须使用流式输出。不能等 Agent 生成完整回答后才进入 TTS。

第二，Agent 的输出需要适合朗读。例如：

- 不输出 Markdown。
- 不输出 emoji。
- 少用复杂列表。
- 保持句子简洁。
- 正确使用标点。
- 将金额、日期和缩写转换成适合朗读的形式。

对于语音 Agent，Agent 输出的不只是文字内容，也是 TTS 的“表演脚本”。

### 4. 如何一边生成文字，一边转换成语音

Agent 可能按下面的方式流式输出：

```text
“好的”
“，我来”
“帮你查询”
“明天最早的航班”
“。”
```

不能简单地把每个 token 分别合成，否则 TTS 缺少上下文，可能出现停顿混乱、语调不连续和音色变化。

常见策略是增加一个文本缓冲区：

```text
Agent token stream
→ 累积文本
→ 遇到逗号、句号、问号
   或达到一定长度
→ 提交给 TTS
```

例如：

```text
第一段：“好的，我来帮你查询。”
第二段：“明天最早的一班航班是上午七点三十分。”
```

此时第二段还在生成，第一段已经可以进入 TTS 并开始播放。

#### 两种“流式 TTS”

需要区分两类流式能力。

第一类只有输出流式：

```text
提交完整文本
→ TTS 逐块返回音频
```

它不需要等完整音频文件生成，但仍然需要先获得完整文本。

第二类是输入、输出都流式：

```text
Agent 持续输出文字
→ TTS 持续接收文字
→ TTS 持续返回音频
```

第二类更适合语音 Agent，因为它能让 Agent 生成和 TTS 合成真正重叠。

#### 常见 TTS 模型和服务

| 模型或服务                    | 特点                                                                   |
| ----------------------------- | ---------------------------------------------------------------------- |
| Cartesia Sonic 3 / 3.5        | LangChain 示例采用的方案；支持 WebSocket、continuation、context 和取消 |
| ElevenLabs Flash v2.5         | 面向低延迟，音色库和声音复刻能力较强                                   |
| OpenAI `gpt-4o-mini-tts`      | 接口简单，可通过自然语言 instruction 控制说话方式                      |
| Deepgram Flux TTS / Aura      | Flux TTS 面向流式 Agent；Aura 提供较广泛的现成音色                     |
| Qwen-TTS-Realtime / CosyVoice | 中文表现和声音复刻能力较强                                             |
| Azure Speech TTS              | Neural Voice、SSML、定制音色和企业能力成熟                             |
| Google Cloud TTS              | 多语言和 Google Cloud 生态集成                                         |
| Amazon Polly                  | 支持 Neural、Generative、SSML 和多种音频格式                           |

Cartesia 使用 `context_id` 管理每一轮语音，使后续文本可以延续上一段声音的韵律。[Cartesia WebSocket TTS](https://docs.cartesia.ai/api-reference/tts/websocket)

ElevenLabs WebSocket 可以持续接收 LLM 产生的文字，并通过字符阈值决定何时触发音频生成。[ElevenLabs 实时 TTS](https://elevenlabs.io/docs/eleven-api/guides/how-to/websockets/realtime-tts)

#### 客户端如何连续播放音频

TTS 返回的通常是 PCM、Opus、MP3 或 μ-law 音频块。

浏览器不能让每个音频块一到达就独立调用 `play()`，否则网络抖动可能导致块之间出现间隙。通常要通过 Web Audio API 建立播放时间轴：

```text
收到音频块
→ 解码成 AudioBuffer
→ 放入播放队列
→ 根据 nextPlayTime 连续调度
```

客户端一般保留一个很小的 jitter buffer：

- 缓冲太少，网络抖动容易造成卡顿。
- 缓冲太多，用户会感觉回答延迟。
- 收到用户打断事件时，必须立即清空缓冲。

#### Sandwich 的首音频延迟

从用户说完到听见回答，延迟大致为：

```text
首音频延迟
= 端点判断
+ STT 最终确认
+ Agent 首 token
+ 首个可朗读文本片段
+ TTS 首音频
+ 客户端播放缓冲
```

“边说边转”的价值在于：用户说话期间，STT 已经完成大部分工作，因此用户说完后不需要重新处理完整录音。

## 二、Speech-to-Speech：让模型直接听声音、说声音

Speech-to-Speech 的结构更短：

```text
用户麦克风
    ↓ 音频流
原生实时音频模型
    ↓ 音频流
扬声器
```

模型不再只接收 STT 产生的文字，而是直接处理音频 token。这意味着它可以利用文字之外的信息：

- 用户的语气和情绪。
- 语速和停顿。
- 重音。
- 犹豫。
- 笑声等非语言信息。
- 环境中的部分声音信息。

例如，同一句“没关系，我挺好的”，可能表达真正轻松、委屈、愤怒或讽刺。Sandwich 中的文本 Agent 通常只看到相同的文字；S2S 模型则有机会根据声音理解真实语气。

### 1. S2S 的运行过程

典型流程是：

```text
浏览器建立 WebRTC 或 WebSocket 会话
→ 持续发送麦克风音频
→ 模型检测 speech started
→ 模型持续理解音频
→ 模型检测用户说完
→ 直接返回 audio delta
→ 客户端连续播放
```

模型还可能同时返回：

- 用户输入转写。
- 回答音频的转写。
- 工具调用事件。
- speech started / stopped 事件。
- interruption 事件。
- response done 事件。

但需要注意：在原生 S2S 模型中，转写有时只是用于 UI 和日志的辅助输出，不一定精确代表模型内部对音频的理解。

### 2. 常见 Speech-to-Speech 模型

#### OpenAI GPT-Realtime

代表模型包括：

- `gpt-realtime`
- `gpt-realtime-mini`

它们支持音频输入和输出，可以通过 WebRTC、WebSocket 或 SIP 建立实时会话，并支持 VAD、语义轮次判断、工具调用和可选转写。[GPT-Realtime](https://developers.openai.com/api/docs/models/gpt-realtime)

#### Google Gemini Live

当前代表模型是：

- `gemini-3.1-flash-live-preview`

它面向低延迟 audio-to-audio 对话，可以处理音频、图像和视频输入，适合实时多模态助手。不过它仍是 Preview 模型，生产使用需要关注版本稳定性和会话限制。[Gemini 3.1 Flash Live Preview](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-live-preview)

#### Amazon Nova 2 Sonic

Nova 2 Sonic 提供：

- 双向音频流。
- 自适应用户语气。
- 智能轮次判断。
- 用户打断。
- 多语言语音对话。
- 工具调用和异步工具执行。

它更像一个包含语音理解、对话管理和语音生成的完整语音模型。[Amazon Nova 2 Sonic](https://docs.aws.amazon.com/nova/latest/nova2-userguide/using-conversational-speech.html)

#### 千问实时语音模型

主要包括：

- `Qwen3.5-Omni-Realtime`
- `Qwen-Audio 3.0 Realtime`

它们支持实时音频输入输出、语义打断、工具调用、音色控制以及 WebRTC/WebSocket。对于中文、方言和国内网络环境，值得优先测试。[Qwen3.5-Omni-Realtime](https://help.aliyun.com/zh/model-studio/realtime)

#### 开源模型

代表方案包括：

- Qwen2.5-Omni-7B
- Moshi

Qwen2.5-Omni 可以理解文本、图像、音频和视频，并流式生成文字和语音。Moshi 更强调全双工语音对话，即模型在讲话时仍然能够继续听用户说话。

开源 S2S 适合私有化和研究，但实时推理、GPU 显存、音频服务稳定性和并发能力都需要自行解决。

## 三、两种方案的优缺点

| 对比维度       | Sandwich                                   | Speech-to-Speech                  |
| -------------- | ------------------------------------------ | --------------------------------- |
| 架构           | STT、Agent、TTS 三个独立模块               | 一个原生音频模型处理输入输出      |
| 用户语气和情绪 | STT 后容易丢失                             | 可以直接利用原始声音              |
| 首音频延迟     | 流式实现后可以较低，但存在多个服务边界     | 简单对话通常更低                  |
| 模型选择       | 可以分别选择最适合的 STT、Agent 和 TTS     | 可用模型相对有限                  |
| Agent 能力     | 可以直接使用成熟文本 Agent、RAG 和工具生态 | 取决于实时音频模型能力            |
| 可观察性       | 可以分别检查转写、Agent 文本和 TTS         | 内部过程相对不透明                |
| 发音控制       | 可以做文本规范化、SSML、热词和发音词典     | 取决于统一模型提供的控制接口      |
| 调试           | 容易定位是听错、想错还是说错               | 错误边界不容易拆分                |
| 供应商绑定     | 相对较低，每个模块都可以替换               | 相对较高                          |
| 系统复杂度     | 多个连接、缓冲区和取消链路                 | 组件较少，但实时会话状态仍然复杂  |
| 打断处理       | 需要自行取消 Agent、TTS 和播放队列         | 部分模型原生支持语义打断          |
| 审计与合规     | 可以保存明确的输入、输出文字               | 音频理解与转写可能不完全一致      |
| 私有部署       | 可分别私有化 STT、Agent、TTS               | 开源 S2S 模型选择和部署成熟度有限 |

### Sandwich 的主要优点

- 可以继续使用成熟的文本 Agent。
- STT、Agent、TTS 可以独立选型。
- 转写和回答内容透明，容易审核。
- 可以精细控制声音、发音和文本格式。
- 某一供应商效果不好时，可以只替换一个模块。
- 更容易判断问题来自听错、推理错误还是发音错误。

### Sandwich 的主要缺点

- 三个服务意味着更多网络跳转和连接。
- 需要维护多条并发流。
- 打断时必须向多个模块传播取消信号。
- STT 会丢失部分语气和情绪信息。
- TTS 根据文字重新创造声音，不一定与用户语境完全匹配。
- 流式文本分段不合理时，容易出现韵律割裂。

### Speech-to-Speech 的主要优点

- 可以直接理解语气、停顿和情绪。
- 简单对话的首音频延迟通常更低。
- 模型可以根据用户说话方式调整回答语气。
- 更适合自然打断、附和和全双工对话。
- 应用层需要编排的模型组件更少。

### Speech-to-Speech 的主要缺点

- 可选择的模型较少。
- 更容易被单一供应商绑定。
- 难以清晰判断模型究竟“听到了什么”。
- 发音、音色和输出格式的控制可能弱于专业 TTS。
- 实时音频 token 的成本可能较高。
- 复杂工具、结构化输出和 Agent 工作流能力取决于具体模型。
- Preview 模型较多，接口和能力可能发生变化。

## 四、分别适合什么场景

### 更适合 Sandwich 的场景

#### 1. 业务流程型 Agent

例如：

- 机票和酒店预订。
- 银行账户查询。
- 电商客服。
- 售后工单。
- 医疗预约。
- 企业内部助手。

这些场景更关心：

- 用户说的金额、日期、订单号是否准确。
- 工具调用是否可追踪。
- Agent 的每一步是否可以审计。
- 回答内容是否符合业务规则。

Sandwich 可以明确保存：

```text
原始音频
→ STT 文字
→ Agent 工具调用
→ Agent 最终回答
→ TTS 音频
```

因此更适合强业务逻辑和合规要求。

#### 2. 已经有成熟文本 Agent

如果已经拥有成熟的：

- LangChain/LangGraph Agent。
- RAG 系统。
- MCP 工具。
- 工作流和权限系统。
- 文本审核与内容安全能力。

那么在前面接 STT、后面接 TTS，通常比迁移到 S2S 模型更直接。

#### 3. 对音色和发音控制要求高

例如：

- 品牌客服音色。
- 声音复刻。
- 固定播报风格。
- 医疗、金融术语。
- 产品名称和人名。
- 精确朗读金额与验证码。

这类场景通常需要专业 TTS 的音色、SSML、发音词典和文本规范化能力。

#### 4. 多供应商或私有化部署

如果需要：

- STT 私有部署。
- Agent 使用指定文本模型。
- TTS 使用品牌定制音色。
- 某些模块部署在本地。
- 控制数据流向。

Sandwich 的模块化优势会非常明显。

### 更适合 Speech-to-Speech 的场景

#### 1. 强调自然交流体验

例如：

- AI 伴侣。
- 情绪陪伴。
- 心理支持中的非诊疗对话。
- 虚拟角色。
- 游戏 NPC。
- 实时社交助手。

这些场景中，语气和情绪本身就是输入的一部分，不能只依赖转写文字。

#### 2. 语言学习和口语陪练

S2S 可以利用：

- 发音。
- 重音。
- 语速。
- 停顿。
- 流利度。
- 对话情绪。

因此比纯文字 Agent 更适合口语练习、面试训练和表达训练。

#### 3. 低延迟实时助手

例如：

- 驾驶助手。
- 智能眼镜。
- 实时现场助手。
- 游戏内语音角色。
- 快速问答。
- 需要自然插话和打断的场景。

这类系统更关心“像人一样及时回应”，而不是完整保留每个中间文本边界。

#### 4. 实时多模态交互

当用户同时提供：

- 声音。
- 摄像头视频。
- 屏幕画面。
- 环境声音。

原生实时多模态模型可以在同一会话里共同理解这些信息，更适合“边看、边听、边说”的助手。

## 五、如何选择

如果核心问题是：

> 系统是否必须准确、可控地完成业务任务？

通常优先选择 Sandwich。

如果核心问题是：

> 系统是否需要像人一样理解语气，并进行自然、低延迟的对话？

通常优先考虑 Speech-to-Speech。

一个实用判断方式是：

```text
业务正确性、可审计、工具复杂、音色可控
→ Sandwich

情绪理解、自然交流、低延迟、实时打断
→ Speech-to-Speech
```

两种架构并不是互相取代的关系。Sandwich 的优势是工程边界清晰、Agent 能力成熟；Speech-to-Speech 的优势是保留声音信息并提供更自然的交互。

对已经有 Agent 开发经验的团队而言，Sandwich 通常是更稳妥的第一步。真正需要补齐的不是 Agent 本身，而是语音工程中的几个关键能力：

```text
流式音频采集
→ 边说边转
→ End-of-Turn 判断
→ Agent 流式输出
→ TTS 文本分段
→ 连续音频播放
→ 用户打断和全链路取消
```

当这些能力成熟后，再根据业务是否真正需要情绪理解、全双工交互和更低延迟，决定是否迁移或扩展到 Speech-to-Speech。
