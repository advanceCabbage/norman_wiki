## 一、 两分钟项目介绍

测试工作流是服务于团队内部测试场景提效和测试正确性保障机制，整个流程覆盖测试用例生成到执行全流程，包含：生成功能描述型测试用例 -> 可执行型代码测试用例 -> 代码与用例一致性校验 -> 真机执行并产出测试用例执行报告 共四个主要步骤。

在功能实现上基于 openClaw 建设双 Agent 机制，负责用例生成的 agent 搭配 codex 作为 runtime agent；负责评审用例的 agent 搭配原始 Pi 作为 runtime。两个 agent 具备不同模型、不同 agent runtime、搭载不同 skill、记忆与身份信息完全隔离

部署方面是基于独立的本机电脑部署，原因是流程最后一步要驱动真机执行用例：构建 APP 包、装到测试机上、打开美团 APP 里的小程序容器跑用例，这需要物理连接的设备，云上服务器做不到

同时本机部署带来一个问题：大象机器人需要配置一个回调地址，用户在群里 @ 机器人时，大象服务端会把消息 POST 到这个地址。而本机没有公网 IP，~~企业内网也不允许对外开端口。~~
因此在通信方面
我在中间加了一层公网服务 dxOpen，做反向消息桥。大象的回调地址配到 dxOpen 上，dxOpen 收到消息后不转发，而是存成带 requestId 的标准事件，等本机来取。

本机跑一个 channel 插件，是 openclaw 的自定义渠道实现，channel 插件通过长轮询获取 dxOpen 消息，并将消息传递给 openClaw 的 agent，由此完成消息通信。


## 二、 如何精确保障最多三轮审核

首次派审时后端会创建一条任务记录，写入 taskId、当前轮次、最大轮次、任务状态以及分支和 commit 信息，taskId 贯穿整条链路。质量运营助手每次准备修改并发起下一轮时，不能直接给审核者发消息，必须调 dxOpen 的评审工作流接口——后端凭 taskId 查任务，只有当前轮次小于 3 ~~且任务处于允许修改的状态~~，才授予许可并真正把消息投递给审核者。第三轮仍未通过时，后端原子地把任务置为「人工审核」终态，发出固定通知，之后不再向质量运营 Agent 投递任何修改事件。审核者侧也做同样的上限校验，形成生成方和审核方的双重约束。所以即使出现消息重复、Agent 丢失上下文、或者误发第四轮请求，后端都会因为任务已到终态而拒绝


**思考：本地 channel 是一个服务吗？**

channel 是 openclaw 的渠道适配层，本质上是一个注册进 Gateway 的插件模块，类似设备驱动——openclaw 定义统一的消息渠道接口，插件负责把具体 IM 翻译成这套接口。它不是独立服务，不监听端口，跑在 Gateway 进程里。

一个渠道插件要实现账号解析、能力声明、出站发送这几个必需适配器，入站部分通过 gateway 生命周期钩子接管——我们的大象插件就是在这个钩子里跑那个 25 秒的长轮询循环

**追问回答**：
**它是独立的 npm 包、可插拔、接口级解耦，但运行在 Gateway 进程内**。这三件事同时成立，不矛盾



## 三、完整的流程解读
#### 【背景与约束】

我们这套测试工作流的两个 agent 部署在本机。原因是——流程最后一步要驱动真机执行用例：构建 APP 包、装到测试机上、打开美团 APP 里的小程序容器跑用例，这需要物理连接的设备，云上服务器做不到。

但本机部署带来一个问题：大象机器人需要配置一个回调地址，用户在群里 @ 机器人时，大象服务端会把消息 POST 到这个地址。而本机没有公网 IP，企业内网也不允许对外开端口。

#### 【解法：反向消息桥】

所以我们在中间加了一层公网服务 dxOpen，做反向消息桥。大象的回调地址配到 dxOpen 上，dxOpen 收到消息后不转发，而是存成带 requestId 的标准事件，等本机来取。

本机跑一个 channel 插件，是 openclaw 的自定义渠道实现。它启动时**先注册、再轮询**：用 Bot 的 clientId 和 clientSecret 算出一个 bridge Token。注册信息里除了 Bot 身份，还带了消息处理策略——比如这个 Bot 是接收群里所有消息，还是只响应 @ 它的。注册完成后 dxOpen 就知道两件事：某个大象 Bot 当前由哪个 channel 实例消费，以及事件该怎么过滤和组装。

#### 【长轮询】

注册完，channel 进入长轮询循环：发一个 HTTP 请求给 dxOpen，最多挂 25 秒。一旦有消息立即返回，channel 拿到后马上发起下一个请求。整条链路上本机只有出站连接，不需要公网入口，也不用申请任何网络策略变更。

#### 【入站派发】

channel 拿到事件后做几件事。

第一，**路由**：按 `channel + accountId` 解析到目标 agent。我们两个助手是不同的 accountId，各自有独立的 workspace 和 session store。

第二，**会话隔离**：生成稳定的 session key。私聊按发送者，群聊按「群 + 发送者 + 当天日期」。这样同一个群里不同人不会共用上下文，同一个人隔天也会开新会话。

第三，**包装**：把大象的上下文转成 openclaw 的标准入站信封。

第四，**创建投递器再派发**。这一步是整个机制的核心：channel 不是把消息丢进去等结果，而是**先现场创建一个 ReplyDispatcher**，把「怎么把消息发回 dxOpen」这段逻辑作为 deliver 回调塞进去，requestId 由闭包捕获，然后连同消息一起调 openclaw 的 `dispatchInboundMessage`。

#### 【出站回程】

agent 执行完成后，调用 channel 传入的 deliver 回调拿到内容，带上闭包里的 requestId POST 给 dxOpen。requestId 是 dxOpen 在入站时生成的，含有大象 Bot、群 ID、发送者这些信息。dxOpen 拿它反查出原始会话，以该 Bot 的身份把结果发回原来的群或私聊。

所以整条链路上，**agent 完全不知道大象的 API 长什么样，channel 也完全不理解 agent 的业务逻辑**，两边是接口级解耦的。后面要换通信渠道，agent 侧零改动。

#### 【双 agent 协作】

补充一点：两个 agent 之间没有内部 RPC。质量运营助手要派审时，输出的是「@审核者 + 评审协议」，这条消息通过它自己的 requestId 回到大象群里；大象服务端对审核者 Bot 产生一条新的回调，走一遍完全相同的链路进到审核 agent。本质是两个 Bot 在群里通过 Bridge 往返的**事件驱动协作**。

#### 【诚实的边界】

这套设计有个真实的缺陷：关联状态活在闭包里，不是随消息流转的。channel 进程重启，在途任务的 deliver 闭包就没了，那条回复会丢——而我们的任务动辄跑几分钟。

框架侧有一层缓解：dispatcher 会注册到全局，只要还有回复在途，网关就不会重启打断任务。但这挡不住进程崩溃。

所以我们把三轮评审的强制控制做在 dxOpen 后端，用 taskId 管状态，而不是依赖本机进程存活或 agent 的记忆。即使出现消息重复、进程重启、agent 忘了上下文，后端也能凭 taskId 拒掉超轮次的请求

## 四、评审要求与人工介入时机

测试用例助手依据需求文档生成功能描述型用例，交由审核者助手评审。评审者从两个维度进行评审，分别是用例全面性和正确性，全面性是指参数类型是否包含异常和正常场景、高并发、边界场景等。正确性是用例格式、执行步骤是否清晰等。
审核者最多审核三轮，设置 90 分为达标，不达标则携带原因自动交由「测试用例助手」修改。三轮均不达标则@人工介入

**功能描述性测试用例完成后**，进入可执行测试用例生成环节，可执行测试用例生成的是可直接运行测试用例的代码文件，审核机制也是保持最多三轮与功能性用例一致。

**代码与用例一致性检查是将本次需求的代码 PR 改动和可执行的用例都交给 Agent**，由 Agent 评估代码改动部分，是否被测试用例完全覆盖

真机运行测试用例步骤包含：构建 APP 包 -> 将可执行测试用例构建为美团内部小程序 -> 驱动真机下载最新 APP 包 -> 驱动真机打开美团 APP 及对应的小程序页面 -> 在小程序页面内自动执行测试用例（支持全量执行、按模块执行）-> 自动收集测试用例结果并上传测试报告到 S3

## 五、双 Agent 的优势与劣势
- 优势
	- **提高质量**：质量运营助手专注生成和修改，审核者专注按 EC1-EC13 等规则找问题，减少“自己生成、自己放行”。
	 - **降低单模型偏差**：两个 Agent 使用不同角色提示词、规则集，不同模型，判断视角更独立。
	 - **流程可追溯**：每轮派审、分支、评审意见和结论都在大象消息与任务记录中留痕，便于复盘。
	 - **易扩展**：以后可以增加安全审核、规范审核、代码审核等专职 Agent，不必把所有逻辑塞进一个 Agent。
	 - **风险隔离**：审核 Agent 默认只读、不给修改代码权限；生成 Agent 不拥有最终放行权
- 劣势：
	- **更慢、更贵**：一次任务可能经历生成、审核、修改、复审，多了模型调用和消息往返
	- **错误会传递**：审核意见本身可能错误，生成 Agent 可能机械修改，导致用例质量反而下降
	- **需要兜底**：必须设置最大评审轮次、人工审核终态、超时和幂等控制，否则会产生无限循环或重复执行
双 Agent 的核心价值是职责分离和交叉校验，用额外的时延与系统复杂度，换取更稳定、可审计的用例质量。它适合质量要求高、允许异步处理的场景；前提是用结构化协议和持久化状态机控制协作边界

## 六、审核者审批标准
Agent 需要严格按照评分机制给测试用例打分，仅当测试用例得分大于 95 分时才允许审核通过。评分标准为以下：
- **全面性 70%** （参数类型正常&异常、超长字符、合法枚举&非法枚举、异常 Case、连续多次调用、高并发、边界场景（文件不存在等）、跨端兼容场景（不同端、低端机））
- **有效性 30%**  （用例写入的文件位置正确、用例的可执行步骤清晰、用例的可测试环境正确、满足 TC+EX 语义、JSON 格式正确）

**以及为什么是三轮为最佳**：实际运行中 60%需要三轮审核、40%需要两轮审核。三轮都不通过的概率较少，月维度偶现 1~2 个三轮审核不通过，原因是：需求文档给的内容太长，通常是事件性 API，同一个需求文档中包含 4~5 个事件型 API。举例：流式上传 API，包含：启动流式分片上传、停止分片上传、取消流式分片上传

## 七、多个用户并发机制
- 生成阶段每个用户的消息是 session 隔离，不会存在影响
- 写入代码方面，代码分支都是基于 master 拉取，使用 用户名+需求+时间命令，不会有冲突
- 执行测试用例阶段会阻塞排队，单个测试手机一次仅能安装单个 APP 独立执行测试用例

## 八、多个 agent隔离机制
- 两个agent是以docker容器隔离的，不会存在相互干扰、修改对方文件的可能性
- 配置sandbox:{scope:"agent"}，每个Agent一个独立容器
- 本机需安装并启动 Docker Desktop，然后配置openclaw sandbox，Agent第一次执行工具时，openclaw会自动启动沙箱容器

最终，两个Agent的文件操作在各自Docker容器中执行。Docker会给每个容器独立的文件系统视图，因此两个Agent无法直接互相修改文件

## 九、项目的难点或亮点

我认为最大的难点不是让 AI 生成用例，而是解决“AI 生成的用例谁来证明它可信”这个循环依赖。因为这套系统的目的是替代 RD 手工准备环境、写用例和跑三端九种组合，所以如果只追求生成速度，产物一旦漏了边界、和代码行为不一致，或者真机无法执行，整个自动化就没有价值了。

我把这个问题拆成了四层：
第一层是需求理解是否完整，用 11 种覆盖规则和 13 条评审规则，把“写得全不全”变成可检查项；
第二层是避免生成者自己放行自己，因此让生成 Agent 和审核 Agent 使用不同 Runtime、模型、角色和权限，审核方只读且不能修改代码；
第三层是用真实 PR Diff 和增量用例做一致性校验，发现新增参数、错误码和条件分支是否遗漏；
最后一层才是真机执行，在 Android、iOS、HarmonyOS 和三个容器的实际环境中验证。

另外特别关注工作流的可控性：双 Agent 不能只靠提示词约束三轮，而是让 `taskId` 贯穿链路，由后端状态机持久化轮次和任务状态。第三轮仍不通过就原子转人工，避免模型遗忘上下文、消息重试或进程重启后继续无限循环。

最终没有把 AI 当作一个一次性生成器，而是把它做成了“生成—独立评审—源码校验—真机验证—报告回流”的可信闭环，用不同强度的证据逐步降低不确定性

## 十、T01~T11（生成规则） 及 EC1～EC13（评审规则）
- **T01 正向用例**：合法输入、正常链路
- **T02 反向用例**：类型错误、空值、不传、非法枚举
- **T03 异常用例**：异常状态、错误码、资源耗尽
- **T04 边界用例**：数值上下界、集合边界、文件或资源存在性边界
- **T05 流程用例**：多接口先后依赖、状态流转、参数联动和条件必填
- **T06 权限用例**：首次授权、拒绝授权、权限撤销后调用及三端权限差异
- **T07 安全用例**：注入攻击、路径穿越、敏感数据保护、签名或加密防篡改
- **T08 性能用例**：大数据量、高频调用、并发压力、耗时和资源占用
- **T09 兼容性用例**：弱网或网络切换、系统版本差异、不同机型尤其低端机
- **T10 幂等 / 重试用例**：连续重复调用、并发竞争、副作用一致性、失败后的重试
- **T11 降级与容错用例**：外部 SDK 不可用、断网、本地资源缺失、兜底与快速失败

- **EC 1 canIUse 覆盖**：API、入参和出参能力声明是否完整，是否覆盖嵌套字段与三端平台差异
- **EC 2 通用用例**：每个入参是否按类型矩阵覆盖必需场景，出参及嵌套出参是否有断言
- **EC 3 场景用例**：是否覆盖应命中的流程、并发、大数据、权限、降级等场景；不可模拟错误码是否说明
- **EC 4 用例类型**：T 01–T 11 中该 API 应命中的类型是否充分覆盖，覆盖率是否达到阈值
- **EC 5 文件位置**：用例文件路径、模块名和 API 文件名是否符合目录规范
- **EC 6 JSON Schema**：JSON 是否可解析，顶层结构、标准用例、场景测试和 TC/EX 格式是否合规
- **EC 7 模块与文件**：是否一 API 对应一份 JSON，模块和 API 原名是否与文档一致
- **EC 8.1 字段忠实**：字段名、字段类型、取值范围是否忠实于 API 文档，避免虚构
- **EC 8.2 errno 忠实**：期望错误码是否来自该 API 文档；无法模拟的错误码是否明确说明
- **EC 8.3 平台分支忠实**：iOS、Android、HarmonyOS 的支持范围、平台限定和差异是否与文档一致
- **EC 9 描述可执行**：TC 是否有具体动作和值，EX 是否写清成功/失败和可断言结果
- **EC 10 描述具体度**：是否明确平台、次数、数据量、关键断言等必要限定，避免“测试一下”“大数据测试”这类模糊描述
- **EC 11 环境可达**：用例指定的平台和执行前提是否真实可用，不在不支持的平台安排执行
- **EC 12 可验证性**：副作用是否清理；并发是否断言全部子调用；流程是否验证关键中间状态
- **EC 13 内容去重**：是否存在场景和预期结果相同或语义重复的用例
