## 一、为什么需要多 Agent 框架
- **第一，上下文会爆炸**。既要多方调研多个方案又需要执行方案编写
- **第二，职责混乱**。一个 agent 即当评审者也当程序员
- **第三，没法并发**，一个 agent 一次只能做一件事
## 二、渐进式演进多 Agent 流程

**原型阶段**：使用单 Agent 把系统流程跑起来，当遇到上下文撑爆、某类子任务质量不佳时，再把对应环节拆出来交给专门的 Worker Agent 执行。单 Agent 的优势在于架构简单、维护成本低、链路透明易于调试

**演进阶段**：将原型阶段的 Agent 瓶颈均拆分交个多个专门的 agent 执行，演进过程是自然而然的，演进阶段设计对多 Agent 的编排。Agent 流程编排通常有两种方案**中心化和去中心化**方案
- **去中心化方案**：是指由多个 Agent 通过共享的消息队列或状态空间自行协商、直接通信。目前更多停留在学术研究阶段，原因是去中心化方案普遍存在几类问题：任务分配没有协调、执行顺序没有保证、失败没有感知、没有 agent 来最终确认任务整体的完成质量
- **中心化方案**：目前业界使用的多 Agent 方案几乎都是中心化方案，由一个「总调度员」规划整体路径、派发任务、对任务的整体结果负责。通常有以下几种变体，用于适配不同复杂度的场景
	- **静态路由**（Static Router），任务拆分和分配规则是预先定义好的，比如「遇到代码任务交给 Coder Agent，遇到搜索任务交给 Researcher Agent」，逻辑简单可预测
	- 进阶一点的是**动态规划**（Dynamic Planner），「总调度员」 本身是一个 LLM，它会根据用户输入动态生成任务计划，决定需要几个步骤、每步交给谁，计划本身也可以在执行过程中调整
	- 最复杂的是**自适应编排**，「总调度员」不仅动态规划，还会根据 Worker 的执行结果实时调整后续计划，比如 Researcher 搜回来的信息不够，「总调度员」会追加一轮搜索任务，而不是继续往下走。实际项目里，大多数场景用动态规划就够了
## 三、多 Agent 如何协作
**方式一**：**消息队列+异步通知** [[Claude的多Agent设计机制]]

**方式二**：**共享状态**，所有 Agent 都读写同一个状态对象，LangGraph 就是这个思路设计

**共享状态的弊端**：多个 Agent 同时读写同一个状态，容易出现结果覆盖、读到一半更新的脏数据

**共享状态的关键设计**：
- **首先状态结构分为「全局状态」和「局部状态」两层**：全局状态存所有 Agent 需要读取的信息，例如当前任务进展等；局部状态放每个 Agent 自己的中间过程，局部状态不会暴露给其他 Agent
- **其次是写入规则明确**：使用「只追加不覆盖」方式，和 LangGraph 的思路一致，每个节点返回的是「增量更新」
- **最后是错误状态处理**：假设某个 Agent 执行失败，它的错误信息也应该写入状态，后续的 Agent 读到这个错误状态，才能做出正确决策。比如：跳过这一步或者直接终止任务

## 四、基于 LangGraph 讲解多 agent 动态路由设计

**4.1 定方案**
我会用 Plan-and-Execute 加 调度器 的组合。图上定义五类节点：规划器、调度器、若干领域 worker Agent、重规划器、收尾节点。拓扑是星型——调度器出发到各个 worker，各个 worker 再回到调度器

**4.2 关键设计**
LangGraph 的图是编译期静态的，节点和边在编译时就固定了，运行时长不出新节点。所以"让 agent 自行规划执行线路"不是让它生成一张新图，而是让规划器通过结构化输出，产出一个带依赖关系的任务**有向无环图**，存进 State。节点集合是静态的，动态的只是这一次走哪几条边

**4.3 具体落地**
规划这一步三件事。
- 第一，维护一张 agent 注册表，每个 agent 带能力描述，像写 tool description 一样注入提示词当能力清单——规划质量基本上取决于这份清单写得好不好。
- 第二，输出的 agent 字段用枚举锁死，模型指派不到不存在的 agent。
- 第三，生成之后跑一遍程序化校验：id 有没有重复、依赖有没有指向不存在的步骤、拓扑排序查有没有成环、步数有没有超限；不合法就把错误信息拼回提示词让它自己改，最多三次，三次还不行就降级成单步执行（即一次普通的 LLM 调用回复用户问题），不让整个系统崩

**4.4 执行与并行**
调度器我特意没用 LLM，它是一个纯函数：从 State 里挑出"还没做过、且依赖的前置步骤全部成功"的步骤，挑出几条就是几条能并行，用 Send 一次性分发出去。这里有个细节——被 Send 触发的节点拿到的不是全局 State，而是 Send 的 args 原样，所以上下文隔离不需要额外机制：我给依赖步骤的结果全文，其他已完成步骤只给一行摘要。并行的 worker 同时写回结果，靠字段上的 concat reducer 合并

**4.5 容错与人机协同**
单步失败先重试两次，仍失败就把失败原因写进 State，而不是抛异常炸掉整张图——失败的步骤会把下游卡住，自然逼出一次重规划

重规划器只在"卡住"或"计划跑完"时才调

防止无限执行的护栏是四个数字：
- 单份计划最多 XX 步、最多重规划 XX 次、校验打回 XX 次、全局超步上限 XX
最后配 checkpointer 做断点续跑，用 interrupt 在计划生成后停一下让人审批

**4.6 收尾**
一句话总结：能力集合有限且可单测，编排交给模型；不确定性只收敛在规划和重规划两次调用里，中间的调度全是确定性代码，出问题能立刻分清是规划错了还是某个 agent 执行错了

**4.7 Agent 路径规划进阶**
实践中最稳健的做法是两种路由组合用：主流程用静态路由，把确定性的节点切换都写成规则，保证绝大多数情况下系统行为稳定可预测；只在遇到没有匹配规则的边缘情况时，才交给 LLM 动态决策。这样静态路由负责「保底」，动态路由负责「兜住异常」，两者互补



**checkpointer**：图 State 的完整快照，**框架自动写**，每个超步一份；绑定 `thread_id`，一次会话内；断点续跑、时间旅行调试、human-in-the-loop、容错重放
**store**：你自己定义的任意 KV 文档，**你在节点里手动** `put`；**跨 thread、跨用户**，用 namespace 分层；长期记忆：用户偏好、跨会话事实、agent 学到的东西

## 五、社区多Agent框架

#### 5.1 流程编排类
- **CrewAI**：CrewAI 是开源的Python 多 Agent 框架。
	- **优势**：它以"角色扮演"为核心抽象——为每个 Agent 设定角色、目标与背景，支持顺序与层级两种流程及 Agent 间委派，配合 YAML 配置和 CLI 脚手架，上手快、心智负担低；
	- **劣势**是本质仍靠 prompt 驱动，稳定性与可控性弱、调试困难、token 消耗高，复杂状态与断点恢复不如 LangGraph，且仅支持 Python。
	- **适用场景**适合内容生产、市场调研等"多角色接力、每步需开放判断"的中等复杂度任务和快速原型验证，不适合强确定性、可审计的生产级工作流
- **LangGraph**：LangGraph 是开源的 Python 与 JS/TS 双版本都支持的Agent框架。
	- **优势**：它以有向状态图为核心抽象——节点、边与共享 State 显式建模，原生支持循环、条件路由、持久化 checkpoint、断点续跑、人工介入与时间旅行回溯，可控性和可调试性极强，且可脱离 LangChain 独立使用；
	- **劣势**：是抽象偏重、学习曲线陡、样板代码多，简单任务属于杀鸡用牛刀，API 迭代快、文档易过时。
	- **适用场景**：适合需要审计、长时运行、复杂状态流转与人工审批的生产级 Agent 工作流，不适合快速做 demo 或一次性脚本
- **LlamaIndex Workflows**：以Python为主同时也支持TS版本的开源框架
	- **优势**：它采用事件驱动抽象——用 `@step` 定义步骤、靠收发 Event 串联，无需显式声明边，异步优先，天然支持并发扇出扇入、循环与分支；最大优势是与 LlamaIndex 的文档解析、索引、检索生态无缝衔接
	- **劣势**：社区规模小于 LangGraph，多 Agent 原语较年轻，调试与可视化工具偏弱，控制流分散在各事件里、大型流程难通读
	- **适用场景**：适合 RAG 密集型、文档处理与复杂检索编排，尤其是已在用 LlamaIndex 的团队

#### 5.2 可视化/低代码
- **Dify**：Dify 由中国团队 LangGenius 推出，是低代码 LLM 应用平台而非代码框架。
	- **优势**：是可视化拖拽编排 Workflow、内置知识库 RAG、统一接入数十家模型、自带 Prompt 调试与日志标注，支持 Docker 自托管、数据可控，非开发者也能上手，从 0 到可用极快，中文社区活跃。
	- **劣势**：是复杂逻辑很快撞墙，版本管理、测试与协作远不如代码，深度定制需改源码，多 Agent 能力偏弱，流程一大就难维护。
	- **适用场景**：适合企业内部知识库问答、客服机器人与快速验证，不适合高度定制的生产级 Agent 系统
- n8n
- **Coze**：Coze（扣子）是字节跳动出品的零代码 Agent 平台，云服务闭源，但核心的 **Coze Studio 已于 2025 年 7 月以 Apache 2.0 开源**，Docker 最低 2 C 4 G 即可完全私有化部署，商用无限制。
	- **优势**：是纯可视化搭建、UI 精致、内置知识库/工作流/插件与 Multi-Agent 编排，云版还能一键发布到抖音、飞书、微信等渠道。
	- **劣势**：是开源版缺失分发渠道、音色等能力限商业版，插件市场与免费模型额度不含在内，迭代滞后于云版，且官方提示公网部署存在代码节点执行、SSRF、越权等风险；代码化与深度定制能力弱，复杂逻辑易撞墙。
	-  **适用场景**：适合快速做 C 端 Bot、企业内网私有化助手，不适合高度定制的生产级系统
