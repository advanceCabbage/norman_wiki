## 一、需要设计的项
#### 1.1 状态与持久化（最核心）
长任务的本质是进程可以卡死，任务不能死
- **状态必须落库，不能只在内存**。LangGraph 的checkpointer 可在每个节点执行完存一次快照，崩溃后按 `id` 恢复继续跑
- **幂等**：每个有副作用的步骤要有幂等键（写文件、发请求、写库）。恢复重跑时不能重复扣款/重复发消息
- **基于 LangGraph 实现**：每次传入 id、每个 step 保存 checkpoint（不要用内存级别的），进程崩溃后用同一个id 恢复。具有副作用节点必须携带唯一标识，例如：发消息、写文件等避免重复发送或执行
#### 1.2 上下文管理
长流程一定会撑爆 context，这是长任务和短对话最大的区别
- 别把全部历史塞进 prompt。策略：滚动摘要（老消息压缩成 summary）+ 外部记忆（把中间产物写文件/写向量库，prompt 里只放索引和摘要）
- 工具返回的大块内容（网页、文件全文）落盘，prompt 里只回传摘要 + 引用 ID，需要时再取
- 间隔时间超过 1 h 或轮数太多的上下文可以由模型选择去掉；工具执行结果等可以去掉
- **基于 LangGraph 实现**：每次调用由一个 build_context 节点拼装：目标 + 当前计划步骤 + 摘要 + 必要引用

#### 1.3 控制流与终止条件
- **架构选型**：简单任务 ReAct 循环够用；长流程建议 **Plan → Execute → Reflect**，先出计划（可持久化、可人工改），再逐步执行，每步后检查是否要重规划
- **硬性熔断**：最大步数、最大 token/成本、最长运行时间、**无进展检测**（连续 N 步状态没变化就停）。不设这些必然会遇到烧钱死循环
- 明确的终止判据，别让模型自己决定"我做完了"，要有可验证的完成条件
- **基于 LangGraph 实现**：每步执行后都走 reflect 节点，由规则优先、模型辅助判断：完成条件是否满足、下一步是否还有效、是否需要重新规划、是否触发熔断

#### 1.4 可靠性
- 工具层统一：超时、重试+指数退避、错误信息**结构化回传给模型**（让它自己纠错，而不是整个任务失败）；同时区分可重试任务（网络超时）和不可重试任务（业务明确报错信息，无操作权限等）
- 模型降级链路，主模型不可用时切备用
- **基于 LangGraph 实现**：给所有工具统一包一层 ToolExecutor 错误统一返回：网络超时、业务错误等。同时通过retry_policy 给节点配置重试策略函数

#### 1.5 人机协作
- 支持在任务图中设审批节点：考虑长时间暂停后再继续任务
- 支持中途注入新指令（考虑立即加入或当前任务完成加入）、修改计划、终止
- **基于 LangGraph 实现**：通过 interrupt 持久化状态，等待多久都可以；随后以同一个 `thread_id` 和 `Command(resume=...)` 恢复

#### 1.6 调度与并发
- 别在 HTTP 请求里跑长任务，上任务队列（MQ + Redis），API 只负责创建 run 并返回 ID，worker 异步执行，前端轮询/SSE 拿进度
- 子任务能并行的并行（LangGraph 支持分支/fan-out），但注意并发写状态的冲突

#### 1.7 考虑子agent
将消耗上下文、耗时操作交给子 agent 处理

#### 1.8 可观测性与评估
- 记录每步的 token 和成本，长任务的成本失控是常见问题
- 记录每个流程的执行，例如：工具的输入输出、流程的执行轨迹、模型的系统提示词与输出等
- 评估要做**轨迹级**（步骤是否合理、有没有绕路），不只看最终答案

## 二、长任务拆分

#### 2.1 静态拆分
**定义**：人工提前把任务流程设计好，固定成一个确定的 Workflow，按照执行顺序规定每个步骤执行的内容
**优势**：行动轨迹完全可预测，出现问题易于排查
**劣势**：灵活性低，遇到没有考虑到的场景容易卡住流程

#### 2.2 动态拆分
**定义**：把「任务拆解」这件事交给大模型做，给大模型一个目标，要求大模型输出一个完整的计划，后续再按照计划一步步执行，这也是 Plan-and-Excute 的思想

**首先**：将目标任务拆分为一个个可执行的小任务
**然后**：判断任务之间的依赖关系，决定哪些任务可以并行执行。实现方式是将依赖关系画成一张**有向无环图**，每个节点是一个步骤，边表示「依赖」。没有依赖的节点就能同时跑，依赖它们的节点要等父节点完成。
**接下来**：拿着任务列表开始执行任务，并在单个任务结束后更新任务表及同步结论
**最后**：「汇总」将各步骤的执行结果汇总，生成最终的输出

**关键点**：任务拆分粒度的把握，拆的太细则步骤太多，LLM 调用次数越多，每步事件太小，LLM 无法看到全局；拆的太粗则回到了拆分之前，模型的上下文窗口、注意力受限
**示例**：「搜索 A 产品信息」属于原子，「分析 A 产品优劣势」不属于原子
**最佳实践**：将每个步骤拆分为**原子级别**，**定义原子级别则是你能给当前步骤写出清晰的函数签名吗？能则是原子的，否则不是原子的**

#### 2.3 长任务拆分的补偿机制
- **Replan 机制**：任务执行过程中，发现原本制定的任务不符合实际情况，则重新编写任务计划。代价是每步执行结果都需要调用一次「评估计划」，token 和延迟都会增加。实践中的做法是：不是每步都触发 Replan，而是设置触发条件，仅到某步输出和预期差异很大或执行失败时，才启动 Replan

#### 2.4 拆分结果的验证标准
- **第一个是「完备性」**，也就是所有步骤加在一起，能不能覆盖原始任务的全部要求，有没有遗漏
- **第二个是「独立性」**，也就是每个步骤的职责边界是不是清晰，有没有两个步骤在做同一件事，或者某个步骤的输出和另一个步骤的输出有重叠
- **第三个是「可验证性」**，也就是每个步骤执行完之后，能不能用一个简单的标准判断它做对了没有。这一点在实际项目中特别容易被忽视，但它直接决定了你能不能做自动重试和质量把控

举例：你拆了一个步骤叫「搜索竞品 A 的定价信息」，如果没有完成标准，执行完成后只能人工确认。但假设在拆分时便定义了需要包含价格数字和计费模式，执行完成后自动检查输出是否包含这两个要素即可

## 三、以美团助手为例 agent 的主流程设计

用户目的：制定出行计划

**核心思路**：通过主子 Agent 规划用户行程，先讲方案规划、再讲注意事项
主 Agent 负责：用户 需求澄清、规划任务、回复整体方案
功能型子 Agent 负责：分别负责出行规划、景点游玩规划、酒店预定等

**首先**：收到用户问题时，先检索历史用户信息。用户信息分两类：
1. 用户身份信息，记录用户的偏好、特征等。例如：用户平时出行是自驾还是打车等
2. 历史会话信息：使用混合检索方式，历史会话中和本次相关的信息
**接下来**：主 Agent 针对行程中不清晰的点，结合用户记忆信息进行针对性的询问，目的是澄清本次出行需求。例如：出行人数、游玩时间、预算等；需求澄清之后制定整体的行程规划，包含：出行任务、景点游玩、吃饭、住宿等
**然后**：将每个子任务分发给不同的子 agent，例如：出行 agent 依据用户过往信息+本次出行目的地和时间制定可行的出行计划；景点游玩 Agent 依据用户过往旅游偏好+本地旅游目的地+天气等制定可行的计划
**接下来**：主 agent 收集多个子 agent 的调研结果，汇总并按照约定格式回复给用户确认，按照用户建议继续优化行程（重新制定计划、子 agent 重新执行）
**最后**：考虑工具调用失败退避方案、上下文过长、支付等具有副作用的操作的幂等性、主子 agent 通信、大模型调用失败的降级方案、将本次用户的旅行偏好记录下来方便下次使用、考虑评测集

## 四、AI 基于三给出的优化版

以美团助手为例，用户的目标是制定出行计划。我会采用主子 Agent 架构：**主 Agent 负责需求澄清、任务拆解、全局协调和最终回复；功能型子 Agent 分别负责交通、景点、酒店和餐饮等领域的调研与规划。** 主 Agent 对整趟行程的可行性负责。

**首先，结合用户记忆理解本次需求。**

用户记忆分两类：一类是结构化的用户画像，比如交通偏好、住宿偏好和饮食习惯；另一类是历史会话信息，通过关键词与语义混合检索，召回和本次出行相关的内容。

这里需要处理记忆的时效性和冲突：本次用户明确提出的需求优先于历史偏好，同时避免把一次性的出行选择直接当作长期偏好。

**第二，主 Agent 有针对性地澄清需求，建立本次行程的约束。**

结合当前问题和历史信息，优先确认会影响方案可行性的内容，比如出发地、目的地、日期、人数和预算，减少重复询问。

同时区分硬约束和软偏好。例如，“周日晚必须返回”是硬约束，“尽量少走路”是软偏好。信息足够后，先形成整体行程骨架，并把已确认需求维护成结构化的行程状态，作为后续主子 Agent 协作的共同依据。

**第三，拆解任务，按依赖关系调度子 Agent。**

交通 Agent 查询可行的交通方式和抵达时间；景点 Agent 结合游玩偏好、开放时间、预约要求和天气安排候选景点；酒店 Agent 根据预算、人数和游玩区域筛选住宿，餐饮 Agent 则结合路线和饮食偏好提供建议。

独立的查询可以并行执行，有依赖的任务按顺序推进。例如，抵达时间会影响第一天的游玩安排。

每个子 Agent 只接收与任务相关的需求和记忆，并返回结构化结果，包括候选项、费用、时间、来源和限制条件。具体的价格、库存、距离等事实，通过业务工具获取。

**第四，主 Agent 整合结果，并进行全局可行性校验。**

重点检查时间是否冲突、路线是否合理、总预算是否超出，以及是否满足用户的硬约束。例如，交通中午才到达，就不能安排上午入园。

发现冲突后，主 Agent 调整方案或让相关子 Agent 补充查询；如果没有可行方案，就明确说明冲突，并让用户选择需要放宽的条件。

校验通过后，按照“每日安排、交通住宿、费用和关键注意事项”的格式输出，说明主要取舍。会影响方案成立的问题，比如门票售罄，需要在规划阶段解决。

**第五，根据用户反馈做增量调整。**

用户确认或提出修改后，更新行程状态，只重新执行受影响的任务。例如，更换酒店后，重新检查通勤路线和周边餐饮。

同时维护方案版本，防止旧版本子任务的结果覆盖用户最新的需求。

**工程上，我会重点保障执行可靠性和状态一致性。**

工具调用失败时，区分可重试错误、业务不可用和结果未知，设置超时、有限重试和降级策略；关键状态持久化，支持中断恢复。上下文过长时，保留已确认约束和当前计划，压缩历史过程。

如果涉及下单或支付，需要明确用户授权，并确认具体商品、日期、金额和退改条件。通过幂等机制防止重复操作；请求超时且结果未知时，先查询订单状态，再决定后续动作。

任务结束后，将适合长期保存的偏好更新到用户记忆中，本次临时条件保留在行程状态里。

**最后，用评测验证这套设计是否有效。**

我会同时评估行程质量和系统表现：包括硬约束满足率、事实准确性、偏好匹配度、用户修改轮次、端到端耗时和任务成本。评测集除了正常规划，还要覆盖历史记忆冲突、用户中途改期、库存变化、工具超时和无可行方案等情况。
