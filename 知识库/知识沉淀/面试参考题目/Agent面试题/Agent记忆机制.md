## 一、四层记忆机制

- **感知记忆**：当前输入的原始内容
- **短期记忆**：context window 里的对话历史，包括存入到 JSONL 中的文件
- **长期记忆**：存在外部数据库、语义检索召回 + 关键字检索
- **实体记忆**：已知历史对话提取的关键事实，比如：用户偏好习惯等。通常使用结构化存储
实际设计时要解决三个核心问题：存什么、怎么存、什么时候取出来用

## 二、openClaw 的记忆机制
##### 2.1 记忆文件类型
- **用户身份信息类文件**：AGENTS.md、`SOUL.md`、`IDENTITY.md`、`USER.md` 等文件，
- **长期记忆类**：分两种类型，一类是可以跨任务、每次对话时均可见的内容存储在 MEMORY.md；另一类是明细层，支持按照日期、项目等主题创建的文件，存储在 memory 目录 `memory/YYYY-MM-DD.md`。判断一条记忆是写入 MEMORY.md 还是 memory 目录下是由 `AGENTS.md` 中的 Agent 行为约定，以及自己的提示词决定的
##### 2.2 记忆文件注入时机与注入策略
- **用户身份信息类文件**：会在 session 首次执行时生成快照，session 运行途中修改身份信息文件，身份信息文件不会动态注入。通常需要重启 gateway 、/new 或 /reset (new 是新建窗口；reset 是清空历史对话通常会保留模型选择)
- **长期记忆类**：
	- MEMORY.md 不超过 2 万字符时会全量注入到上下文中
	- 当模型判断当前用户问题中涉及旧决策、人物、偏好等时才主动调用记忆检索工具对 memory 文件夹中长期记忆进行混合检索，存储时使用的SQLite 数据库既进行了向量存储也进行了原文存储，**混合检索时向量权重 0.7、全文 FTS 权重 0.3**。记忆检索时会阻塞主 agent，直到检索内容回来才会继续主 agent Loop

## 三、Claude code 的记忆机制
##### 3.1 记忆文件类型
- **显示记忆**：由人工或初始化生成的CLAUDE.md 文件
- **隐式记忆**：由 Claude 自行总结的记忆文件，通常以 project 命名文件夹，存在四种类型的记忆文件，分别是：
	- **user**：用户的角色、目标、偏好、职责、知识背景，用来调整 Claude 的协作方式
	- **feedback**：用户对 Claude 工作方式的反馈，包含“以后避免什么 / 继续做什么”，强调记录原因和使用方式
	- **project**：关于当前项目的目标、计划、事故、bug、长期背景，但必须是不能从代码或 git 历史直接推导出来的信息
	- **reference**：外部系统入口，比如 Linear、Slack、Grafana dashboard 等
##### 3.2 记忆文件注入时机与注入策略
- **显示记忆**： CLAUDE.md 文件会在会话开始从磁盘读取，注入到上下文中。使用/clear、/compact 等均会再次从磁盘读取 CLAUDE.md 文件
- **隐式记忆**：每轮对话都会加载 `MEMORY.md` 文件的前 200 行或 25 K 数据注入到上下文中，`MEMORY.md` 中存储的是隐式记忆文件的概要信息。主 agent 可以知道记忆信息的概要情况。
	- 另外启动独立的记忆选择器，传入用户问题和各个记忆文件的 manifest，有单独的模型判断最相关的五个记忆文件，并以结构化 JSON 返回最多五个候选文件名。不阻塞主 agent 执行任务，主 agent 在每轮工具调用结束后检查记忆文件是否筛选完成，如果任务结束前都没有返回最相关的记忆文件则放弃



## 四、社区开源的记忆存储库

#### 4.1 Mem0
Mem0 的核心是把对话转化为可检索、可维护的长期记忆：写入时通过 LLM 提取用户偏好、背景等事实，结合已有记忆去重，再生成 embedding 并持久化；Mem 0 特别适合「个性化记忆」场景，检索时按 user_id 等限定范围，召回与当前问题相关的记忆，由应用注入模型上下文，实现跨会话个性化。它的关键在于事实提取和记忆管理。

默认使用的 Qdrant 向量数据库，没有引入图数据库（Neo4j 等），使用普通数据库维护**实体 ->  关系 -> 实体**

#### 4.2 Letta 莱塔
Letta 前身是大名鼎鼎的 MemGPT，Letta 把 Agent 的记忆分成了三个层级。
- **Core Memory** 是始终留在 context window 的核心信息，例如：用户画像
- **Recall Memory** 是最近的对话历史，类似于缓存，按时间顺序存储，支持快速回溯
- **Archival Memory**:长期归档的知识
最有意思的是，Letta 让 Agent 自己通过工具调用来管理记忆，Agent 决定在三个层级中移动记忆，例如将某条记忆从 Core Memory -> Recall Memory

#### 4.3 Zep
Zep 引入来「时间感知」的概念，Zep 给每条记忆标注「有效时间窗口」。通过时序知识图谱来管理记忆的生命周期，自动识别过期记忆

## 五、生产级记忆整合策略

**目的**：消除内容重复、内容过期、互相矛盾的记忆内容，提升检索的质量

- **第一步去重**
把语义相近的多条记忆合并成一条更完整的版本

- **第二步冲突消解**
当两条记忆互相矛盾时，保留时间更新最近的那条，另外一条标记为过期

- **第三步抽象提炼**
本质上是把情节记忆转化为语义记忆的过程

## 六、Agent 使用记忆的三个步骤：读、用、写
#### 首先：任务开始前读取记忆
从实体记忆里取出用户的结构化偏好（语言偏好、风格要求、过往决策），再用任务描述作为查询词，去长期记忆里做一次语义检索，拿回最相关的历史背景。把这两部分信息拼进 system prompt 的开头，Agent 进入任务时就已经带着完整的「用户画像」，不需要用户重复交代背景

#### 然后：任务执行中，持续用记忆
如果某个执行步骤需要特定的专业知识（比如查某个 API 的文档、回想某次历史决策），Agent 可以临时发起一次长期记忆检索，把「查记忆」封装成一个 Tool，用当前上下文作为查询词，把检索结果注入到这一步的 context 里，用完即走，不需要永久保留在 messages 中

#### 最后：任务结束后，主动写记忆
任务完成，进行最后一步：把本次任务产生的新知识写回持久化存储。具体来说，如果用户在对话中表达了新的偏好，就**更新实体记忆**的对应字段；如果任务产生了有价值的结论，就把这条**摘要写入长期记忆**，embedding 后存入向量数据库，供下次检索

## 七、短期与长期记忆怎么存、粒度是多少

**短期记忆**：通常的短期记忆是纯粹的消息列表，所有消息都往列表中存。进阶的概念是**结构化工作记忆**。其核心思路是给记忆划出几个固定区域，比如一个区域专门放「当前任务目标」，一个区域放「已确认的中间结论」，一个区域放「待验证的假设」。每一步执行完之后，Agent 不只是把新消息追加到列表末尾，而是主动更新对应区域的内容，把过时的中间结论替换掉，把已验证的假设移到确认区。

**长期记忆**：长期记忆比较合理的存储粒度是，按「一次完整交互」或「一个独立的知识点/事件」来存。前者是用户的一个具体请求加上 Agent 处理结果，信息完整性好；后者是把「用户偏好：Python，简洁风格，英文注释」打包成一条结构化记录，检索时一次拿到完整偏好，不会碎片化

进阶的长期记忆可以按「类型」分为三层：
- 第一种是**语义记忆**（Semantic Memory），存的是事实性知识，比如「用户是 Python 开发者」「项目预算上限 5 万」，这些是不随时间变化的客观信息
- 第二种是**情节记忆**（Episodic Memory），存的是具体事件的经历，比如「上周二用户让我写了一个爬虫，中间因为反爬策略改了三次方案」，它带有时间线和因果关系
- 第三种是**程序记忆**（Procedural Memory），存的是「怎么做某件事」的方法论，比如「给这个用户写代码时，先确认风格偏好，再写主逻辑，最后加注释」，它更像是 Agent 积累下来的行为模式

长期记忆还需要保证「**记忆衰减**」问题，常见的做法是：
- 给每条记忆加一个「新鲜度权重」，检索排序时同时考虑语义相似度和时间新鲜度，越久远的记忆权重越低
- 另一种做法是定期让 LLM 审查长期记忆库，把过时的、矛盾的记忆标记为失效或者合并更新，保持记忆库的「健康状态」
