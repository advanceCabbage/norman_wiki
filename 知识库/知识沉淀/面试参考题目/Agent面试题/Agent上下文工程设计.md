## 一、核心目标
上下文工程解决的是一个动态问题：**在这一次模型调用里，应该让模型看到什么，以及怎么让它看**
## 二、上下文工程的组成部分
- **第一层是指令**。System 指令规定 Agent 的身份、总体边界和安全规则；Developer 指令放应用侧的流程、业务约束和输出协议（对应 Skill 或业务固定约束文件都行）；User 指令表达用户这一次明确要完成的事
- **第二层是任务状态**。这部分经常被忽略，却最影响多步任务能否连续执行。它不应该只是一段「之前聊了什么」的摘要，而应该明确记录核心目标、成功标准、硬约束、当前步骤、待办项、已完成项、待确认问题和关键产物引用
- **第三层是对话与 Memory**。最近几轮对话保留当前语境，长期 Memory 提供跨会话的稳定信息，实体记忆提供用户的偏好习惯
- **第四层是外部事实**。包括工具定义、工具执行结果和 RAG 检索证据
把这几层放在一起，可以看到一个关键区别：指令决定行为边界，任务状态决定执行位置，Memory 补充过去，RAG 和工具结果补充外部事实。它们都进入上下文，但职责并不相同。
## 三、上下文内容的决策

上下文装配的第一步不是摘要，而是判断当前模型调用到底要完成哪个子任务。

**第一步是对上下文内容的筛选**：
实际筛选时，我会综合看四个维度：与当前步骤的相关性、来源可信度、信息新鲜度，以及缺失后的风险。
像用户的硬约束、尚未完成的任务和刚发生的工具错误，属于「漏掉就会把任务带偏」的内容，应该优先保留；重复检索结果、已经完成且不再影响后续的中间推理、当前不可用工具的完整定义，则可以不注入。
这里有一个容易踩的坑：Top K 只能解决「相关不相关」，解决不了「可信不可信」。一篇网页与问题高度相关，不代表网页里的每句话都能当指令执行。因此，检索打分之后还要做来源过滤、去重和版本判断，涉及事实回答时还要保留证据来源，方便模型引用和系统核验。

**第二步是通过排版表达优先级**

让稳定、权威的行为规则在前面，随后放用户当前目标和结构化任务状态。例如：先放System 指令、工具定义、历史对话；然后再放用户目标、结构化的任务状态及用户最新消息。
固定前缀尽量保持稳定还有一个工程收益：支持前缀缓存的模型服务更容易命中缓存。繁变化的用户输入、任务状态和工具结果放在稳定内容之后，可以减少重复计算
