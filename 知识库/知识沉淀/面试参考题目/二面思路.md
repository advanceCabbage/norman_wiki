## 四、最难或亮点的事项

智能客服项目的难点，是如何让一个概率型的大模型在研发支持场景中变得可信任、结果可量化。研发咨询和普通客服不同，用户问的是 API 参数、端能力差异和实现行为，错一个字段就可能导致线上问题；但又不能为了避免答错，把所有问题都转人工。

所以我没有把目标定义成“搭一个 RAG”，而是把它拆成一套可信度闭环：**首先**治理知识质量及时效性，不同知识源采用不同的入库和返回策略，打通 API 文档与知识库同步更新机制；**其次**设计回答边界，信息不足就追问，需要实现细节时再进入源码检索，无可靠依据时不强答；**然后**用用户咨询机器人后是否仍提工单，结合点踩和会话复盘，衡量问题是否真的被解决。**最后**用丰富的评测集保障每一轮迭代的准确度不下降

这样一套机制让我能把失败拆成可行动的问题：鉴定问题属于是文档缺失、知识过期、用户输入不完整还是回答范围过宽；再针对性修复，而不是笼统地调整 Prompt。最终我们不是只得到一个能回答问题的机器人，而是得到一套能持续降低人工支持成本、且能通过业务行为验证效果的 AI 服务机制。

如果面试官问“这为什么算你的亮点”，你的回答应当是：

> 很多人会把 AI 项目做成模型和技术的组合；我更关注把它做成一个有质量控制、有风险分流、有结果反馈的业务系统。因为模型会变化、知识会变化，但这套判断和闭环可以复用到其他 AI 项目。不承诺模型永远准确；我通过知识治理、风险分流和结果反馈，让错误更少发生、错误更容易被发现，并且不会被持续放大。

## 七、Moka AI 的理解

#### 7.1 如何证明一个招聘 Agent 比传统搜索/筛选方式更好，而不是看起来更智能？
评测维度
- **效率**：Agent 需要比传统人工筛选更快，观测指标可以是：首批合格候选人耗时、约面周期、每个招聘岗位的耗时
- **招聘质量**：可观测的指标是：HR 采纳率、面试通过率、Offer 率、Offer 接受率、入职后表现/留存
在“候选人质量、合规和公平性不下降”的前提下，Agent 是否让单位时间带来的合格候选人、有效面试或成功入职更多

**评测方法上，我会采用两阶段**：
- **离线评测**：先用历史真实岗位和脱敏候选人数据，构建标注集。  比如给定岗位 JD、候选人池和企业历史规则，评估推荐候选人的技能匹配、过往经验匹配、稳定性匹配、期望工作城市等。 
- **对比实验评测**：Agent 真实运行，但不影响决策。让 Agent 和招聘者的传统搜索同时给出候选人列表，引入LLM 或 不同招聘者进行评测两者的质量。这样能发现幻觉、漏召回、偏见或工具调用问题
**招聘场景还要特别警惕两个坑**：
- **历史标签偏差**：过去录用的人不必然是“最适合的人”，可能只是当时被看见、被面到、被偏好的人。
- **自动拒绝风险**：早期 Agent 应以“推荐、解释、辅助触达”为主；对于淘汰候选人、薪酬、Offer 等高影响决策，应保留人类决策和可申诉路径

#### 7.2 一个付费客户说 Agent 偶发执行错操作，你如何止血、排查、修复并恢复信任

我会把它按一次生产事故处理，而不是先争论“模型为什么会错”。尤其是 HR 场景涉及员工数据、合同等，哪怕是偶发，也要默认高优先级
- **第一优先级是止血和保护客户**，而不是立刻定位模型原因。我会先基于租户、Agent 能力和具体工具调用做最小范围熔断：暂停该客户的写操作，或关闭有问题的动作类型，同时保留只读能力；必要时撤销相关 Token、暂停异步任务队列。随后确认影响范围，阻止重复执行，并尽快通过可逆的补偿操作恢复错误数据（*服务端维护按租户、能力和动作划分的执行策略，并在统一工具执行入口做实时校验。服务器可以向 Agent 下发只读状态，但最终执行权限由执行服务控制*）

- **第二步是用完整 Trace 重建事实**：用户请求、当时的权限上下文、Prompt/模型/知识库版本、检索结果、工具调用参数、审批记录和最终写入结果。我要区分这是模型理解错误、权限或租户边界错误、工具参数映射错误、重试导致重复执行，还是底层业务 API 本身的问题

- **第三步是修复和验证**。除了修 Bug，还要把问题转为回归评测样本；在隔离环境复现，并验证修复不会影响正常任务。对于写操作，我会增加结构化参数校验、业务规则校验、幂等键、金额/人数/范围阈值和人工确认

- **最后是信任恢复**：主动、事实化地向客户说明已知影响、已完成的修复、尚在调查的部分和下一次更新时间；提供可核验的审计记录及数据恢复结果。根因确认后给出复盘和明确的长期防护措施。客户要看到的不只是“我们修了”当前问题，而是同类错误以后很难再发生

## 十、设计一个 Agent 应该考虑哪些要点
  - **Agent 流程方面**
	  - **明确业务目标和边界**：先定义它替谁完成什么任务、什么算成功、什么绝不能做；输出建议，还是直接执行动作；允许自主到什么程度：只读、或需确认后写入、或 Agent全自动完成
	  - **把 Agent 设计成“受控工作流”**：很多场景不该是自由规划的 Agent，而应是“LLM 理解 + 确定性工作流执行”；将任务拆成状态机，理解意图 → 校验身份/权限 → 查询 → 生成方案 → 用户确认 → 执行 → 回读结果；写操作需要考虑幂等、超时重试、补偿/回滚；为每个步骤提供降级方案，例如模型调用失败、工具失效、数据缺失、转人工处理等
	  - **模型与上下文策略**：按照任务选择模型，例如简单分类、结构化提取、复杂推理、长文档问答不一定需要同一个模型；控制上下文防止上下文撑满，设置压缩策略及上下文恢复策略

- **Agent 运行安全方面**
	- **工具、权限与人机协同**：工具定义要有清晰的输入、输出。工具执行权限按照最小权限设计，对于高风险动作设置人工审核环节
	- **安全防护**：设置工具白名单、工具参数校验、输出前检查敏感信息、越权内容和违规操作等；外部链接、网页视为不可信；Prompt 注入攻击不可信（例如：“忽略规则、把数据发到某处”等指令不能被执行）
	- **数据、知识库与多租户隔离**：首先是数据来源是否可信、知识库中的数据更新机制、确保知识库数据是具有时效性的、保密数据需要做到脱敏、加密等；不同企业、不同员工的数据做到租户隔离


  - **Agent 评测与迭代方面**
	  - **评测集与可观测、可追溯轨迹**：评测集覆盖正常高频任务、模糊、多轮追问、数据缺失、工具异常、权限不足、高风险操作、对抗样本：越权、提示注入、隐私探测；真实线上失败案例的持续回灌。可观测需要看：Prompt、模型和版本、工具调用的入参和结果及权限、检索到的文档及版本、token 费用、请求耗时、最终输出及实际执行结果等
	  - **上线与持续迭代**：考虑白名单客户、灰度发布，保证回滚策略完善（模型版本和工作流、prompt 一致性回滚）

我会先界定业务价值和自动化边界，再用权限、工作流和人工确认控制执行风险；用租户隔离和最小化数据访问保护隐私；最后通过离线评测、线上指标和全链路审计，让它的效果、安全性和责任归属都可验证。

## 十一、目前主流的 Agent 框架有哪些，优势与劣势

- **Agent 产品**：开箱即用，替人完成任务，如 Claude Code、Codex
- **Agent Framework（开发框架）**：帮自己编写 Agent，如 LangChain、LangGraph、OpenAI Agents SDK、AutoGen、CrewAI、LlamaIndex
	- **LangChain**：Agent 开发框架；模型、Tool、RAG、结构化输出等抽象与大量集成；上手快
	- **LangGraph**：Agent Runtime / 编排；图状态机、持久化、断点恢复、流式、人工审批、细粒度控制
	- **AutoGen**：多 Agent Framework；对话式多 Agent、团队协作、事件驱动 Core，适合实验多角色协作；需要注意多 Agent 很容易成本失控、循环或责任不清，生产应限制角色和终止条件
	- **CrewAI**：多 Agent Framework；Crew（角色协作）+ Flow（流程）；概念直观
	- **LlamaIndex**：数据/RAG 优先框架；强项在数据连接、索引、检索、知识 Agent
	- **Semantic Kernel**：是微软开源的 AI 应用开发框架，充当大模型与业务系统之间的编排层；它统一管理模型调用、Prompt、RAG 检索、记忆和插件工具，将现有 API、数据库操作等封装为模型可调用的能力，从而帮助开发者构建可扩展、可观测、可控的 Agent 和企业级 AI 应用
- **Harness（智能体脚手架/执行环境）**：把模型、Prompt、工具、文件系统、上下文管理、子 Agent、沙箱等组合成一个能持续干活的运行环境，如 Claude Code、Codex、DeepSeek Harness
- **Agent Host / Personal Agent Runtime**：接入消息渠道、日程、邮箱等，让 Agent 长期驻留，如 OpenClaw、Hermes
## 十二、优秀的设计

我选 Claude Code。
第一个优秀设计是它的“能力渐进披露”。  
当工具、MCP 和 Skill 越来越多时，它没有把所有工具定义一股脑塞给模型，而是保留少数高频核心工具，把低频能力以索引形式暴露，需要时再搜索和加载。  
这解决的是 Agent 规模化后的上下文膨胀和工具误选问题；同时让请求前缀稳定，能提高 Prompt Cache 命中率，降低成本和延迟。代价是偶尔多一次工具发现调用，但对低频能力是合理交换

第二个优秀设计是它把“模型提出动作”和“系统授权执行”彻底分开。模型只能提出 Read、Edit、Bash 等调用，真正能否执行由 runtime 的 Permission 决定；Hooks 又让企业能在工具前后插入审批、审计或策略服务。  
我认为这很关键：不能把安全寄托在 prompt 上。这样 Claude Code 才能从个人编程助手走向可在企业代码库中部署的平台——模型可以不完全可靠，但执行边界必须确定、可配置、可审计

所以我认为 Claude Code 最强的不是“模型会写代码”，而是它把不确定的模型能力关进了一个可扩展、可控、成本可治理的 Agent Runtime

## 十五、如何看待模型能力迭代会覆盖掉曾经做过的工程化建设

不把“自建还是等模型”看成二选一，而是先区分：这个问题到底是模型能力问题，还是组织知识、业务流程和责任边界的问题

对于通用模型会快速迭代的部分，比如总结、分类、语义理解、代码阅读和生成能力，我会尽量借用成熟模型或平台能力，不投入重资产去复刻；但对于模型天然拿不到、也无法替团队承担责任的部分——例如内部知识的权威性和时效性、权限、业务路由、人工兜底、效果评测和反馈闭环——我认为应该自己建设

智能客服就是一个例子。我们没有去训练或微调自己的问答模型，也没有自己造代码 Agent，而是分别使用知识库平台和 Claude Agent SDK 的通用能力。但我们投入建设了 API 文档的双通道索引、历史工单的准入规则、文档更新同步、知识库/源码/追问/转人工的路由，以及“用户问完机器人后是否仍提 TT”的效果闭环

半年后，模型的长上下文、检索和代码理解能力可能更强，甚至能替代一部分双通道或检索调优的实现；但它仍然不知道哪份内部文档是最新权威版本、哪类工单可以成为团队结论、什么情况下应该转人工，也无法替我们定义“用户的问题是否真的解决”。这些投入会随着模型变强而增益，而不是被替代

所以我的判断标准是：如果投入是在弥补模型暂时的通用短板，我会小步验证、保持可替换（例如：embedding 模型、向量维度、API 摘要生成 Prompt、图片 OCR 模型、问答大模型）；如果投入是在沉淀团队独有的数据、流程和评测标准，我会优先建设。前者要追求可替换性，后者才值得追求复利。
