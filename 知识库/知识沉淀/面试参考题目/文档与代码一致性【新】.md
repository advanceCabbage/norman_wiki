
## 一、两分钟项目介绍

Serena 是一套围绕 LSP构建的、**领域专精**的代码语义检索与编辑工具集，外加项目配置管理、记忆持久化、多种协议接入层（MCP/CLI/Dashboard）。它自己不具备"调用 LLM、跑对话循环"的能力。

Serena 的 Agent 能力由 Agno 框架补充，Agno 是跟 LangChain/AutoGPT 这类框架同类型的开源 Python 库，提供的是**跟具体业务领域无关的 Agent 基础设施**，包括：LLM 调用循环、对话历史持久化 (SQLite)及将 Agent 包装为一个 http 服务器等等

**LSP 是协议规范，语言服务器是遵守这份协议规范的服务端程序（每种语言一个），Serena 是这份协议的一个客户端实现（消费方）**。LSP 本身**不含任何代码解析逻辑**，它只是规定了消息长什么样、怎么编号、怎么应答


Serena 的核心是自己实现了一层 LSP 客户端框架，在这之上包了一套面向 Agent 的符号抽象工具，例如：find_implementations（查找符号的实现）、find_declaration（查看符号声明）等工具，将 IDE 级别的符号分析能力赋予 LLM，进而实现高效符号索引。


## 二、记忆存储机制

**存储分类**：
- 全局记忆：`global/` 前缀的记忆存在用户级目录下
- 项目级记忆：`<project>/.serena/memories/*.md`

**存储原理**：
- 每条记忆是一个 `.md` 文件，可以用 `/` 分层组织成主题/文件夹（如 `frontend/debugging`）
- 记忆之间可以用 `` `mem:xxx` `` 语法互相引用，形成一张"渐进式发现"的知识图谱——agent 先看 `core.md`（图的根节点），再按引用逐步深入到具体主题
- 支持 read-only 记忆（工具上下文中不可写）、ignored 记忆（完全从列表/读写中排除）等访问控制

## 三、Continue 的实现
[[基于API文档与代码一致性智能检测工具]]
**创建索引阶段**
- **分块索引**
	- 基于 tree-sitter 进行语法层面分块，定位函数、类等语法结构；超出 token限制的块则折叠，然后对子块进行递归切块
	- 不支持 tree-sitter 的则按照固定长度切块
- **分段索引**：将函数、类的定义+功能描述+名称提取出来，作为待检索的向量，同时完整函数、类均原文存储
- **全文索引**：利用SQLite 内置的 FTS-5 引擎 ，采用trigram 三元分词、BM25 对检索结果排序
- **向量索引**：对分块和分段的内容创建向量索引
- **Repo Map 构建**：记录每个文件路径， 并抽取文件功能实现定义

**检索阶段**
- 向量检索
- 关键词检索
- Repo Map 检索
- 检索结果是否重排可由用户配置
	- 无重排：直接召回  N 段（最多支持 25 段）；**固定权重拼接**：最近编辑文件占 25%  + 全文检索占 25%  + 向量检索占 50% +  Repo Map：额外加入，不计入上述配额（文件路径清单交给 LLM，选择 5–10 个文件）
		- 各自独立召回后直接拼一起，仅按顺序拼接无打分机制，去重（按 `filepath + startLine + endLine` 去重）
	- 有重排
		- 每个通道先分别召回 `nRetrieve` 个候选，合并去重
		-  然后调用配置的 rerank 模型排序，例如：传入用户query和检索结果给重排序模型进行排序 Voyage rerank-2.5(**continue仅支持重排模型排序**) [[混合检索结果融合与排序方法]]

## 四、LSP 的定义及语言服务器的定义
LSP 是微软 2016 年为 VSCode 定义的一套基于 JSON-RPC 的**标准消息格式**，，规定了编辑器和"代码智能提供者"之间应该怎么对话，比如：
- `textDocument/documentSymbol`：查看符号树
- `textDocument/definition`：查看跳转定义
- `textDocument/references`：查看查引用
LSP 本身**不含任何代码解析逻辑**，它只是规定了消息长什么样、怎么编号、怎么应答。这解决的是经典的 **M×N 问题**：在 LSP 之前，每个编辑器（VSCode/Vim/Emacs…）要支持每种语言（Python/Java/C++…）都得单独写一个插件，M 个编辑器 × N 种语言 = M×N 份集成代码；有了 LSP 之后，每个编辑器只需实现一次 LSP 客户端，每种语言只需实现一次 LSP 服务端，变成 M+N

例如：Python 的 `pyright`、C/C++ 的 `clangd`，他们启动后是独立的进程。它们各自内嵌了该语言的解析器/类型检查器，把分析结果按 LSP 规定的消息格式吐出来。**它们互相之间毫无关联**，pyright 不知道 clangd 的存在，也不知道自己被谁调用（VSCode？Neovim？还是 Serena）——只要调用方按 LSP 规范发消息，它就能响应

## 五、详细介绍 Serena
 
 Serena 自己实现的一套 **LSP 客户端框架**（`ls.py` 里的 `SolidLanguageServer` 类），职责和 VSCode 内置的 LSP 客户端是**同一层面的东西**——负责启动语言服务器子进程、维护 JSON-RPC 通道、发请求收响应、管理文档同步状态。区别只是 VSCode 把结果渲染成 UI（跳转、悬浮提示），Serena 把结果转成给 LLM 用的工具返回值（JSON 字符串）

- **语义代码检索与编辑（核心卖点）**
	- Serena 把 LLM 对代码的操作从'文本层面的 grep/read'升级成'符号层面的语义检索与编辑'，核心是自己实现了一层 LSP 客户端框架，在这之上包了一套面向 Agent 的符号抽象
	- **核心数据模型**：`Symbol` 抽象 + `name_path` 寻址；模型不需要知道符号在文件里的精确坐标，只要给一个"大概的名字层级"，剩下交给匹配器
	- **检索链路：分层递进，尽量少读全文件**：`get_symbols_overview`（只看文件顶层符号骨架）→ 只精确读要用的那一个符号 → `find_referencing_symbols`（查引用关系）；**关键效率设计——两层磁盘缓存**：一层缓存 LSP 原始响应，一层缓存转换后的结构化符号树，都按**文件内容哈希**做失效判断，并且是持久化到磁盘的。这意味着同一份代码只要没改过，哪怕进程重启、语言服务器重启，也不需要重新问一次 LSP。这是"token 效率"和"响应速度"两个维度的双重优化，模型不用读整份源码，Serena 也不用每次都重新解析
	-  LSP 不给源码文本，Serena 自己切片、 编辑链路：只用 LSP 定位，编辑动作 Serena 自己做

**与传统检索方式的对比**

|       | 传统 grep/red    | Serena 的语义方式                       |
| ----- | -------------- | ---------------------------------- |
| 定位    | 字符串/正则匹配，容易误伤  | LSP 语义索引，精确到符号级别                   |
| 读取成本  | 经常要整文件读入上下文    | 先概览骨架，再按需精确读取单个符号                  |
| 重复检索  | 每次都要重新扫描       | 内容哈希 + 磁盘持久化缓存，命中率高                |
| 编辑安全性 | 手工处理格式/空行，容易出错 | 结构感知的插入逻辑自动处理                      |
| 重命名   | 全局替换不安全        | 走真正的 LSP 重构协议，跨文件正确                |
| 多后端适配 | 无              | `Symbol` 抽象统一 LSP / JetBrains 两套实现 |

**为什么 Serena 可以精确找到对应的代码**
- **语义级别的代码理解**：传统文本搜索只能匹配字符串，LSP 可实现符号级别查找。```symbol_manager.find_by_name("ClassName.method_name")  # 精确定位到类的方法```
- **跨文件依赖分析**：LSP 构建完整的项目依赖图，理解模块间的引用关系。LSP 可调用 find_referencing_symbols 方法知道，哪些函数调用了目标函数、哪些类继承了目标类等
- **类型感知智能操作**：LSP 可提供类型信息，Agent 通过获取函数的签名信息能知道入参、出参的类型
- **多语言统一接口**：LSP 为不同编程语言提供统一的接口，使 Agent 能跨语言工作

## 六、适配多端差异的提示词
Prompt 拼接是在项目工程中实现的，拼接的时机时并发执行检索之前。动态拼接部分包括：
- 你是一个经验丰富的{platform}开发工程师
- 使用 active_the_project 激活{projectName}项目，为{projectName}项目的{API}生成一份详尽的报告

- 定义输出格式，要求以 MD 格式输出。并且给出 fewshot 参考
	- **三端特定差异部分提示词**：
		- iOS 端：参数类型为 NSNumber 时统一输出为 number 等、参数必填性重点看 NSAssert 等断言的使用、在属性声明中查看默认值等
		- Android 端：参数必填性重点看@MISIParamChecker、@NonNull 等、默认值可查看构造函数默认值设置、参数类型为 Integer 统一输出为 number
		- Harmony OS 端：使用 interface 定义查看参数的类型

## 七、实现了哪些效率优化

- **并行实现**，原本 Serena 仅有一个 agent 实例，agent 实例负责激活目标项目、执行工具调用等流程。android、iOS、harmony 属于不同项目，不能使用同一个 agent 进行代码分析。通过支持创建多个 Agent 实例的方式，实现 android、iOS、harmony 均各自独享一个 agent，agent 之间相互独立互不影响，使得三端的代码检测可以并发执行
- **Serena agent 的记忆机制**
	- 以 session 为维度的记忆机制，相同 session 会共享记忆文件，记忆内容包括：会话记录、每次 agent 的运行记录、会话摘要、用户长期记忆
	- 以项目为维度的记忆机制，相同的项目可以共享，存储在.serena/memory 目录下，和项目相关的记忆文件
	- **cache 文件夹**：用于存储与 LSP 交互的缓存信息
- **预初始化项目缓存**
	- **project.yml 文件**（纯配置序列化与 LSP 无关）：包括，projectName、language、read_only、ignored_paths、excluded_tools、initial_prompt 等
	- **memories 文件夹**：包括，代码风格约定、注解使用；项目描述、项目文件结构、技术栈；项目涉及的命令，构建命令等
- **多人同时触发代码检索任务时**，通过锁机制，排队执行。否则同一个 agent 可能出现串激活项目、工具执行等问题，一个 API 从分析到 diff 对比完成大约耗时 5 分钟

## 八、项目的难点或亮点

我认为这个项目最大的难点，不是让 Agent 去读代码，而是定义并实现“跨端 API 一致性”的判定。

MSI 有 400+ 基础 API，覆盖 iOS、Android、Harmony 等多端，并服务多个业务线。过去文档出错后只能靠工单或群聊被动修复，人工无法持续核对全量 API。真正困难的是，同一个 API 在不同端的源码表达差异很大：比如必填性可能体现在 iOS 的断言、Android 的注解或参数校验逻辑中；默认值、返回字段和错误码也分散在接口、实现类、参数对象和调用链的不同位置。所以不是简单搜索到 API 名称就能完成判断，而是要判断不同端的实现，在文档语义上是否等价，并筛出真正需要修复的文档问题。

为解决这个问题，我没有把它当成普通的 RAG 检索任务。这个场景需要确认的是参数默认值、必填性、类型和错误码等代码事实，核心是找到权威定义，而不是召回一批语义相关的代码片段。因此我调研了 Cursor、Continue、Cline 和 Serena 的 CodeBase 实现方案，最终选择基于 LSP 的 Serena。它可以通过定义跳转、引用查找和类型信息，让模型以符号级方式分析代码。

在实现上，我将整个能力拆成两层：Doc Agent Server 负责根据 API 名定位仓库、分别组织三端分析任务、汇总结果、比对线上文档并生成草稿；CodeBase Server 则专注封装通用的 LSP 代码分析能力。针对三端的差异，我补充了对应的分析规则，把各端结果统一成文档需要的字段，例如参数类型、是否必填、默认值、输出字段和错误码，再进行一致性检测。

另一个亮点是把一次性的人工专项，做成了可持续执行的系统能力。三端仓库通过多 Agent 实例并行分析，避免项目上下文串扰；同时预初始化项目配置和记忆信息，并复用 LSP 缓存降低重复分析成本。由于 Agent 能读取核心代码仓，我还将代码仓权限限制为只读，并移除了编辑类工具，保证它只做分析、不具备修改代码的能力。

最终，项目完成了 432 个存量基础 API 的首次全量三端核对，识别出 1000+ 文档问题；文档草稿的检测准确率达到 98%+。我认为这个项目最大的价值，是把原本依赖人工经验、只能事后处理的问题，转化为可批量运行、可复核、可持续优化的文档质量保障能力。

##### 9.1 各个端对应的语言服务器
- java 使用的是：Eclipse JDT Language Server
- OC 使用的是：通过 Serena 接入 clangd，复用 Clang 对 Objective-C 的语法和静态语义分析能力
- 鸿蒙端 ArkTS 使用的是：TypeScript Language Server，复用 TypeScript 的语言分析能力，辅助检索鸿蒙端的 API 实现代码
##### 9.2 TS 语言服务器为什么能解析 ArkTS 
`.ets` 接入 TS 语言服务需要分两步：
- 首先在 Serena 侧把 `.ets` 纳入 TypeScript 文件识别范围；
- 其次打开文档时设置 `languageId: "typescript"`
TypeScript Language Server 会将其标记为 TS 类型，然后让 tsserver 按 TypeScript 语法分析内容。
ArkTS 在 TypeScript 生态基础上发展，保留了许多基础语法，同时增加了约束与扩展，因此语法相同，解析器就能识别。对于 ArkTS 扩展部分无法保证 TS Language Serve 支持。

## 十、扩展类
##### 10.1 为什么不使用 grep、向量检索或直接把文件交给模型
**grep**: 查询方式是字符串或正则；典型的返回内容是匹配行和路径；优势是无需持久化索引，查询速度快，支持精确匹配检索；劣势是无法解释文本与程序实体的关系，不利于控制搜索范围和输出控制

**向量检索**：查询依据是提前构建的向量索引；典型的返回内容是排序后的代码候选；优势是根据自然语言寻找功能，用户缺少精确标识符时极为有效；劣势是：检索前需要构建索引，维护向量的时效性，切块方式会影响检索质量，相似度最高的片段不等于回答所需证据最充分，向量搜索存在两层误差，目标代码在 embedding 空间里没有排得足够靠前，为了检索速度，大型索引可能采用近似最近邻算法，导致没有返回真正最近的向量

**LSP**：查询方式是符号、作用域和类型关系等；典型的返回内容是符号、位置、引用等；优势是提供符号级精确查找；劣势是需要配置对应语言服务器，静态类型不等于运行时对象，跨语言和动态连接可能不在符号图里，为了检索速度，基于文件哈希值保存 LSP 检索结果缓存
##### 10.2 JSON-RPC 的请求与通知
LSP 使用 JSON-RPC 2.0 表达消息。请求携带 id，接收方返回带相同 id 的结果或错误，因此可以匹配并发调用的响应；通知不带 id，也没有对应响应。比如查询定义需要结果，所以是请求；文件变更用于同步文档状态，所以是通知。在我的项目中，还需要区分查询无结果与语言服务器调用失败，避免把检索失败误判为文档问题
##### 10.3 解决运行时代码读取
采用 DAP（Debugger Adapter Protocol）调试适配器协议，核心思想是通过统一协议连接调试客户端与不同调试器，让客户端以一致的方式控制程序执行、读取运行时状态

**Agent 接入 DAP 的核心实现步骤**
- **封装工具**：向 Agent 提供启动调试、设置断点、读取变量、单步执行和结束调试等接口。
- **启动适配器**：以 Python 为例，工具服务通过子进程执行 `python -m debugpy.adapter`，通过 stdin/stdout 通信，再发送 `launch` 启动目标脚本。
- **确定观测位置**：Agent 根据问题和源码选择断点，工具服务配置断点并运行复现用例。
- **获取运行时上下文**：命中断点后，将调用栈、对象类型和字段值返回 Agent，支持按需展开。
- **迭代分析**：Agent 根据现场决定继续执行、单步跟踪或调整断点，结合源码验证假设。
- **输出与清理**：Agent 给出附带运行条件和观测证据的结论，工具服务结束会话并释放资源

## 十一、coding agent 相关
##### 11.1 如何给 Coding Agent 找上下文？
我会把上下文获取设计成一个随任务推进的过程。

首先，从用户需求、明确引用的文件、当前编辑位置、错误信息和项目约定中提取初始线索，确定要解决什么问题、从哪里开始查。

然后根据线索选择检索方式：已知文件名、符号名或错误字符串时，优先用文件和文本搜索；只有自然语言功能描述时，可以用语义检索找到候选模块；定位符号以后，通过 LSP 查询定义、引用和实现，再读取源码，补齐类型、调用方、配置和测试等必要信息。

每轮读取后，Agent 根据尚未解决的信息缺口决定下一步查询。进入模型的内容要去重、控制大小，并保留路径、位置和版本；关键实现保留原文，大段日志和历史按需读取。

编辑器里还要处理未保存文件和索引过期，保证读取和修改依据的是正确版本。修改之后，把诊断和测试结果作为新的上下文，继续迭代。

最后，我会用关键证据覆盖率、任务成功率、耗时和 token 成本来验证这套策略，而不只看搜索结果是否相似。
##### 11.2 Agent 改完代码后，如何判断任务完成？
核心是把用户需求转换成可验证的验收条件，再根据执行证据判断是否完成。需要区分两个状态，模型自己决定停止执行还是任务已经满足验收要求后的任务停止状态

我会先把需求拆成验收项，明确预期行为和必须保持的约束。

修改后按影响范围执行静态检查、针对性测试和必要的集成验证，再审查最终 diff。完成判断必须依赖真实工具结果，而且证据要对应最终代码版本。

 编排层检查必要验收项是否满足；验证失败则继续修复，环境阻塞或预算耗尽则如实报告未完成部分。模型输出“完成”只是一个结论，背后必须有对应的验证证据
##### 11.3 用户正在编辑文件，Agent 同时读写，怎么办？
用户正在编辑时，同一个文件可能有三个状态：Git 中提交的版本、磁盘上的文件内容、编辑器里尚未保存的内容；

编辑器里的交互任务，Agent 读取的是编辑器里尚未保存的内容，并记录文件版本、内容快照、文档 URI。整体思路是：Agent 推理期间，允许用户继续编辑；真正应用修改时，检查依据的版本是否仍然有效。

文件会跟随用户的输入、撤销等操作不断的创建累加的版本 ID（字符级的变更创建不同版本）。在 Agent 准备编辑前，通过携带预期的 versionId 与当前待修改的文件 versionId 进行比较。versionId 一致时可正常修改文件；versionId 不一致时依据不同策略决定：
- 第一种：只是位置移动，例如用户在文件开头增加了几行，目标函数没有变化。可以重新定位然后按照预定流程修改代码
- 第二种：修改区域不同，例如用户修改日志，Agent 修改参数处理。可以尝试合并或编辑范围重映射
- 第三种：修改重叠或者原本的判断依据变化了，例如用户和 agent 都修改同一个默认值。应该保留当前内容，让 agent 根据新内容重新计算；意图存在歧义时，再通过差异界面交给用户决定

对于长任务可以采用 worktree 隔离，考虑创建 worktree 时明确基线，隔离期间不覆盖用户修改，合并时仍可能与用户修改存在冲突
