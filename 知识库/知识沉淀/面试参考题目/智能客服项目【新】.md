### 一、 两分钟项目介绍

我所在团队负责为整个美团体系的业务线提供 Android、iOS、Harmony、H5 等多端 基础API 能力，例如获取系统信息、定位等与业务无关的基础能力API。因为用户是研发，日常咨询集中在参数默认值、端能力差异、接入异常和实现行为上；值班同学每天大约需要投入 0.8 PD，而且同类问题会被反复询问

这个项目的目标是建设团队智能客服，降低重复工单和人工答疑成本。但我认为它的难点不在于搭一个 RAG，而在于研发场景里“错一个字段就会失去信任”：API 文档、接入指南、历史工单和源码的可靠性、完整性和时效性都不一样，不能用同一种方式处理。

因此我做的核心设计是按知识类型治理，而不是把所有内容统一切片入库。对于 API 文档，我采用双通道索引：用功能和场景摘要做召回，但命中后返回完整原文，避免入参表、返回字段和多端差异被切散后产生半对半错的答案；接入指南按结构切分；历史工单先由模型总结和判断复用价值，再由人工兜底，避免无结论、错误或过期工单污染知识库

对于普通文档可回答的问题，系统通过混合检索和 RRF 获得上下文；当用户主动要求 deepsearch、且提供了 API 名称和端信息时，再进入只读源码检索。信息不足时不强答，而是追问；没有可靠依据或超出边界时转人工

我尤其关注上线后的真实效果，而不只看模型回答是否通顺。我们把“用户咨询机器人后是否仍提人工 TT”作为核心行为信号，结合点踩和会话复盘，将失败归因到文档缺失、知识过期、输入不完整、检索不准、回答过宽或路由错误，再分别修复。

最终，周工单从 50+ 降到约 20，下降约六成；值班投入从约 0.8 PD 降至约 0.4 PD。这个项目让我形成的经验是：**AI 项目不能把准确率当作模型能力，而要把它做成由知识质量、路由边界和业务反馈共同保证的系统属性**

## 二、智能客服的底层框架是什么
底层 Agent 框架、编排流程是由公司内统一基建团队搭建，采用的是工作流编排形式。业务方团队可结合业务属性灵活编排流程、构建知识库及检索策略。在我们团队智能客服流程编排上采用了如下的流程设计：
- **首先**依据用户输入关键字判断走代码检索分支 还是知识库检索分支
- **然后**代码检索分支先小模型 agent判断用户传入的信息是否足够，即是否传入 API 名称和对应端，假设必须信息不足则礼貌要求用户补充，充足则从用户 query 中提取 API 名称和对应端
	- **接下来** API 名称、端（例如：iOS）及用户问题传入 「http 请求节点」
	- 「http 请求节点」内调用服务端接口，触发 Claude SDK 进行代码级的任务分析
	- 将返回的检索任务再返回给用户
- **其次**走知识库检索分支
	- **首先**调用知识库节点进行混合检索，分别获取向量检索+关键词检索各 20 个片段
	- **接下来**采用并集去重 + RRF（倒数排序融合）获得前 20 个片段
	- **最后** Agent 基于 20 个文档片段进行问题回复
## 三、 如何实现文档更新与并集去重
#### 3.1 并集去重原理

- **切块的场景**：混合检索检索到内容片段后通过 chunkIndex 进行区分。使用分段和语义切割的内容均按照**混合检索策略**存储，因此他们相同切块的 chunkIndex 是一致的，这样可以去重
- **FAQ 的场景**：具备 faq_id 字段作为唯一标识

#### 3.2 向量数据如何更新
- **第一学城类文档且是自动更新机制**：按照学城文档的链接作为 document_id，每天定时 12 点定时获取已入库的学城文档是否定时更新，存在更新时会按照当前文档既定策略（按段落、按语义）重新 embedding，实现自动更新并删除历史的向量数据库中旧文档
- **第二类 FAQ 内容格式的更新**：
	- 首先，我们会对每个API 文档调用大模型进行摘要总结
	- 然后，调用知识库提供的 API 进行向量化存储，其中摘要会被向量化，API 原文会全量存储，并传入业务线+API 名称作为唯一标识
	- 后续，后台系统监听到 API 文档变化时，会触发定时任务，对 API 文档再次进行摘要总结并且调用知识库接口进行覆盖式更新

## 四、项目基础

#### 4.1 基础模型与相似度选择
Embedding 模式：BGE-m3
向量数据库：Mlivus
- 余弦相似度：适用于文本语义检索 ✅
- 欧几里得距离：图像特征、人脸/商品特征
- 点积相似度：用户-物品推荐

#### 4.2 知识库包含的文档类型
- **API 文档**：总结摘要 + 全文存储
- **段落**：接入文档按段落标题切分，同时使用父子段落方式存储
- **图片**采用两种模式
	- 一是 OCR 能力 提取图片中的文字
	- 二是使用多模态模型总结图像描述
	- 将文字 + 图像描述作为向量化的内容，metadata 中同时传入图片的地址
- **表格**：我们的场景比较少


## 五、用户问题不清晰

针对用户问题不清晰场景：
- **多查询**：使用 LLM 从用户输入的查询生成多个不同的查询视角，然后为每个查询检索一组相关文档，合并这些结果以获得更全面的文档集合
- **分解**：使用 LLM 将用户的问题分解为一系列子问题，这些问题可以依次解决也可并行解决
- **后退**：使用 LLM 将复杂问题分解为更高层次的问题，主要包含抽象和推理，抽象是指：不直接针对问题进行回答，而是首先促使 LLM 提出一个更高级别的「回溯问题」。推理是指：在高级概念或原则的基础上，利用语言模型的内在推理能力，对原始问题进行推理解答，这种方法被称为基于抽象的推理。举个例子：输入：警察可以合法逮捕吗？ 输出：警察可以做什么？
- **假设文档嵌入**：基于 query 生成一个假设性文档或回答，接着对假设性回答进行向量化，以假设性文档作为 context 去向量库中搜索相似的回答

## 六、文档清洗
首选回答有哪些类别文档：API 文档、API 使用指南、MSI 介绍文档、容器接入指南、历史工单
-  **API 文档**：AI 摘要清洗（双通道 Q&A 架构），生成摘要作为 Q，原文作为 A。生成摘要时仅取"功能描述、注意事项、基础信息、入参、出参、错误码"，主动剔除"示例代码、Native 基础库、依赖组件"等与检索语义无关的信息，避免噪声进入向量化内容。固定模板要求摘要 ≤150 字符，必须包含功能描述、使用场景、关键说明、支持容器
- **历史工单**：使用 LLM 进行内容总结：分为**四个模块内容，问题、现象描述、分析过程、处理方案**，字符数限制在 500 以内。涉及图片使用多模态模型（LongCat-VL 模型）进行内容提取，通常为代码片段截图。测试阶段由值班同学确认总结内容完整性、正确性，测试数据通过后再批量总结历史工单并入库
- **文章时效性**：针对一年未更新的文档，交由人工确认是否入库
- **全局自动更新机制**：当天有更新的 API → 大模型重新生成摘要 → 更新 MD 文档 → 转换为 Excel（Q&A 格式）→ 调用知识库平台更新接口全量替换
- **其余可做的事项**：校验不同文档内容重复性部分。但 MSI 未发现重复文档

## 七、权限管控
  录入知识库会确认 C4 等级的文档不能录入知识库，其余均可录入知识库，无权限管控
- 知识库分两类权限
	- 第一是对当前知识库的可见性、可操作性。通过配置管理员和用户级权限，控制使用者具备知识库的可见性与可管理性
	- 第二是文档相对于知识库的权限控制，具备文档管理权限的用户才能将文档录入到知识库
- 使用知识库的权限
	- agent 中使用知识库需要当前创建者即是 Agent的管理者，同时是知识库的管理者
	- 用户在使用 agent 时，内部员工均可使用，外部员工需要申请权限后才能使用 agent

## 八、智能客服遇到的问题分类
- **客服回复与人工回复一致，用户对智能客服的回复不信任**，因此再次发起工单进行确认（问题举例: 用户提问：RegisterExtendAPI 是否支持鸿蒙。智能客服回复：官方不建议使用、有卡控机制、即将下线。用户不信任因此再次询问人工）
- **文档内容不完善**。（问题举例：外卖 APP 没有在文档上标记某个桥的实现情况）
- **用户在智能客服中提问的问题不够完善，用户没有耐心去补充完善问题
- ***客服回复的问题排查方向太宽泛**（问题举例：用户问 uploadFile 上传视频成功但 URL 不可访问。智能客服回复：1. 确认状态码是否为 200，如果为 404 则表示实际上传失败 2. 检查视频文件数据是否完整 3. S3 配置问题，S 3 bucket 权限配置问题。最终实际问题为 S 3 bucket 权限配置问题）

## 九、监控智能客服手段
  **检测手段**
- 客服回复的答案具备点赞和点踩，重点关注点踩内容（客服上线前期每周约有 4~5 个点踩）
- 统计客服拦截率，针对业务既咨询智能客服也咨询人工的问题，进一步分析
- 查看所有客服问答记录，找出回复不准确、不完善的问题近一步分析
- 发放调查问卷，邀请业务方提出建议和问题

**评估手段**
- 创建数据集，将历史用户问题及问答问题录入数据集。每轮版本修改时测试质量
- 将增量问题选择性的录入数据集

## 十、Claude SDK 检索源码

基于 Claude Agent SDK 作为 agent 底座，提供 Node 服务的 Http 接口。用户传入 API 名称和对应的端，由 Node 服务脚本判断所属 git 仓库。假设当前服务器中无该代码仓则拉取，否则复用已有代码仓。代码仓伴随双周迭代更新，通过定时任务每天半夜 12 点拉取一次已有代码仓最新分支代码，保证代码是更新后的。代码获取成功后，调用 Claude Agent SDK，设置为只读模式，并指定代码仓和用户问题，当 SDK 检索完成后，通过 HTTP 请求将答案回传给客户端，请求结束后关闭，不记录用户状态，不做 resume。

**Claude SDK 具体使用**
- 通过 cwd 确定检索的的代码仓目录
- query 传入用户的问题
- canUseTool、allowedTools、disallowedTools 等参数确定工具的调用权限
- abortController、maxTurns、permissionMode 分别控制取消调用、最大调用 LLM 轮次、权限（不使用bypassPermissions，使用 default）
## 十一、个人真实案例

- **背景与业务目标**：MSI 是公司级 API 基础能力，用户量大，客服群 1000+ 人，值班同学每天约花 0.8 PD 处理工单。问题中有较大比例是重复咨询、文档可解答的问题，或者只是用户没有提供完整上下文导致需要反复追问。我的目标是通过 AI 客服解决高频问题，减少人工工单，并把用户问题沉淀成可复用知识
- **约束/难点** ：难点在于技术问题答案必须准确、完整、具备时效性。知识来源既有 API 文档、接入指南、历史 TT，也有源代码；其中代码不能被切碎，历史工单也不能不加筛选地入库；同时需要引导用户优先使用智能客服，随时关注用户体验，积极寻求用户反馈
- **我的技术判断与取舍**：我没有采用“所有内容直接切块向量化”的方案
	- API 文档采用“双通道”：文档摘要负责召回，完整文档和代码示例负责回答，保证代码不丢失。
	- 历史 TT 先由模型总结和筛选，再人工抽检后入库，避免低质量内容污染知识库。
	- 对需要理解实际实现的问题，RAG 和代码检索并行；代码检索只在必要时触发，平衡效果、成本和耗时
- **如何推动跨团队落地**：我和值班运维同学一起定义机器人能答、该追问、该转人工的边界（文档内容缺失、智能客服判断无可用知识时转人工）；和文档、研发同学一起补齐高频缺失知识，并建立文档自动同步知识库的机制。之后通过“用户问完机器人仍提 TT”的数据，持续定位是文档、检索、回答还是能力边界的问题。
- **量化结果**：工单从每周约 50 个下降到约 22 个，减少约 56%，人工客服工作量下降约 50%。智能客服咨询后不再提 TT 的比例约 73%；周活跃用户达到 60+
- **复盘：如果重来会怎样做**：我会更早建设完善离线评测集，而不是主要依赖上线后的二次提 TT 发现问题。评测不只看回答是否像样，而看是否真正解决问题、是否该追问、是否应该转人工，以及代码检索带来的实际增益。
	- 一句话收尾：这个项目让我意识到，AI 客服的关键不是“能不能回答”，而是能否在正确的边界内，稳定解决问题，并通过数据持续迭代。
## 十二、项目难点或亮点

我认为项目最大的难点，是如何让一个概率型的大模型在研发支持场景中变得可信、可控、可量化。研发咨询和普通客服不同，用户问的是 API 参数、端能力差异和实现行为，错一个字段就可能导致线上问题；但又不能为了避免答错，把所有问题都转人工。

所以我没有把目标定义成“搭一个 RAG”，而是把它拆成一套可信度闭环：**首先**治理知识质量及时效性，不同知识源采用不同的入库和返回策略，打通 API 文档与知识库同步更新机制；**其次**设计回答边界，信息不足就追问，需要实现细节时再进入源码检索，无可靠依据时不强答；**然后**用用户咨询机器人后是否仍提工单，结合点踩和会话复盘，衡量问题是否真的被解决。**最后**用丰富的评测集保障每一轮迭代的准确度不下降

这套机制让我能把失败拆成可行动的问题：是文档缺失、知识过期、用户输入不完整、检索不准，还是回答范围过宽；再针对性修复，而不是笼统地调整 Prompt。最终我们不是只得到一个能回答问题的机器人，而是得到一套能持续降低人工支持成本、且能通过业务行为验证效果的 AI 服务机制。

如果面试官问“这为什么算你的亮点”，你的回答应当是：

> 很多人会把 AI 项目做成模型和技术的组合；我更关注把它做成一个有质量控制、有风险分流、有结果反馈的业务系统。因为模型会变化、知识会变化，但这套判断和闭环可以复用到其他 AI 项目。我不承诺模型永远准确；我通过知识治理、风险分流和结果反馈，让错误更少发生、错误更容易被发现，并且不会被持续放大。

## 十三、评测集的分类

我把评测对象从“模型回答对不对”，详细拆分为“知识是否可靠、系统是否选对路径、回答是否可执行、用户是否最终解决问题”四层。因为研发支持场景里，正确回答只是必要条件，正确分流和真实解决才是最终目标。

评测集包含几个类别的数据集：
- **知识缺失评测集**：已知文档未记录的实现情况，如鸿蒙端定位 API 不支持获取楼层信息；期望无特定信息时智能客服应转人工/说明暂无相关资料
- **用户输入不完整评测集**：用户只描述现象，缺 API 名、端、环境等信息；期望智能客服不是直接回答，能准确追问真正缺失的信息
- **检索召回准确性评测集**：基于标准 API 文档提问、基于历史真实问题提问；期望正确资料进入 Top-20，智能客服能准确回答该类问题
- **回答收敛性评测集**：有明确根因的历史工单，如 uploadFile 上传成功但 URL 不可访问，最终原因时 S3 桶权限问题；期望智能客服优先给出最可能原因和验证步骤
- **检索分支路由评测集**：基于有无 deepSearch 关键字，及 API 名称与端；期望有 deepSearch 关键字则走代码检索，并且提取 API 名称与对应的端，否则正常走知识库检索
- **真实用户问题评测集**：增量添加真实用户使用智能客服未解决的问题，添加到评测集中
