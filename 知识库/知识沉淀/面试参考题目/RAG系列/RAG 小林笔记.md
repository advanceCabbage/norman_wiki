## 一、向量化时分块的长度限制 & 最佳的切割长度
首先切块的算法不会限制字符串的长度，例如 langchain 的 `textsplitters` 对待切割和已经切割的字符串没有长度限制。但进行向量化的 embedding 模型具备上下文窗口限制，例如：
- OpenAI `text-embedding-3-small` / `large`，单条限制为**8192 tokens**
- 智谱 `embedding-3`，单条限制为**3,072 tokens**
因此分块向量化的理论长度限制是由 embedding 模型决定的。根据不同的分词训练策略，计算 token 的规则也不相同， 1000 汉字大约对应 1000-1500 tokens，1000 个英文单词大约 1300 token（标点符号也会参与分词，生僻字可能被拆分为多个 token）
- **上下文窗口管理**
```
chunkSize: 500  // 字符，不是 token
```

## 二、向量切割的最佳长度定义

业界并没有对于向量切片长度的最佳定义或者说需要针对不同的场景具体制定切割长度的定义。通常来说不建议将向量切块的长度大于 1000 字符。一些通用的规则定义：

- **问题是精确事实定位**：小块更好，**常落在 `200–500 字符`，80 overlap ** 或 `64–300 tokens`。
- **问题需要解释流程、条件和上下文**：中块更好，**常落在 `500–1,000 字符`，120 overlap** 或 `512–800 tokens`
- chunk 越大，向量主题更容易被稀释；chunk 越小，召回到的内容又容易缺上下文。
- 结构优先于长度：Markdown 应先按标题/段落，再对超长段落递归切分。你目前的实现正是这个方向

**短问答类**（FAQ、单条规章制度）：chunk size 300-500 字符，overlap 50 字符  
**技术文档、教程**：chunk size 800-1200 字符，overlap 100-150 字符  
**合同、法律文书**：chunk size 1500-2000 字符，overlap 200-300 字符


## 三、RAG 解决的问题
- **第一是知识时效性**：LLM 训练完知识就固定了，训练截止日期之后发生到的事它一无所知
- **第二是私有知识覆盖**：公司内部文档、行业专有数据不会进入训练集，LLM 不知道内部资料
- **第三是幻觉问题**：没有知识依据时 LLM 容易「自己发挥」，编一个听起来合理但实际错误的答案

## 四、向量文本切割的几个类别

##### 4.1 重叠切割
**定义**：让相邻 chunk 之间有一段内容重叠，通常设为 10%～20%。过小导致覆盖覆盖面过小，太大导致重复内容太多，存储和检索成本上升

**优势**：实现简单
**劣势**：语义连贯的句子可能会被切断

##### 4.2 按语义边界切割
**定义**：按照中文或英文断句，然后将附近+1 的句子（即三个句子）集合在一起，然后 embedding，最后计算每个句子之间的相似性，距离在前 5%的句子分割开，其余句子自然组合，超过 maxChunk 的再按照「重叠切割」

**优势**：语义保留完整
**劣势**：需要调用 embedding 模型

**其他判断是否应该语义切割**
**gradient**：对距离的**变化率(梯度)再取百分位；适合**句子都很像**的场景(如法律/医疗,绝对距离都偏高、拉不开差距),看"相对突变"而非绝对值

**其余语义切割的方式**
- **相邻距离断点**：相邻句语义突变处切
- **带 buffer 的变体**：断句后先和邻居拼再 embedding（**langchian 的用法默认为 1**），简单来说就是三个句子一起 embedding。（例如 ABCD 四个句子，会生成 AB、ABC、BCD、CDg）
- **LLM / 命题式**:让 LLM 直接判断边界
- **聚类式**:把语义相近的句子**聚类**成块(可跨不相邻句)
- **结构/层级式**:按标题、章节等文档结构切

##### 4.3 句子窗口检索
**定义**：存储时把文档切成单个句子，每个句子单独向量化；检索命中一个句子后，将这个句子前后各 N 个句子一起返回，形成一个上下文窗口，交给 LLM

**优势**：检索粒度细，定位准确，相关性高
**劣势**：检索粒度细而导致 LLM 拿到的信息不完整，存储量大，每个句子都需要单独向量化

##### 4.4 父子切割
**定义**：用小 chunk 检索，用大 chunk 生成，存储时同一段内容存两份，使用子段进行向量化，检索到子段时将父段一起返回。通常两者通过 ID 关联

##### 4.5 命题化切割
**定义**：使用 LLM 把文档分解为一条条那独立的「命题」，每个命题是一个完整、自包含的陈述句，包含了事实所需上下文，不依赖于别的片段

**优势**：每个 chunk 的语义密度最高、最独立，检索精度非常好
**劣势**：需要额外调用 LLM，成本比较高

##### 4.6 上下文检索（anthropic 2024 提出）
**定义**：让 LLM 看到整篇原始文档，为每个切出来的 chunk 生成一段简短的背景说明，把生成的 context 前置拼接到 chunk 前面，然后把 context + chunk 整体进行 embedding

## 五、Embedding 模型选型

- **第一是中英文比例**：知识库以中文为主，可以选择 Qwen3-Embedding；中英混合选 bge-m3（北京智源人工智能研究院）；纯英文或追求省事，选 text-embedding-3-small
- **第二是数据合规**：数据不能出境，就使用本地部署的开源模型，BGE 系列和Qwen3-Embedding 都是很好的选择
- **第三是向量维度**：维度越高精度越好，但存储空间和检索时间都会增加。百万量级（即百万 chunk）的知识库，1024 维是合理的平衡点；如果规模小，1536 维也无所谓

#### 5.1 如何评估 Embedding 模型

MTEB 是 **Massive Text Embedding Benchmark** 的缩写，可以理解为一套开源的文本向量模型评测基准。
不应该仅看 MTEB 这类通用排行榜的分数来选模型，正确的评估方法是在自己的业务数据上测试；准备几百条业务相关的「问题+正确答案 chunk」对，分别用候选模型做检索，看正确的 chunk 有没有出现在前 K 条结果里。

## 六、Embedding 有哪几种算法
Embedding 算法大致经历了三代演进。

**第一代是静态词向量**，以 Word2Vec 和 GloVe 为代表，把每个词映射成固定向量，但同一个词不管上下文是什么，向量永远不变，处理不了多义词。

**第二代是以 BERT 为代表的上下文相关向量**，同一个词在不同语境下有不同的向量，表达能力大幅提升，但 BERT 本身输出的是 token 级别的向量，两个句子要比较相似度就必须拼在一起跑，百万条文档就要跑百万次，检索速度完全不可接受。

**第三代是以 Sentence-BERT、SimCSE、BGE 为代表的句子级对比学习 Embedding**，专门为「两段文本有多相似」这个任务优化，**文档向量在建库时预先计算，用户提问时只计算“问题”的向量**，再去向量库检索，是 RAG 场景的标配。

面试官如果问到，就说我们是中文居多，选择的是 BGE（北京智源研究院）提供的 bge-m3

## 七、向量数据库选项
向量数据库是专门用来存储和检索「向量」的数据库；向量数据库的核心是**近似最近邻搜索（ANN）**，支持在百万及上亿的数据量中快速找到相似的片段。

#### 7.1 两种核心索引算法 HNSW 和 IVF

**HNSW （Hierarchical Navigable Small World 分层可导航小世界图）**，是目前召回率最高的 ANN 算法之一。它构建的是一个多层图结构，查询时从最上层的稀疏图开始导航，逐层收窄范围，最终在底层找到最近邻。Qdrant、Milvus、Chroma 默认都用 HNSW

**IVF(Inverted File Index 倒排文件索引)**
先对向量做聚类，把相似的向量分进同一个「桶」里，查询时只搜最相关的几个桶，而不是全量遍历。PostgreSQL 同时支持 HNSW 和 IVF

**优势**：HNSW 精度高、速度快；IVF 用聚类换内存，牺牲一点精度就能处理超大规模数据
**劣势**：HNSW 的内存消耗和向量数量成正比

#### 7.2 向量数据库的核心能力
- **Metadata 过滤**：向量数据库支持给每个向量挂上 metadata 字段，检索时加过滤条件，只在符合条件的子集里做 ANN 搜索
- **实时更新**：向量数据库都支持在线写入，新数据进来后增量构建索引，不需要停服重建
- **与关键词检索融合**：有些向量数据库同时支持向量检索 + BM25 关键词检索

#### 7.3 向量数据库选项

**本地验证阶段**：首选 Chroma、SQLite，上手快，本地内存运行，零配置

**中小到大规模、团队小、快速上线**：首选 Qdrant，性能好、API 设计简洁、文档完善、Rust 写的性能稳定

**数据规模在千万到亿级**：首选 Milvus，分布式支持好，但同时部署运维复杂度也高

**已经在用 PostgreSQL，数据库不是特别大**：首选 pgvector 插件，不用引入新组件，运维成本低

**数据在云上，用 Pinecone**，全托管 SaaS，按用量付费，适合快速验证商业化产品。不过要注意数据出境的问题，如果业务数据有合规要求，Pinecone 就不合适了。
