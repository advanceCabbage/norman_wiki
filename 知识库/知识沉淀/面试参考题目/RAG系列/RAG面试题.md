## 一、知识库持续更新机制
#### 1.1 RAG 知识库更新比普通数据库麻烦
- 原始文档与向量库之间是一对多关系；一篇文档可能被切割为几个或几十个 chunk
- 通常无法精准更新变更的 chunk 内容，因为文档内容变化，切割边界也会变化，chunk 会重新排列
#### 1.2 更新知识库的核心思路与解决
核心思路是：**先删掉旧文档对应的所有 chunk，再重新切割入库**
找到某篇文档被分割为哪些 chunk 的关键步骤是，切割和向量入库阶段给**每个 Chunk 的 metadata 里存上文档 ID 字段**，向量库都支持按 metadata 字段过滤批量删除。

#### 1.3 如何检测文档是否变化
- 常见的方案是内容 hash。每次文档入库时，计算文档内容的 MD5，把 hash 值和文档 ID、文档最后修改时间及对应的 Chunk ID 列表存下来。下次检测到这篇文档时，**首先对比最后修改时间是否一致，修改时间有变再计算 hash 和存储的值对比**，相同则说明未改动，不同则说明内容有更新，触发重新处理流程。

**两种主流的变更感知方式**

- **方式一定时轮询**：按固定时间扫描所有文档，对比最后修改时间、hash 值是否变更。适合对文档实时性要求不高的场景，例如：内部知识库、产品文档。劣势是：更新有延迟、文档数量大时全量扫描、对比也是一笔开销
- **方式二事件驱动**：数据源有变更时，主动发出一条消息，知识库更新服务订阅这些消息，收到事件立刻处理。优势是：延迟低，适合实时性要求高的场景。代价是需要数据源支持发消息的能力
#### 1.4 灰度更新：稳妥地切换新版本
**根本原因**：核心的生产知识库，直接删旧数据、写新数据风险大。例如新切割的内容可能存在问题、向量化入库失败等

**实现方案**：不直接删除旧数据，而是先并行写入新版本，验证没问题再切换

**具体做法**：把新版本的 chunk 写入时打上 version=new 的标签，旧版本保留 version=old。再验证阶段，用同一批测试问题同时跑新旧两个版本，对比答案质量。验证通过后，把检索时的版本过滤条件从 old 切换到 new，最后再清理掉旧版本的 chunk。


####  1.5 两个问题
#### 1.5.1 通过 MD 传入的文本应该如何命名
- 由唯一标识决定，通常由人和系统共同决定，目的是记录 documentId 为了实现文档更新

#### 1.5.2 如何给旧（待更新）的文档已有的 chunk 打上version=old
- **首先**分块时每个 chunk 的 metadata 字段中存入 docmentID 和 docVersion 字段，例如 docID：docmentID
- **然后**像 langchian 框架或其他，最终会在 milvus 数据表中有一个 docID 字段
- **接下来**为 docID建立倒排索引（把相同docID的数据位置记录在一起），查询时无需遍历所有 chunk
- **分版本查询**：调用向量库检索时同时传入 docVersion 字段，向量数据库会先按照docVersion 进行过滤，然后再进行相似度检索（同时也是基于 docVersion 创建了索引的）
- **最后**对比不同版本的回复内容，选择删除旧版本


#### 1.6 写我们更新的机制
- **第一学城类文档且是自动更新机制**：按照学城文档的 ID 作为 document_id，订阅学城文档更新事件，被更新后的文档会在每天晚上 12 点定时更新，与原文档比较 hash 值，有变化则对新文档进行 embedding 然后入库，与此同时删除旧文档
- **第二类 FAQ 内容格式的更新**：
	- 首先，我们会对每个 API 文档调用大模型进行摘要总结
	- 然后，调用知识库提供的 API 进行向量化存储，其中摘要会被向量化，API 原文会全量存储，并传入业务线+API 名称作为唯一标识
	- 后续，后台系统监听到 API 文档变化时，会触发定时任务，对 API 文档再次进行摘要总结并且调用知识库接口进行覆盖式更新

#### 1.8 如何切分 PDF

**首先区分 PDF 的类型**
- **原生文本 PDF** ： 直接抽文本
- **扫描件 PDF** ： 走 OCR
- **图文混排/表格**：视觉理解/多模态

**然后结构化 PDF 存储保存以下内容**
- 页码、标题层级
- 章节、段落
- 表格、图片、角注
例如合同 PDF 需要知道 chunk 来源于：第几章、第几条、第几页

**接下来切分 PDF chunk 的标准**
- 按照语义化切标题
- 正文内容可以按语义段落切
- 表格单独为一个 chunk，表格可以按照行列转化为结构化文本，每个 Chunk 都要带 metadata（例如：文档 ID、页码、章节标题、表格编码、时间版本等）。可以为表格添加上下文
- 图片与图表需要生成摘要

**最后可以给 Agent 提供 PDF 搜索工具，不直接将 PDF 全文给 Agent**
- search_PDF 检索相关片段
- read_page 读取指定页
- 抽表格
- 看图片
- 返回引用

**评测阶段关注的数据**
- 检索片段命中、页面正确
- 表格解析准确、OCR 无漏字
- 图片信息正确理解等

#### 1.9 RAG 权限管控
多租户、多权限管控策略

**第一：明确 RAG 权限管控的核心边界与失效场景**
- 确保从切片、检索到生成、输出全链路闭环，确保用户看不到任何权限外的信息，包括直接内容和间接推导结论
- 分片粒度不均会导致高密级内容夹带在低密级分片中，过滤失效
- 多维复杂权限超出向量库过滤能力
- 模型通过多片推理拼凑出敏感信息，发生间接泄密
- 权限变更与知识库更新不同步，导致临时权限过期仍能访问

**第二：选一套核心方案核心落地多种场景**
核心：分片级最小权限打标  + 检索后权限引擎校验 + 生成侧合规脱敏 三层防护
- **分片阶段**按最小权限粒度切割，单分片内权限登记、归属租户完全一致，杜绝不同权限内容混片，从源头降低夹带风险
- **检索时**按照用户权限进行筛选过滤，返回候选片段后统一送入独立权限校验引擎，引擎承载部门、职级、项目等全维度权限逻辑，剔除所有越权内容，不完全依赖向量库的原生过滤能力
- **生成前后**各做一次合规校验，生成前拦截敏感上下文，生成后检测输出内容的敏感等级与推理泄密风险，超权限内容自动脱敏或替换拒答话术

**第三：生成落地的异常处理细节**
- 向量数据库能力不足的场景，将复杂权限逻辑全部上移到检索代理层，向量库仅做租户级粗隔离，细粒度鉴权统一由权限引擎处理，不侵入底层存储
- 权限变更与知识库发布走同步流程，权限调整后异步刷新对应分片的权限标记，变更生效期间暂停对应范围的检索请求，保证过渡阶段无权限漏洞
- 所有检索与鉴权操作全程留痕，支持按用户、按文档溯源审计。
- 监控越权拦截次数、敏感片段检出率、推理泄密告警次数等异常指标自动触发告警
- 如果权限引擎出现故障，系统自动降级为最低权限模式，仅返回公开知识库内容。故障恢复后补做权限复核与审计
