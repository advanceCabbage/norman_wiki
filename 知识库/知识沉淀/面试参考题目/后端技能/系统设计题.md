# 一、如果你的系统的 QPS 突然提升 10 倍你会怎么设计?

按 **“先稳住系统 → 找出瓶颈 → 针对性扩容 → 压测验证”** 来回答。关键是：**QPS 增长 10 倍，不代表每个组件都需要扩容 10 倍**
### 第一步：先稳住系统，保证核心业务可用

可以先采取这些措施：
- **限流**：限制入口请求量，优先保障核心接口和关键用户。
- **降级**：暂时关闭推荐、复杂统计等非核心功能，返回简化结果或允许使用的缓存数据。
- **设置超时、控制重试**：避免慢请求长期占用资源，也避免重试进一步放大流量。
- **资源隔离**：防止非核心业务耗尽核心业务所需的线程、连接和计算资源
- **弹性扩容**：增加处理能力，让系统接得住更多请求（假设是数据库或下游饱和时，不能只靠增加应用实例）

**队列削峰解答**：队列削峰是把高峰期来不及处理的任务暂存在消息队列中，由消费者按照下游能够承受的速度逐步处理，等流量回落后再消化积压，从而避免突发请求压垮系统。它本质上是用处理延迟换取系统稳定，适合允许异步处理的业务；如果流量长期超过处理能力，仍然需要扩容或限流

接下来区分流量是**短期突发还是长期增长**：
**短期突发应对策略**：优先用已有缓存、预留容量、限流和队列削峰；恢复后逐步清理积压
**长期增长应对策略**：上述措施先争取时间，同时启动持续扩容和容量改造，不能长期依靠降级维持


### 第二步：找出瓶颈，确定哪一层先达到上限
需要沿着调用链，查看吞吐量、P95/P99 延迟、错误率，以及资源使用和排队情况。

|观察到的现象|可能的瓶颈|下一步确认|
|---|---|---|
|应用 CPU 持续很高|计算密集、序列化开销或热点代码|查看耗时分布和性能分析|
|应用 CPU 不高，但请求很慢|等数据库、外部接口，或者连接池耗尽|查看调用链和等待时间|
|数据库延迟明显上涨|慢查询、IO、锁竞争或连接过多|查看慢查询、锁等待和连接情况|
|大部分流量集中在少数数据|热点 Key、热点行或热点分区|查看访问分布，不能只看总量|
还需要区分：
- **读请求为主**：重点看缓存命中率、重复查询和数据库读取压力。
- **写请求为主**：重点看事务、锁竞争、写入吞吐和消息积压。
- **请求均匀增长**：水平扩容通常更容易起效。
- **单个热点暴涨**：需要针对热点处理，增加普通节点可能帮助有限
对于短时突发，重点找出当前最先饱和的环节；对于长期增长，还要识别扩容后会出现的下一个瓶颈

### 第三步：针对性扩容，根据瓶颈选择方案
这里的“扩容”既包括增加资源，也包括减少每个请求消耗的资源

**针对读请求，优先考虑「减少重复查询和多级缓存」**：如果瓶颈来自大量重复读取，继续把所有请求交给 MySQL 就不合适，Redis 也会遇到热点或带宽瓶颈。这时我会考虑「**本地缓存  +  Redis 分布式系统缓存**」双层架构。把那些极少变化的热点数据，直接加载到应用服务器自己的内存里。

**针对允许异步的写请求，核心思路是排队削峰**：引入**消息队列 MQ** 将高峰来不及处理的任务暂存在消息队列中，由消费者按照下游能够承受的速度逐步处理

**针对数据库底层的终极改造**：如果数据库是瓶颈，优先看索引、SQL、长事务（缩短事务，减少持锁时间）、锁等待和连接池配置，确认是否是慢查询或长事务造成的。如果优化后单库容量或吞吐仍然不够，再考虑「读写分离」和「分库分表」。用主库抗写压力，多台从库抗读压力；把原本的大表，按规律拆分小表，分散到不同的机器上，增加处理能力

**针对服务计算能力不足**：启用预留实例，支持无状态部署、水平扩容、自动缩扩容

### 第四步：压测验证，证明方案能承受目标流量
新方案先在隔离环境压测，再灰度上线，验证完整调用链，需要分别验证。

| 情况       | 验证重点                                              |
| -------- | ------------------------------------------------- |
| **短时突发** | 流量突然跳到 10 倍时，限流是否生效、扩容是否及时、队列是否溢出；<br>高峰结束后多久清空积压 |
| **长期增长** | 持续高负载下，延迟和错误率是否稳定，是否出现内存增长、<br>连接耗尽或持续积压，成本是否可接受  |
最终判断依据是：**目标流量下业务指标达标；超过容量时能受控降级；流量回落后能够恢复**

# 二、如何设计一个幂等接口，避免重复下单或重复扣款？

**幂等概念**：同一笔业务请求，不管执行一次还是重试多次，最终只产生一次业务结果
**触发场景**：用户连续点击、客户端超时重试、MQ 重复投递，都会将幂等问题引发出来

#### 第一步：先定义「什么算同一笔请求」
例如：创建订单时，客户端第一次操作时生成一个请求 ID，后续重试沿用它；服务端将请求 ID 和用户、接口等作用域一起作为幂等键

#### 第二步：让「防重复」和「业务执行」在同一个可靠边界里
如果订单就在 MySQL，给幂等键加唯一索引，在本地事务里插入请求记录、创建订单、保存处理结果。两个相同请求同时到达，只有一个能成功占用这个键；另一个等待事务结果后，查已有记录并返回对应订单

### 第三步：状态更新要带条件
比如支付成功只允许把订单从「待支付」改为「已支付」，并检查影响行数（本次 SQL 修改了多少条记录）。只有这次转换确实成功，才记录积分、通知等后续事件

### 第四步：跨系统调用要继续传递幂等键
本地接口做了去重，不代表第三方支付自动去重。我会给下游传固定的业务单号，使用它提供的幂等能力；调用超时后先按单号查询结果，确认未执行才决定是否重试

**总结汇总**：固定的业务幂等键识别同一笔请求，唯一索引和事务控制并发，状态条件更新避免重复推进，保存结果让重试返回原结果；跨系统操作则继续使用相同业务单号，并补上结果查询和记账。
