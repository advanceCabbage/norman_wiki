## 一、分布式事务解决的问题
**一次业务操作涉及多个独立的事务资源时，如何避免部分成功、部分失败破坏业务一致性**这些资源可以是不同数据库、不同服务背后的存储，也可以是数据库和消息队列

## 二、分布式事务策略列表

| 策略                     | 核心思路                             |
| ---------------------- | -------------------------------- |
| 2PC（两阶段提交，常通过 XA 接口接入） | 各分支先持久化准备状态，协调者再统一决定提交或中止        |
| 3PC（三阶段提交）             | 在投票与提交之间增加预提交状态，配合超时和终止协议减少阻塞    |
| TCC                    | 业务实现 Try 预留、Confirm 确认、Cancel 释放 |
| Saga                   | 多个本地事务逐步提交，失败后执行业务补偿             |
| AT（以 Seata 为例）         | 自动保存数据前后镜像，先本地提交，失败时按日志反向恢复      |
| 事务消息（以 RocketMQ 为例）    | 先发不可消费的半消息，再按本地事务结果提交或撤销消息，异常时回查 |
| 本地消息表 / Outbox         | 业务数据和待发送事件在同一本地事务落库，再异步投递        |

## 三、分布式事务详解

#### 3.1 2PC ：先准备，再统一决定
**核心概念**：
- **第一阶段：先准备**：**协调者**要求所有参与者准备提交；**参与者**完成必要的本地操作、检查和日志持久化，但不正式提交；收集参与者返回的 Yes 或 No
- **第二阶段：Commit 或 Abort**：所有参与者都返回 Yes，协调者持久化 Commit 决定；任一参与者返回 No 或超时未提交，协调者决定 Abort
**失败时为什么会阻塞**：假设协调者已经把 Commit 发给订单数据库，随后宕机，库存数据库还没收到决定。库存数据库只知道自己已准备，无法判断其他分支是否提交。
Prepared 参与者不能因为等待超时就自行回滚，否则可能与已经提交的分支冲突。它需要恢复协调日志，或通过协议允许的决策查询获得结果。网络分区时，为保持原子性，可能必须等待。
如果最终决定已经是 Commit，某个参与者暂时无法提交，应恢复后继续提交，不能随意把全局决定改成回滚
**适用倾向**：参与者支持相应接口、事务较短，且可以接受协调等待和资源占用的跨库操作

#### 3.2 3PC：先询问能否提交，再投票，最后正式提交
**核心概念**：
- **第一阶段，CanCommit**：协调者询问能否提交，参与者投票；出现拒绝或未满足协议要求则中止
- **第二阶段，PreCommit**：投票全部通过，协调者广播预提交；参与者进入预提交状态，记录必要信息并确认
- **第三阶段，DoCommit**：收到预提交确认后，协调者通知正式提交，参与者提交并确认
**核心解决问题**：3PC 相对于 2PC，主要想解决：协调者故障后，参与者处于“不知道该提交还是回滚”的状态，导致事务长时间阻塞。3PC 增加 PreCommit 状态，是为了让参与者掌握更多全局进度信息，并配合故障检测、节点间状态交换和终止协议，在协调者故障后仍有机会安全推进
**3PC 的局限是什么**：经典 3PC 依赖通信延迟有界、故障可靠检测、没有网络分区等假设。它改善的是特定故障条件下的阻塞问题，并没有解决任意网络故障下的安全提交问题 

#### 3.3 TCC：先预留，再确认或释放
**核心概念**：TCC 有三个业务接口，但全局推进通常分为两个阶段：第一阶段 Try，第二阶段根据结果调用 Confirm 或 Cancel
**需要预防的三个问题**：
- **幂等**：Confirm / Cancel 重复调用不能重复扣款或重复释放。用分支状态和条件更新控制，例如 `TRIED → CONFIRMED`
- **防悬挂**：Try 因网络延迟晚于 Cancel 到达时，必须识别已经取消并拒绝继续预留
**代价与优势**：通过业务预留降低跨流程持有数据库锁的需要，但业务要自行维护预留、确认、释放和恢复规则。取消通常释放的是预留资源，区别于 Saga 对已完成业务的补偿

#### 3.4 Saga:已提交的步骤通过业务操作补偿
**核心概念**：Saga 把长业务拆成多个本地事务，每一步独立提交。当某一个事务失败时，补偿通常按依赖关系逆向进行
**由谁驱动流程**
- **编排式**：由协调器持久化步骤状态，决定执行下一步、重试还是补偿
- **事件协同式**：各服务订阅事件，完成本地操作后发布下一事件，按约定推动流程

**失败与并发边界**
- **超时不等于失败**：支付接口超时可能已经扣款，应按幂等业务号查询结果，再决定继续或退款
- **补偿也可能失败**：需要记录状态、重试、告警，必要时人工处理，不能写成一次异常回调就结束
- **默认没有全局隔离**：其他流程可能已经看到中间状态，需要“待确认”等业务状态或预留规则限制使用
- **有些动作不可逆**：已经发送的邮件、已经发货的商品无法靠数据库回滚撤销，需要业务接受或重新设计步骤顺序
**适用倾向**：长时间运行、跨异构服务，并且能够定义业务补偿或向前恢复的流程

#### 3.5 AT：框架自动记录并撤销数据库修改
**核心概念**：由框架自动记录并撤销数据库修改
**核心步骤**：
- **第一阶段：先完成业务修改，同时留下回滚依据**：例如库存从 10 改成 9，把修改前后的数据记入 `undo_log`，与业务修改一起提交。本地数据库锁释放，全局锁继续保留
- **第二阶段：根据全局事务结果收尾**
	-  **全部成功**：保留业务修改，清理回滚日志并释放全局锁。
	- **需要回滚**：检查当前数据与修改后的镜像是否一致；一致时，根据日志恢复，例如库存从 9 恢复到 10。若不一致，则按冲突策略处理，不能直接覆盖
**适用范围**：AT 依赖数据源代理、支持的数据库与 SQL，不是任意资源都能自动回滚。AT 的日志能撤销数据库修改，但不能自动撤回已经发送的邮件或外部支付。与 XA / 2 PC 的重要区别是：AT 第一阶段已经提交本地业务修改，XA 分支在准备后尚未正式提交
**AT 与 Saga 的补充差异**：

| 对比 | AT | Saga |
| --- | --- | --- |
| 补偿依据 | 数据库前后镜像和回滚日志 | 开发者定义的业务规则 |
| 谁实现补偿 | 框架生成反向 SQL | 开发者实现取消、退款等接口 |
| 恢复目标 | 撤销受管理的数据库修改 | 达到业务认可的最终状态 |
| 并发控制 | 全局锁与回滚前的数据校验 | 业务自行处理隔离、预留与状态转换 |
| 外部系统操作 | 无法仅靠数据库日志撤销 | 外部系统支持补偿时可纳入流程 |

#### 3.6 事务消息
**核心概念**：事务消息用于**协调“本地业务事务”和“消息发布”**：业务提交成功，消息才允许投递；业务明确回滚，消息就不投递。
**执行原理**：
  这里以 RocketMQ 为例
- **先发半消息**：MQ 保存消息，但暂时不让消费者看到。
- **执行本地事务**：例如创建订单，并保存可回查的事务结果。
- **通知 MQ**：本地提交成功则 Commit，明确回滚则 Rollback，结果不确定则 Unknown。
- **异常时回查**：如果生产者宕机或没通知成功，MQ 回查生产者保存的本地事务结果，再决定是否投递。
- **消费端独立处理**：消息可见后，消费者执行自己的本地事务，并处理重复投递

它解决的是生产端“业务已提交但消息没发出，或业务失败却发出了消息”的问题。消费端仍需重试和幂等，MQ 不会自动回滚订单或库存数据库
## 四、分布式事务选型

| 主要条件               | 优先评估                 |
| ------------------ | -------------------- |
| 所有操作能放进同一个数据库事务    | 本地事务，先减少跨资源边界        |
| 跨库、短事务、资源支持准备与提交接口 | 2PC / XA             |
| 能明确设计冻结、预留、确认和释放   | TCC                  |
| 长流程、外部系统、可定义业务补偿   | Saga                 |
| 受支持的数据库访问，希望少写补偿代码 | Seata AT             |
| 本地更新后异步驱动下游        | 事务消息或 Outbox，配合业务状态机 |
