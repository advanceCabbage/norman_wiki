## 一、分布式 ID 定义
分布式 ID 解决的核心问题是：**多个进程、服务或数据库同时创建数据时，如何在约定的业务范围内生成唯一标识**。

**设计分布式 ID 应该考虑以下要点：**

| 目标 | 含义与取舍 |
| --- | --- |
| 唯一性 | 明确在哪个业务范围内、跨哪些节点，以及重启和故障后仍不能重复 |
| 可用性 | 数据库、网络或协调服务故障时，是否还能生成 ID |
| 性能 | 每次生成是否需要网络请求，能否在本地批量生成 |
| 有序性 | 是否需要大致按时间排序，还是要求严格递增 |
| 存储成本 | 64 位整数占 8 字节，UUID 的二进制值占 16 字节；文本保存通常更大 |
| 运维成本 | 是否需要管理节点编号、时钟、号段和故障恢复 |
## 二、常见的分布式 ID 策略
#### 2.1 数据库自增
**原理**：由同一个数据库分配 ID，所有服务实例共享同一套分配规则
**优势**：实现简单；整数紧凑；适合多个应用实例共用一个数据库，通常不需要额外发号服务
**劣势**：依赖数据库的性能和可用性；多个独立数据库各自自增会冲突；回滚、缓存和故障等情况可能产生空洞，不能当作连续编号或提交顺序
**适用场景**：单库业务、早期项目

#### 2.2 分步长 / 分余数自增
**原理**：预先把整数空间分给不同节点
**优势**：生成时无需逐次访问统一发号中心；规则简单；可得到整数 ID
**劣势**：扩缩容时需要重新规划，不能直接修改步长；节点编号或计数进度管理错误会重复；各节点之间不保证时间顺序
**适用场景**：节点数量相对固定的多库自增方案

#### 2.3 数据库号段模式
**原理**：数据库统一分配互不重叠的区间，各节点领取后在本地逐个使用
**优势**：每领取一段才访问数据库，显著减少数据库压力；段内生成快；已领取号段未耗尽时，可以容忍数据库短时间不可用
**劣势**：要管理预加载和号段大小；节点宕机可能浪费剩余号码；不同节点消耗速度不同，不保证全局严格递增；分配记录恢复到旧状态可能重复发段
**适用场景**：统一发号服务、高吞吐的整数 ID。美团 Leaf 提供了号段实现

#### 2.4 Redis 原子递增
**原理**：所有节点访问同一个 Redis 计数器，通过原子命令获取不同值
**优势**：实现简单；并发调用由 Redis 原子处理；正常运行时按该计数器的命令执行顺序递增
**劣势**：每次取号需要网络访问，依赖 Redis；计数器删除、过期或回退可能导致重复。异步复制和故障切换可能丢失已确认的递增结果，原子命令本身不能保证故障后的永久唯一性
**适用场景**：已有 Redis，且能够明确处理持久化、故障切换和计数器生命周期的集中发号需求。也可批量领取区间，演变为号段模式

#### 2.5 UUID v4
**原理**：通过高质量随机数生成 128 位标识，其中 122 位用于随机部分，其余位用于版本等信息。各节点无需互相协调
**优势**：本地生成；无需管理节点编号；扩容方便；不依赖数据库或发号服务
**劣势**：碰撞概率极低，但并非数学上绝对不可能；比 64 位整数大；没有时间顺序，作为 B-tree 索引键时可能增加随机写入和维护开销，具体影响取决于数据库实现和负载
**适用场景**：任务 ID、资源 ID、多服务独立创建对象。是学习项目中容易落地的方案

#### 2.6 UUID v7
**原理**：把时间信息放在高位，结合随机部分等生成标识，使结果可以大致按生成时间排序
**优势**：通常可以本地生成，无需分配节点编号；相比 UUID v 4 更有时间局部性，通常更适合希望按时间组织的索引和数据
**劣势**：比 64 位整数大；仍需正确实现随机数和同一时间单位内的生成逻辑；时钟偏差、回拨和同毫秒并发会影响排序，不能据此判断跨节点事件的严格先后；标识包含时间信息
**适用场景**：希望独立生成，同时需要时间排序特征的资源和事件 ID

#### 2.7 Snowflake（雪花算法）及其变种
**原理**：把时间戳、节点编号和序列号拼成一个整数。经典设计使用 64 位：
```text

1 位保留位 | 41 位相对毫秒时间戳 | 10 位节点编号 | 12 位序列号

同一毫秒内：

节点 A：时间 T + 节点 A + 序号 0、1、2……

节点 B：时间 T + 节点 B + 序号 0、1、2……

```
节点之间靠编号区分，同一节点在同一毫秒内靠序列号区分。序列号耗尽时通常等待下一毫秒；位数可以按业务调整
**优势**：完成节点初始化后，可以在本地高速生成；64 位整数较紧凑；整体大致按时间递增
**劣势**：节点编号必须唯一且能安全复用；时钟回拨可能造成重复，需要等待、拒绝发号或采用经过验证的逻辑时钟方案；重启时也要避免复用旧的时间与序列组合；时间戳和序列号的位数限制了使用年限及单节点吞吐
**适用场景**：高吞吐、需要紧凑整数 ID 的业务。美团 Leaf 也提供 Snowflake 实现

## 三、分布式 ID 策略选择

| 需求 | 优先考虑 | 原因 |
| --- | --- | --- |
| 多实例共用一个数据库，需求简单 | 数据库自增 / Sequence | 复用数据库的分配能力，维护成本低 |
| 多节点独立生成，快速落地 | UUID v 4 | 不需要发号中心和节点编号 |
| 独立生成，同时希望按时间组织 | UUID v 7 / ULID | 保留时间排序特征 |
| 高吞吐、64 位整数、本地生成 | Snowflake | 生成快、占用小，但要治理时钟和节点编号 |
| 统一发号，希望减少数据库访问 | 号段模式 | 批量分配，段内本地生成 |
