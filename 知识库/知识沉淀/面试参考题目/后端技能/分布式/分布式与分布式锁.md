## 一、介绍分布式
**分布式系统是多个独立计算节点，通过通信协作，共同提供服务**节点可以承担相同工作（集群也是分布式系统的一种形式），也可以分别承担接单、执行、存储等职责。

| 需求              | 处理方式            | 例子                      |
| --------------- | --------------- | ----------------------- |
| 单机计算、存储或吞吐容量不足  | 将工作或数据分散到多个节点   | 多个 Worker 处理不同任务，数据分片存储 |
| 单节点故障时仍希望服务可继续  | 复制数据或服务，并设计故障接替 | 主节点故障后由副本接替             |
| 用户、设备或业务分布在不同位置 | 将服务分布部署并协作      | 就近接入、跨区域数据处理            |
分布式的收益依赖具体机制。增加副本通常提高可用性或读取能力；将不同数据分到不同节点才直接扩展总数据容量。增加机器也不会自动消除共享数据库等瓶颈

#### 1.1 CAP 的含义

| 字母       | 简单理解                      |
| -------- | ------------------------- |
| C，一致性    | 已确认写入完成后，后续读取不能随意返回更早的值   |
| A，可用性    | 不能因为联系不上其他节点就无限等待或停止提供该操作 |
| P，网络分区容忍 | 机器都活着，但彼此联系不上，也必须定义行为     |
当出现网络分区时，无法同时保证一致性与可用性。原因在于出现网络分区时，服务器 M 和 N 上的数据不一致，假设 M 服务器数据被修改后，用户访问 N 服务器。此时如果直接返回 N 服务器上的数据则违反例一致性；假设为了保证正确而等待，则违反了可用性


## 二、分布式锁概念
#### 2.1 分布式锁解决的问题
**分布式锁让多个独立进程围绕同一资源竞争处理资格，以协调可能冲突的操作**。主要解决以下三个场景：

| 场景            | 想达到的目标       | 重复发生的后果          |
| ------------- | ------------ | ---------------- |
| 热点缓存同时失效      | 尽量由一个进程回源并重建 | 通常增加查询和计算成本      |
| 多个调度器触发同一批处理  | 协调谁负责发起本轮工作  | 可能重复创建任务或产出      |
| 多个处理者修改同一业务资源 | 避免冲突步骤并发推进   | 可能出现数据错误，需额外业务约束 |
#### 2.2 分布式锁需要满足安全性与活性
- **安全性**：在约定的故障模型与有效期内，不应有两个有效持有者同时被允许执行冲突操作。
- **活性**：持有者退出或崩溃后，其他参与者在必要服务恢复可用时，最终仍有机会取得资格，不能永久占用
<font color="#c0504d">租约和会话可以帮助处理崩溃后的释放，但它们不能强制停止旧进程。可靠设计还需要回答：失联期间能否继续、过期后谁可以接管、旧请求由谁拒绝。无限持续的网络故障下不能承诺总能取得锁</font>

## 三、分布式锁的实现
#### 3.1 Redis 分布式锁
**核心概念**：把“某个资源暂时由谁处理”的资格，保存在所有进程共同访问的 Redis 中，通过原子操作竞争这个资格。Redis 保存的是处理资格，不会自动锁住数据库或停止业务代码。尤其是锁过期后，旧进程仍可能运行，关键业务写入还需要版本等条件校验

**Redis 的加锁与解锁**：
```text
SET lock:report:123 本次随机token NX PX 10000
```
加锁时创建锁与设置过期必须原子完成。假设拆分为两个请求，第一步成功后进程崩溃，可能留下没有过期时间的锁

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
return redis.call('DEL', KEYS[1])
end
return 0
```
解锁时查询锁与删除锁必须原子完成，使用 Lua 脚本确保原子性操作。假设拆分为两个请求，可能出现 GET 时属于你的锁，到 DEL 时可能已经属于别人了（可能是锁到期，由 Redis 自动清理）



**Redis 锁的常见故障**

- **错误一：业务未完成但锁已过期**：过期删除的是锁记录，但A线程可能仍在执行，此时可能出现 B 线程拿到锁，然后出现竞争关系
- **对应的处理方案**：
	- 长任务快到期，使用原子操作进行续租；
	- 续期失败或无法确认资格时，通知业务停止，后续步骤不再执行（已发出的请求，不一定能取消）；
	- 实际写入端拒绝旧任务（关键保护），例如数据库使用版本条件更新，对于低版本的任务拒绝执行，核心在于检查版本与写入操作需要同时执行；
	- 对外部副作用做幂等，这样即使旧任务和新任务都发送了同一笔业务请求，接收方也能避免重复执行

- **错误二：主从故障切换导致两个客户端同时持有锁**：A 在主节点加锁成功，锁记录尚未复制，主节点故障，没有该锁记录的副本被提升为主节点，B 在新主节点加锁成功，A 还在执行，B 也开始执行
- **对应的处理方案**：使用 `WAIT` 可以等待副本确认，降低丢失写入的概率，但官方明确说明它不会把 Redis 变成强一致系统，故障切换下仍存在丢失已确认写入的情况。关键业务需要实际存储端约束，不能仅靠增加副本数量证明互斥

#### 3.2 Redis Redlock
**核心概念**：Redlock 是一种**由客户端在多个独立 Redis 节点上申请锁，并根据多数成功结果判断是否获得限时处理资格的算法**。这些节点不依靠主从复制来同步锁
**解决问题**：降低对单个 Redis 锁节点的依赖，并尝试避开“主节点加锁成功、尚未复制就故障，导致接替节点丢失锁记录”的问题
**使用边界**：
- **无法取得有效多数时，必须放弃本次执行**：网络故障可能让客户端拿不到锁，不能为了“继续提供服务”而绕过多数条件
- **依赖时间方面的假设**：需要正确计算剩余有效期，并考虑时钟漂移；Redis 时钟异常跳变可能导致锁提前过期。拿到多数节点的成功响应，不代表可以一直持有锁。
	- **时钟漂移解决手段**：
		- 使用 NTP 持续同步可靠时间源，减少异常跳变
		- 客户端用单调时钟计算耗时，适合计算“经过了多久”，不会因系统日期而被调整
		- 预留时钟漂移余量，仅能用于覆盖假设范围内的小幅误差，无法覆盖任意幅度的时间跳变
		- 关键写入仍由资源端校验
- **业务不能无限期执行**：A 暂停到锁过期后，B 可以获得锁；A 恢复时仍可能继续工作。续期可以降低概率，但不能消除这种情况



#### 3.3 ZooKeeper 锁
**核心概念**：约定多个客户端有序竞争资源，以及持有者故障后的接管
**核心原理**：竞争者在同一锁路径下创建**临时顺序 znode**：临时表示绑定会话，顺序表示服务端追加序号。只监听前驱，通常一次释放只唤醒下一个竞争者，避免所有等待者同时被唤醒的“惊群”
**使用边界，断线与会话过期的区别**：短暂断线不等于立即释放：会话可能在超时前恢复。断线期间，客户端也可能尚不知道集群已判定其会话过期，应暂停依赖锁的工作；确定过期后必须放弃原资格。

#### 3.4 etcd 锁
**核心概念**：etcd 锁是一种借助 etcd 集群协调多个进程处理同一资源的分布式锁。客户端申请锁并绑定租约，获得资格后执行工作、定期续约；主动解锁或租约到期后，其他客户端可以接手。etcd 通过 Raft 多数派共识维护锁状态，避免普通异步主从切换中锁记录丢失的问题。但租约过期不会停止旧程序，关键业务写入仍需接收端控制
