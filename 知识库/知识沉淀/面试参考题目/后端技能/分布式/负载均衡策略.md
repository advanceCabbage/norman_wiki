## 一、负载均衡概念
负载均衡是在多个可用服务节点之间分配流量，以利用处理能力、降低延迟并提高可用性。**均衡不一定意味着每台机器收到同样多的请求，也可以按容量、实时负载、访问位置或请求归属进行分配**
## 二、实例常见的策略

| 策略          | 分配方式                                        | 优势                                  | 劣势                                          |
| ----------- | ------------------------------------------- | ----------------------------------- | ------------------------------------------- |
| 轮询          | 按顺序依次选择可用节点，如 A → B → C → A                 | 实现简单、开销低；节点性能和请求成本接近时较均衡            | 不感知实际忙闲；请求数均衡不代表资源消耗均衡                      |
| 加权轮询        | 按配置权重分配，例如权重 2:1 时，较长时间内请求数量约为 2:1          | 适应节点容量差异；便于按比例分配流量                  | 静态权重不能自动反映实时负载，配置不当会让节点过载                   |
| 随机／加权随机     | 随机选择节点，或按权重决定节点被选中的概率                       | 开销低，不必维护统一轮询顺序；大量请求下可接近期望比例         | 小样本可能明显不均；基础版本不感知忙闲                         |
| 最少连接        | 优先选择当前活跃连接数较少的节点                            | 能适应连接持续时间不同的场景                      | 连接数不等于请求量或 CPU 负载；长连接复用时可能判断失真              |
| 加权最少连接      | 综合节点权重与活跃连接数，按容量比例比较连接负载                    | 兼顾节点能力差异和连接忙闲                       | 需要维护连接状态与权重；仍受连接数不能准确代表工作量的限制               |
| 最少请求／加权最少请求 | 根据正在处理的请求数选择节点，也可结合权重；部分实现只比较抽样候选节点         | 对请求耗时差异较敏感，比只看连接数更适合多路复用请求          | 请求成本可能差异很大；调度器掌握的计数通常只是其可见范围内的状态            |
| 随机二选一       | 随机选两个候选节点，再按活跃请求数等指标选择较空闲者                  | 避免每次扫描所有节点，选择开销小；缓解调度器同时追逐同一空闲节点的问题 | 不保证选到全局最空闲节点；效果依赖候选负载指标                     |
| 最短响应时间      | 根据历史响应时间选择节点，具体实现可同时考虑活跃连接或未完成请求            | 能根据服务表现调整流量分配，倾向于较快节点               | 需要采样与平滑；历史指标有滞后，不同请求类型也会影响比较                |
| IP 哈希       | 使用客户端 IP 或其部分信息计算目标节点                       | 在节点集合稳定时提供一定访问亲和性                   | 多用户共用出口 IP 时可能集中到同一节点；IP 变化会改变归属；不能可靠识别同一用户 |
| 普通哈希        | 对用户 ID、会话 ID、请求路径等计算哈希，例如 `hash(key) % 节点数` | 相同 Key 可稳定路由，便于缓存复用或按对象处理           | 热门 Key 仍会集中；取模方案在节点数变化时可能大量重新映射             |
| 一致性哈希       | 通过哈希环或其他一致性映射结构，将请求 Key 映射到节点               | 节点增减时通常只改变部分 Key 的归属，减少缓存失效与重新映射    | 实现更复杂；仍会遇到热门 Key 和数据倾斜，不自动实现实时负载均衡          |

#### 2.2 跨地域与全局流量调度策略

这类策略常用于全局负载均衡（GSLB），决定访问哪个地区或机房。

| 策略     | 分配方式                                   | 优势                     | 劣势                                        |
| ------ | -------------------------------------- | ---------------------- | ----------------------------------------- |
| 地理位置路由 | 根据用户来源地区匹配预设规则，例如华北用户优先进入北京机房          | 规则直观可控，便于地域运营与流量划分     | 位置识别可能不准确；需要维护区域与默认规则；不保证目标延迟最低           |
| 地理邻近路由 | 根据用户与服务节点的位置，倾向选择地理距离较近的节点；可通过偏置调整覆盖范围 | 可按节点位置划分服务范围，并调整地域流量分布 | 地理距离不等于网络距离；不天然反映拥堵和节点实时负载                |
| 延迟路由   | 根据用户网络到各区域的延迟数据，倾向选择延迟较低的区域            | 更贴近网络访问体验，能适应网络路径变化    | 依赖测量覆盖与更新周期；估算延迟不等于每次请求的实际耗时，也不直接代表机房剩余容量 |
| 权重路由   | 在多个区域入口之间按配置权重分配流量                     | 便于灰度、流量迁移和按区域容量分配      | 不保证就近；DNS 方式下解析缓存与用户流量差异会使实际请求比例偏离权重      |
## 三、常见负载均衡组合策略

```text

北京用户
↓ 地理位置／地理邻近／延迟路由
北京机房入口
↓ 轮询／加权轮询／最少请求等
北京服务器 A、B、C
```

也可以先按用户 ID 做一致性哈希，再结合过载保护；或者先按区域优先级选择健康机房，再在机房内选择实例。组合时需要明确：发生故障、扩缩容或过载时，是优先保持原有归属，还是允许请求转移
