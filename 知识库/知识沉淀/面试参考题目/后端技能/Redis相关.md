## 一、Redis 常见的数据类型与对应场景
Redis 是以键值形式组织数据、主要在内存中处理请求的数据存储服务。常见类型如下，此表并非新版 Redis 的完整类型清单

| 类型          | 特点                    | 常见场景       |
| ----------- | --------------------- | ---------- |
| String      | 保存字符串、数字或二进制数据        | 缓存、计数器     |
| Hash        | 字段到值的映射               | 用户资料、对象属性  |
| List        | 有序、允许重复，支持两端操作        | 简单队列、最近记录  |
| Set         | 无序、成员不重复，支持集合运算       | 去重、标签、共同好友 |
| ZSet        | 成员唯一，按关联的分数排序         | 排行榜、延迟任务   |
| Bitmap      | 用位表示状态，基于 String      | 签到、在线状态    |
| HyperLogLog | 近似统计不同元素的数量           | 独立访客数统计    |
| Geospatial  | 经纬度、距离及范围查询，基于 ZSet   | 附近门店       |
| Stream      | 带消息 ID 的追加式消息结构，支持消费组 | 消息流、事件处理   |
**ZSet 底层数据结构**
ZSet 根据数据规模选择编码：
- **小数据使用 listpack**：在连续内存中按序保存成员和分数，节省内存，按成员查找通常需要 O(N) 遍历
- **超过阈值后使用哈希表 + 跳表**：哈希表按成员定位数据，查询分数平均 O(1)；跳表维护顺序，插入、删除和排名查询平均 O(log N)，常见范围查询为 O(log N + M)，M 为返回元素数

## 二、Redis 性能与网络模型
#### 2.1 Redis 为什么快
- **内存访问**：常规读写主要访问内存，通常无需为每个请求等待磁盘。
- **合适的数据结构**：哈希表、跳表等降低操作复杂度，紧凑编码减少内存开销。
- **事件驱动与 I/O 多路复用**：少量线程可管理大量连接。
- **核心执行路径简单**：普通命令主要串行执行（主线程处理），减少共享数据加锁与线程切换开销。
单线程本身不是“快”的充分原因；大范围操作、复杂脚本、大对象处理和网络传输仍可能产生高延迟。
#### 2.2 单线程与多线程模型
普通 `GET`、`SET` 等命令的核心数据操作主要由**主线程执行，整个 Redis 进程并非只有一个线程**。

| 执行单元      | 主要工作                                                       |
| --------- | ---------------------------------------------------------- |
| 主线程       | 普通命令执行、核心数据结构操作                                            |
| 网络 I/O 线程 | 启用后分担 socket 读写、协议解析（读客户端的请求、解析客户端协议、执行 GET（主线程）、写回客户端的请求） |
| BIO 后台线程  | AOF 后台 fsync、异步内存释放、文件关闭等                                  |
## 三、原子性与并发控制
#### 3.1 Redis 事务的概念
Redis 事务是一种**将多条命令先入队，再按顺序连续执行**的机制，。执行整组命令期间，其他客户端的命令不会插入其中
它保证执行时的隔离，但**不提供错误发生后的自动回滚**，不能理解为“所有命令要么全部成功，要么全部失败”

#### 3.2 Lua 脚本的概念、优势与劣势
**概念**：将一段 Lua 程序发送到 Redis，通过 EVAL 或 EVALSHA 在服务端执行。脚本可以调用 Redis 命令，并根据中间结果进行判断、计算和循环；执行期间不插入其他客户端命令。
**优势**：
- 支持服务端条件判断，能把“读取 → 判断 → 修改”作为一个连续操作完成。
- 多步逻辑通过一次脚本调用执行，减少客户端与 Redis 的网络交互。
- 避免客户端读取与提交之间的并发窗口，不必为这类逻辑使用 WATCH 冲突重试。
**劣势**：
- 需要编写、测试和维护脚本；使用 EVALSHA 时还需处理脚本缓存丢失后的重新加载。
- 脚本执行过久会阻塞其他请求，应控制逻辑复杂度和处理的数据量。
- 未捕获的运行时错误会终止脚本，但之前成功的修改保留，不自动回滚；redis.pcall 可以接收命令错误，也不会自动撤销修改

#### 3.3 MULTI 的概念、优势与劣势
**概念**：MULTI 是**开启 Redis 事务的命令**。随后普通数据命令只进入队列，返回 QUEUED；EXEC 才执行整组命令并返回各自结果。DISCARD 用于取消尚未执行的队列。
因此，通常所说的“使用 MULTI 实现事务”，完整指的是 **MULTI + 命令队列 + EXEC**，MULTI 本身不会立即执行队列。
**优势**：
- 直接组合已有 Redis 命令，使用简单，客户端支持成熟，无需维护 Lua 脚本。
- 整组命令按顺序执行，中间不插入其他客户端命令，适合步骤和参数已确定的操作。
- 可以结合 WATCH，在提交前检查依赖的数据是否被修改。
**劣势**：
- 入队时拿不到真实执行结果，无法在队列中根据前一条命令的返回值决定后续操作。
- 若业务必须在客户端读取、判断再写入，通常需要 WATCH 配合，并自行处理冲突重试。
- 入队阶段出现命令格式等错误时，EXEC 会拒绝执行整组事务；执行阶段某条命令报错时，其余命令仍继续执行，成功的修改不自动回滚

#### 3.4 补充概念，WATCH 与乐观锁
乐观锁是并发控制思想；WATCH 是 Redis 提供的冲突检测命令。WATCH 配合 MULTI + EXEC，可以实现乐观锁式的更新流程

**WATCH 是 Redis 的一个命令**，用来让**当前连接监视一个或多个 key 是否发生修改**，例如 `WATCH count`。
它需要配合 MULTI + EXEC：提交时，如果任一被监视的 key 在 WATCH 之后、EXEC 执行检查之前发生了修改，Redis 就不执行整组事务，EXEC 返回空结果；没有检测到修改才执行事务。
WATCH **不阻止别人读写，也不冻结数据**。它监视修改事件，不只比较最终值；值被改后又改回，也会导致冲突判定。过期、淘汰也会触发冲突判定

**乐观锁**是一种通用的**并发控制思想**：假设冲突较少，读取、计算时不加排他锁，在提交更新时检查数据是否被其他操作修改。
- 没有冲突：提交更新。
- 存在冲突：放弃本次更新，由业务决定重新读取并重试，或返回失败。
数据库的版本号校验也是这种思想的一种实现，乐观锁不专属于 Redis

## 四、Redis 持久化

#### 4.1 三种持久化策略

| 方式 | 原理 | 优势 | 劣势 |
|---|---|---|---|
| RDB | 保存某个时刻的数据快照 | 文件紧凑，恢复通常较快，方便备份 | 故障时可能丢失最后一次快照之后的数据；后台保存有 fork 和写时复制开销 |
| AOF | 记录数据修改，恢复时重放 | 可调节刷盘频率，数据丢失窗口通常更小 | 日志可能更大，恢复可能更慢；有日志写入、刷盘、重写开销 |
| 混合持久化 | RDB 格式基线 + 后续 AOF 增量 | 结合快照加载速度和增量日志 | 仍有重写开销，丢失窗口仍受 AOF 刷盘策略影响 |

混合持久化指 AOF 的基线部分采用 RDB 格式，不等于简单地同时开启独立 RDB 快照与 AOF。纯缓存场景也可以关闭持久化，但重启后需要重新填充缓存

**AOF 原理与刷盘策略**：AOF 全称 **Append Only File**。逻辑上追加记录修改数据的操作，只读查询不需要记录。恢复时加载基线并重放增量，重建数据状态。

| appendfsync 策略 | 同步磁盘的时机                   | 取舍                    |
| -------------- | ------------------------- | --------------------- |
| always         | 每次 AOF 写入后同步，可合并一批命令刷盘    | 持久性更强，磁盘开销较高          |
| everysec       | 后台大约每秒同步一次                | 常用折中，故障时通常可能丢失约 1 秒数据 |
| no             | Redis 不主动执行 fsync，由操作系统安排 | 同步开销较低，丢失窗口更不确定       |

写入文件或操作系统页缓存不等于已同步到持久介质；everysec 的“约 1 秒”不应当作任何异常下的严格上限。

## 五、Redis 缓存治理策略

#### 5.1 内存淘汰策略

| 策略 | 候选范围 | 规则 |
|---|---|---|
| noeviction | 不淘汰 | 默认策略，拒绝受内存限制的写入 |
| allkeys-lru | 所有 key | 优先淘汰最近最久未使用的 |
| volatile-lru | 有过期时间的 key | 同上 |
| allkeys-lfu | 所有 key | 优先淘汰访问频率低的 |
| volatile-lfu | 有过期时间的 key | 同上 |
| allkeys-random | 所有 key | 随机淘汰 |
| volatile-random | 有过期时间的 key | 随机淘汰 |
| volatile-ttl | 有过期时间的 key | 优先淘汰剩余 TTL 短的 |
| allkeys-lrm | 所有 key | 优先淘汰最近最久未修改的 |
| volatile-lrm | 有过期时间的 key | 同上 |
#### 5.2 惰性删除与定期删除
- **惰性删除**：访问 key 时检查过期时间，发现过期则视为不存在并触发清理；无人访问的过期数据可能继续占用内存
- **定期删除**：周期性主动检查一部分带过期时间的 key，清理过期数据，并限制每轮工作量，避免长时间影响请求

## 六、Redis 常见问题的处理策略
#### 6.1 大 Key
大 Key 指某个 key 的值体积过大，或集合元素过多，例如几十 MB 的字符串、包含百万字段的 Hash。没有统一的大小阈值，应按请求耗时、带宽与内存判断。
- **影响**：全量读写、遍历或同步释放可能增加延迟；大响应占用网络与缓冲区；单 key 落在一个分片，可能造成负载不均
- **处理**：按业务拆分，限制集合增长，使用 HSCAN、SSCAN、ZSCAN 等分批访问；大对象删除可考虑 UNLINK
- **排查**：`redis-cli --bigkeys` 按类型查找大对象，再用 `MEMORY USAGE key` 估算占用。集合的元素数量不等于内存字节数

#### 6.2 热 Key
热 Key 指短时间内被大量访问的 key，例如秒杀库存、热门新闻。数据本身可以很小，热点依然可能耗尽所在分片的 CPU 或网络能力。

| 类型 | 常见处理 | 代价或限制 |
|---|---|---|
| 读热点 | 应用本地缓存、只读副本分担读流量 | 缓存失效管理、复制延迟和旧值 |
| 写热点 | 按业务拆分，如分片计数后汇总 | 汇总成本与一致性；库存等强约束不能直接照搬 |
| 突发热点 | 限流；允许延迟时使用队列削峰 | 队列只能缓冲，不能解决长期吞吐不足 |
#### 6.3 缓存雪崩、击穿与穿透

| 问题 | 原因 | 常见处理 |
|---|---|---|
| 雪崩 | 大量缓存同时失效，或缓存服务不可用 | TTL 加随机值、分批刷新与预热、提高可用性、限制回源流量 |
| 击穿 | 某个热点缓存失效，大量请求同时回源 | 合并同 key 请求、互斥重建、提前刷新；允许时返回旧值 |
| 穿透 | 请求的数据在缓存和数据库中都不存在 | 参数校验、短 TTL 的空结果缓存、布隆过滤器、限流 |

#### 6.4 布隆过滤器（用于缓存穿透）
布隆过滤器通过**位数组 + 多个哈希函数**判断元素是否可能存在。
优点是省内存、查询快；缺点是有假阳性，不存原始元素，普通布隆过滤器不能直接通过清零删除元素。对**已正确加入且未被错误删除**的元素，不会产生假阴性。
用于防穿透时，只拦截确定不存在的数据；过滤器必须与新增数据协调更新，避免数据库已有数据却尚未加入过滤器

## 七、集群与扩缩容
#### 7.1 扩容场景与方式

| 场景    | 表现                | 常见应对方式                   |
| ----- | ----------------- | ------------------------ |
| 数据增长  | 内存接近限制，频繁淘汰仍有用的数据 | 增加单机内存或增加分片              |
| 读请求增长 | 读取延迟、CPU 或带宽压力增加  | 只读副本、本地缓存，或增加分片          |
| 写请求增长 | 主节点处理不过来          | 增加分片，将不同 key 的写入分散到多个主节点 |
| 活动高峰  | 预计峰值超过当前容量        | 提前压测并预留容量                |
**增加单机资源称为纵向扩容，增加分片或副本称为横向扩容**。副本保存相同分片的数据，主要扩展读能力和容灾能力，不增加可存储的独立数据量

扩容前应排除慢命令、大 Key、热 Key 等问题，并确认瓶颈确实能通过扩容缓解

#### 7.2 Redis 的扩容方式
| 方式         | 做法                           | 解决的问题          |
| ---------- | ---------------------------- | -------------- |
| **增加单机资源** | 升级内存等资源，并合理调整 `maxmemory`    | 单节点容量不足        |
| **增加读副本**  | 新增副本，客户端将部分读取路由到副本           | 读压力过大，需要接受复制延迟 |
| **增加集群分片** | Redis Cluster 新增主节点，迁移部分槽与数据 | 数据容量或整体读写能力不足  |
**槽是 Redis Cluster 给 key 划分的“逻辑分组”，不是一块固定大小的内存。** 16384 表示分组数量，不代表内存容量。可以分三步理解：
- ① 每个 key 先确定属于哪个槽
- ② 每个槽分配给某个主节点
- ③ 内存占用取决于槽里的实际数据
正常迁移成功后，旧节点不再负责迁出的槽，也不再保存这些槽对应的业务数据。槽本身仍存在于集群中，只是归属变成新节点

#### 7.3 Redis 的常见部署方式

| 名称                | 所属层面       | 核心作用                                                  |
| ----------------- | ---------- | ----------------------------------------------------- |
| **主从复制**          | 数据复制机制     | 主节点的数据复制到副本                                           |
| **Sentinel 哨兵**   | 高可用管理机制    | 监控普通主从部署，自动完成故障切换                                     |
| **Redis Cluster** | 数据分片与高可用架构 | 多个主节点分摊数据，各自主节点可以配置副本，<br>内置故障检测、副本选举和槽归属更新，不需要额外部署哨兵 |
| **读写分离代理**        | 请求接入层      | 接收应用请求，选择后端主节点或副本                                     |
常见组合包括：
- **主从复制 + 哨兵**：复制数据，并自动切换故障主节点。
- **主从复制 + 哨兵 + 代理**：再由代理负责请求路由。
- **Cluster + 代理**：Cluster 负责分片与故障切换，代理负责接入和路由，具体取决于代理能力。

**Cluster 本身也使用主从复制，但它内置故障检测与切换机制，通常不再让 Sentinel 管理同一组 Cluster 节点的故障切换。**
