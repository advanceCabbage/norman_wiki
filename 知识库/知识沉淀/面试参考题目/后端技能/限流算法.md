## 一、限流算法概念
限流用于控制请求进入系统的速度或同时执行的数量，避免系统或下游服务过载

## 二、常见限流算法

| 算法     | 实现方式                           | 优势                    | 劣势                         |
| ------ | ------------------------------ | --------------------- | -------------------------- |
| 固定窗口   | 保存窗口内的累计次数，窗口结束后整体重置           | 状态少，实现简单              | 窗口交界处可能短时间放行两批请求           |
| 滑动窗口日志 | 保存已放行请求的时间戳，每次统计最近一段时间内的记录     | 能精确限制任意滚动时间段内的请求数量    | 需要逐条保存、清理记录，内存与计算开销较高      |
| 滑动窗口计数 | 保存相邻时间窗口的计数，根据时间比例估算最近一段时间的数量  | 比逐条日志节省内存，缓解固定窗口的边界突增 | 属于近似统计，可能多放或少放请求           |
| 令牌桶    | 按固定速率补充令牌，请求消耗令牌，桶有容量上限        | 控制长期速率，同时允许受控突发       | 不能保证请求均匀到达下游；容量过大仍可能形成瞬时压力 |
| 漏桶     | 请求进入有限队列，按固定速率取出；或维护按时间衰减的虚拟水位 | 排队形式可以平滑下游流量          | 排队增加延迟，队列满时仍需拒绝；不同变体的行为不同  |
| 并发数限流  | 维护正在执行的请求数，开始时占用名额，结束时释放       | 直接限制资源同时占用量，适合耗时任务    | 不直接限制每秒请求数；异常退出需要可靠释放名额    |
| 自适应限流  | 根据延迟、错误、资源压力等反馈动态调整阈值          | 能随系统容量和下游状态变化进行调整     | 实现与调参复杂，反馈滞后可能引起震荡或误拒绝     |
## 三、多机全局限流方案

多机全局限流的核心是：**共享同一份额度，原子完成检查与扣减。**每台机器各自维护完整额度，会使总额度随机器数增加

| 实现方案        | 实现方式               | 优势              | 劣势                                               |
| ----------- | ------------------ | --------------- | ------------------------------------------------ |
| Redis + Lua | 共享计数或桶状态，脚本原子判断与更新 | 通常延迟低，支持多种算法    | 热点 Key 可能形成瓶颈；需要 Redis 运维；默认异步复制下故障切换可能丢失最近的扣减记录 |
| MySQL + 行锁  | 锁定共享额度行，在事务中判断并扣减  | 可与同库业务写入一起提交或回滚 | 热点行竞争、事务与日志开销较大，可能挤占业务数据库资源                      |
| 统一限流服务／网关   | 集中提供限流判断或在入口执行规则   | 便于统一配置、监控和治理    | 增加组件与公共依赖，多副本之间仍需协调额度                            |
