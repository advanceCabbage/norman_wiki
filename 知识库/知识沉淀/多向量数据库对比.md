# 三种向量数据库对比:SQLite(LibSQL) · PostgreSQL(pgvector) · Milvus

> 面向三个目标写:**懂差异、会选型、应对面试**。内容基于本项目实际接入并验证过三种后端(向量/关键字/混合/MMR 全部跑通)后的一手结论。

---

## 0. 一句话本质(整篇的锚)

|                           | 本质定位                         | 一句话                                       |
| ------------------------- | -------------------------------- | -------------------------------------------- |
| **SQLite / LibSQL**       | **嵌入式**数据库                 | 向量是"加在**单机文件库**上的能力"           |
| **PostgreSQL / pgvector** | **单机服务型关系库** + 向量扩展  | 向量是"加在**通用数据库**上的能力"           |
| **Milvus**                | **分布式、专为向量而生**的数据库 | 向量是**一等公民**,为海量/高并发向量检索设计 |

**后面所有差异都能从这一行推出来**:嵌入式 → 零运维但难扩展;通用库 → 事务/SQL 强但向量是"附加";专用库 → 向量能力最强但组件重、无事务。

---

| 依赖组件   | 无                       | PG 服务                                   | etcd + 对象存储 + (集群:消息队列) |
| 运维成本   | 极低                     | 中                                        | 高                                |
| 向量索引   | DiskANN 系 / 暴力        | HNSW / IVFFlat / 精确                     | HNSW/IVF/PQ/DiskANN/GPU(最全)     |

| 数据量级   | 万~百万                  | 百万~千万(单机)                           | 十亿级                            |
| 水平扩展   | ❌                       | 有限                                      | ✅(存算分离)                      |
| 高并发     | 单写者                   | 成熟 MVCC                                 | 为高 QPS 设计                     |
| 云托管     | Turso                    | Supabase / Neon                           | Zilliz Cloud                      |

## 2. 部署与运维

- **SQLite / LibSQL**:嵌入式,**没有服务进程**——打开一个文件(`file:data/vector.db`)即用,拷贝文件即备份/迁移。零运维,本地开发和边缘部署最省心。
- **PostgreSQL / pgvector**:是**客户端-服务器**,要先跑起 PG 服务,再 `CREATE EXTENSION vector`。运维是成熟 PG 那一套(`pg_dump` 备份、连接池、参数调优)。
- **Milvus**:**组件最重**。即使"单机版(Standalone)"内部也捆了 **etcd**(元数据)+ **MinIO/对象存储**(数据)+ Milvus 核心;集群版还要加**消息队列**(Pulsar/Kafka),并拆成 proxy / query node / data node / index node 等,**存算分离**。内存占用大(索引常驻内存)。运维成本最高。

> **一句话**:运维成本 SQLite ≪ PG < Milvus;换来的是扩展能力 SQLite ≪ PG < Milvus。

---

## 3. 向量检索:索引与排序

**索引本质**:向量检索快,靠的是 **ANN(近似最近邻)索引**——不全表逐个算距离,而是用图/聚类结构快速逼近。

|          | 索引算法                                              | 说明                           |
| -------- | ----------------------------------------------------- | ------------------------------ |
| LibSQL   | DiskANN 系(`libsql_vector_idx`)或暴力                 | 单机、够用                     |
| pgvector | **HNSW** / IVFFlat / 精确                             | HNSW 最常用                    |
| Milvus   | HNSW / IVF_FLAT / IVF_PQ / DiskANN / **GPU** / SCANN… | 最全,可量化压缩(PQ/SQ)、可 GPU |

**排序**:向量检索的"排序"就是**按与 query 向量的距离/相似度排**(ANN 索引直接返回近邻并带分数)。三者都支持余弦。

⚠️ **分数语义坑(本项目实测)**:同样是"余弦",

- LibSQL、pgvector 返回的是**余弦距离**(越小越相似);
- Milvus 的 COSINE 返回的是**余弦相似度**(越大越相似)。

所以做统一封装时必须按后端把分数归一(本项目在 `toVectorResult` 里对 Milvus 用 `score=原始分`、对另两个用 `score=1-距离`)。**这是"向量库接口能统一、但分数语义各家不同"的典型。**

---

## 4. 关键字检索:索引与排序

三者都是**倒排索引**,但"索引单元"和"排序算法"差别很大:

|                   | 索引结构 / 单元                                    | 排序算法                                        | 中文                    |
| ----------------- | -------------------------------------------------- | ----------------------------------------------- | ----------------------- |
| LibSQL(FTS5)      | 虚拟表 + **字符三元组**倒排                        | **真 BM25**(`bm25()`,但作用在三元组上)          | 子串匹配,query 需 ≥3 字 |
| pgvector(pg_trgm) | **GIN + 字符三元组**倒排                           | `word_similarity`(三元组重叠,**非 BM25**)       | 子串匹配,2 字也行       |
| Milvus(2.5+)      | **词级**(jieba)+ 稀疏倒排(`SPARSE_INVERTED_INDEX`) | **真 BM25**(TF+IDF+文档长度归一,作用在**词**上) | **词级分词,最好**       |

关键区别:

1. **索引单元**:PG/SQLite 是**字符三元组**(trigram,3 字符一组,中文哈希存),Milvus 是**词**(jieba 分词)。
2. **排序算法**:FTS5 和 Milvus **都是真 BM25**(同一套 TF/IDF/文档长度归一公式),区别在**作用单元**——FTS5 是 BM25 over **字符三元组**,Milvus 是 BM25 over **词**(词级的 IDF/TF 更有语义,排序更准)。真正**不是 BM25** 的是 **pg_trgm 的 `word_similarity`**(只是三元组重叠度,不看 TF/IDF/长度)。
3. **筛选与排序的关系**:PG 是"GIN 索引筛选 + `word_similarity` 另算排序"两步;Milvus 是"稀疏索引搜索一步出 BM25 分"。

⚠️ **pg_trgm 中文排序短板(实测)**:`word_similarity('部署','本地部署Milvus')=0`——词夹在中间、无空格边界时会算成 0 分。即 `ILIKE` **筛得到**、`word_similarity` **排不准**。中文关键字排序质量:**Milvus(BM25 词级) > FTS5 ≳ pg_trgm**。

> 补充:PG **本身**也有真全文检索(`tsvector`+`ts_rank`,接近 BM25),但默认不分中文,要装 `zhparser`/`pg_jieba` 扩展。本项目为"零扩展开箱即用"才选了 pg_trgm——**这一半是能力差异,一半是选型取舍**。

## 5. 混合检索(Hybrid)

把"向量(懂语义)+ 关键字(对得上词)"两路结果融合,是 RAG 提升召回的关键。

|                   | 混合检索方式                                                             |
| ----------------- | ------------------------------------------------------------------------ |
| LibSQL / pgvector | **无原生**,需**应用层融合**(本项目手写 RRF)                              |
| Milvus            | **原生** `hybrid_search` + `RRFRanker`(k=60)/`WeightedRanker`,服务端融合 |

**RRF(倒数排名融合)**:`分数 = Σ 权重/(c+名次)`,c 默认 60。**只看名次不看原始分**,天然回避"余弦距离 vs BM25"量纲不可比的问题。有趣的是 LangChain 的 `EnsembleRetriever`、Milvus 的 `RRFRanker`、我们手写的都用 c=60。

> 本项目为统一,三个后端的 hybrid 都走**我们自己的 RRF**(稠密 store + 关键字索引两路),没用 Milvus 的服务端 hybrid,保持四种模式在三后端行为一致。

## 6. 元数据过滤 & 关系能力(选型关键,常被忽略)

RAG 里经常要"按来源/时间/权限过滤后再检索"。

- **SQLite / PostgreSQL**:标量过滤就是**任意 SQL `WHERE`**,还能 **JOIN 业务表、跑事务**。PG 尤其强:**一份数据既做业务又做向量**,向量检索和关系查询/事务无缝结合——数据不用搬去第二个系统。
- **Milvus**:支持**标量字段过滤**(布尔表达式),但表达能力**远不如 SQL**,不能联表、无跨行事务。它专注向量,不承担通用数据库职责。

> 这条常是决定性的:**如果你的过滤逻辑复杂、或想避免"业务库 + 向量库"两套数据同步**,PG(pgvector)往往比 Milvus 更合适。

---

## 7. 规模 · 并发 · 一致性

|               | 数据量级                 | 水平扩展              | 并发模型              | 事务/一致性                   | 实时可见性                  |
| ------------- | ------------------------ | --------------------- | --------------------- | ----------------------------- | --------------------------- |
| SQLite/LibSQL | 万~百万                  | ❌                    | **单写者**、多读(WAL) | 强 ACID                       | 写入即可见                  |
| pgvector      | 百万~千万(单机,内存受限) | 有限(读副本/分片难)   | 成熟 MVCC,并发好      | 强 ACID                       | 写入即可见                  |
| Milvus        | **十亿级**               | ✅ 存算分离、水平扩展 | 为**高 QPS** 设计     | **无跨行事务**,一致性**可调** | **需 flush/合适一致性级别** |

- **Milvus 可调一致性**:`Strong / Bounded / Session / Eventually`——用一致性换吞吐。本项目 BM25 检索用了 `Strong`。
- ⚠️ **Milvus 实时性坑(实测)**:BM25 插入后**必须 `flush`**,新数据才可被搜到(第一次没 flush 全返回空)。这是"批式/最终一致"系统的典型特征,和 SQLite/PG"写完立刻可查"不同。
- **隔离/多租户**:PG(database/schema/行级安全 RLS)、Milvus(database/collection/**partition** + partition key)、SQLite(靠**多文件**物理隔离)。

## 8. 生态与集成(工程视角)

- **LangChain.js**:三者都有 VectorStore(`LibSQLVectorStore` / `PGVectorStore` / `Milvus`)。但实测两个坑:
  - **Milvus 的 BM25/hybrid 没被 LangChain 暴露**——要用就得直连 `@zilliz/milvus2-sdk-node` 手写(本项目就是这么做的)。
  - `@langchain/community` 已被官方 **sunset**(仍能用,不再更新);且 **没有 `sqlite-vec` 的 JS 集成**,"SQLite"实际用的是 **LibSQL**。
- **云托管**:Turso(LibSQL)、Supabase/Neon(PG)、Zilliz Cloud(Milvus)。

## 9. 决策矩阵:什么场景选谁

| 场景                                         | 首选                | 理由                            |
| -------------------------------------------- | ------------------- | ------------------------------- |
| 原型 / 学习 / 边缘 / 桌面 / 单机小数据       | **SQLite / LibSQL** | 零运维、单文件、够快            |
| 已有 PostgreSQL 技术栈                       | **pgvector**        | 复用运维经验,不引新系统         |
| 中小规模 + 需要**事务/复杂 SQL 过滤 + 向量** | **pgvector**        | 一份数据既业务又向量,强一致     |
| 不想维护"业务库 + 向量库"两套                | **pgvector**        | 向量并入现有 PG                 |
| 大规模(千万~十亿)/ 高并发 QPS                | **Milvus**          | 分布式、水平扩展                |
| 需要多种索引 / 量化压缩 / GPU 加速           | **Milvus**          | 索引最全、性能天花板高          |
| 强中文全文/混合检索、追求排序质量            | **Milvus**          | 原生 BM25 + jieba + 原生 hybrid |

**一句话**:**小而省 → SQLite;稳而全能、和业务同库 → PostgreSQL;大而专、极致向量 → Milvus。**

## 10. 实战踩坑清单(本项目一手,面试加分)

1. **分数语义反向**:Milvus COSINE 返相似度(大=近),LibSQL/pgvector 返距离(小=近)→ 统一层要归一。
2. **Milvus BM25 要 flush**:插入后不 flush,新数据搜不到。
3. **pg_trgm 中文排序弱**:`word_similarity` 对中间位置的词算 0 分(ILIKE 命中但排不准)。
4. **FTS5 trigram 需 ≥3 字**:2 字查询搜不到;pg_trgm、Milvus 都能处理 2 字。
5. **PG `createHnswIndex` 索引名写死**(不含表名)→ 同 schema 只能建一个,第二个被 `IF NOT EXISTS` 静默跳过。
6. **建表方式不同**:LibSQL 要手写 DDL;pgvector `initialize` 自动建;Milvus 首次入库按 metadata 自动建集合/字段/索引。
7. **LangChain 不暴露 Milvus BM25/hybrid**、`@langchain/community` 已 sunset、无 JS 版 `sqlite-vec`。
8. **换库要对齐列名/字段名**(本项目把 PG 内容列从默认 `text` 改回 `content` 对齐 LibSQL)。

## 11. 面试考点速记

- **HNSW**:分层可导航小世界图,上层稀疏做粗导航、下层稠密做精搜,贪心跳邻居;参数 `M`(每点连边数)、`efConstruction`(建图质量)、`efSearch`(查询召回↔速度)。
- **IVF**:先 k-means 聚成 `nlist` 个簇 + 倒排;查询只搜最近 `nprobe` 个簇 → 召回↔速度权衡。
- **量化**:PQ(乘积量化)/SQ(标量量化)压缩向量,省内存、损精度。
- **ANN vs 精确**:近似换速度,核心指标是**召回率 ↔ QPS/延迟**。
- **BM25**:`Σ IDF(t)·[tf·(k1+1)] / [tf + k1·(1-b+b·|d|/avgdl)]`——词频 TF↑、逆文档频率 IDF↑(词越稀有越重要)、长文档被 `|d|/avgdl` 惩罚。
- **稠密 vs 稀疏向量**:稠密=embedding(语义);稀疏=BM25/词权重(字面)。
- **倒排索引 vs 向量索引**:倒排(词→文档)服务关键字;向量索引(图/簇)服务语义。
- **RRF**:`Σ 1/(c+rank)`,c=60,只用名次、跨量纲融合。
- **为什么 Milvus 要 load**:索引要**加载进内存**才能低延迟检索;数据分 growing/sealed 段,涉及 flush 与一致性级别。
- **一致性级别**:Strong/Bounded/Session/Eventually——一致性换吞吐。
