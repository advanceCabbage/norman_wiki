# LangGraph:工作流(Workflows)与智能体(Agents)

> 原文:https://docs.langchain.com/oss/python/langgraph/workflows-agents
> 本笔记为精简版:概念为主,每个模式仅保留极简伪代码示意数据流。

---

## 一、核心区别

|          | Workflow(工作流)        | Agent(智能体)                |
| -------- | ----------------------- | ---------------------------- |
| 控制流   | **预定义**,代码路径固定 | **动态**,LLM 自行决定下一步  |
| 顺序     | 按设计好的顺序执行      | 运行时自主规划流程与工具调用 |
| 可预测性 | 高,行为可控             | 低,能处理开放/未知问题       |
| 适用     | 步骤已知、可拆解的任务  | 步骤不定、需自主决策的任务   |

一句话:**工作流是"你替 LLM 把路铺好",智能体是"LLM 自己找路"。**

> LangGraph 在两者之上统一提供:持久化(persistence)、流式输出(streaming)、调试、部署。

---

## 二、构建块:LLM 的三种增强

在拼装工作流/智能体之前,单个 LLM 通常先被增强:

1. **工具调用(tool calling)** —— 让 LLM 能调用外部函数/API。
2. **结构化输出(structured output)** —— 用 schema(如 Pydantic)约束返回格式。
3. **短期记忆(memory)** —— 在多步之间保留上下文。

```text
llm_with_tools = llm.bind_tools([...])          # 工具
llm.with_structured_output(Schema)              # 结构化输出
```

## 三、工作流的 5 种经典模式

### 1. Prompt Chaining(提示链)—— 串行

把任务拆成**固定的几步**,每步的输出喂给下一步;可在中间插入检查(gate)提前退出。

- **适用**:任务能被清晰拆成有序子步骤。例:先翻译文档 → 再校验译文一致性。

```text
输入 → LLM_1 → [检查?通过] → LLM_2 → LLM_3 → 输出
                 └[不通过]→ 结束
```

### 2. Parallelization(并行化)—— 分头跑再汇总

多个**互相独立**的子任务同时执行,最后聚合。

- **适用**:① 子任务可并行以**提速**;② 对同一问题多次采样以**提升可信度**。例:同时生成"笑话/故事/诗",或让多个 LLM 各自评审再投票。

```text
        ┌→ LLM_A ┐
输入 ───┼→ LLM_B ┼→ 聚合(aggregator) → 输出
        └→ LLM_C ┘
```

### 3. Routing(路由)—— 先分类再分流

先用一个 LLM 判断输入类型,再**导向专门的处理流程**。

- **适用**:输入种类明确、各类处理方式不同。例:客服请求分流到 定价 / 退款 / 退货。

```text
输入 → Router(分类) ──→ 流程_定价
                    ├─→ 流程_退款
                    └─→ 流程_退货
```

### 4. Orchestrator–Worker(编排者–工作者)—— 动态拆分

编排者(orchestrator)把大任务**动态**拆成若干子任务,分派给多个 worker 执行,再综合结果。与并行化的区别:**子任务数量/内容运行时才确定**。

- **适用**:子任务数目事先未知。例:要更新"若干个(数量不定)文档"里的安装说明。

```text
输入 → Orchestrator(动态拆分)
          ├→ Worker_1 ┐
          ├→ Worker_2 ┼→ Synthesizer(综合) → 输出
          └→ Worker_n ┘
```

> LangGraph 中用 `Send` API 动态生成 worker。

### 5. Evaluator–Optimizer(评估–优化)—— 生成后自我打磨

一个 LLM 生成结果,另一个 LLM 评估并给反馈,**循环**直到达标。

- **适用**:有明确评价标准、需要迭代提升质量。例:反复翻译直到译文质量过关。

```text
输入 → Generator → Evaluator ─[不通过:带反馈]→ Generator(重来)
                        └────[通过]────────────→ 输出
```

## 四、Agents(智能体)

智能体是 LLM 在 **"思考 → 调用工具 → 观察结果 → 再思考"** 的循环中自主行动,直到认为任务完成。核心在于:**每一步做什么由 LLM 自己决定**,而非预先写死。

- **适用**:问题与解法都不可预测,需要开放式自主决策。例:根据用户需求自行选择并组合工具(加/减/乘/除…)完成计算或多步任务。

```text
        ┌─────────────────────────┐
输入 → LLM_call → [要用工具?] ─是→ 执行工具 ─┘   (把结果回灌 LLM)
                      └─否→ 输出
```

### 子节:ToolNode

LangGraph 内置的工具执行节点,开箱即用地提供:

- **并行执行**多个工具调用
- **错误处理**
- **状态注入**(工具可通过 `ToolRuntime` 读取图的 state / 上下文)

## 五、Graph API vs Functional API

原文每个模式都给了**两套实现**,二者能力等价,只是风格不同:

- **Graph API**:显式声明 节点(node)+ 边(edge),把流程画成一张图。结构清晰、可视化好。
- **Functional API**:用 `@task` / `@entrypoint` 装饰器,以近似普通函数的写法组织流程。代码更轻。

选型:流程复杂、想要可视化和精细控制 → Graph API;流程简单、想快写 → Functional API。

### 实操示例:一段代码看懂「节点 / 边 / 条件边 / 执行链路」

以 Prompt Chaining(生成笑话)为例,这是 LangGraph 图机制最小而完整的样本——不掺入工具绑定和 Agent 循环,便于聚焦图本身。

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END

# ① State:全图共享的数据结构。每个节点读它、返回增量来更新它
class State(TypedDict):
    topic: str
    joke: str
    improved_joke: str
    final_joke: str

# ② 节点(Node):就是普通函数,入参是 state,返回要更新的字段
def generate_joke(state: State):
    msg = llm.invoke(f"Write a short joke about {state['topic']}")
    return {"joke": msg.content}

# ③ 门控函数:不返回 state,而是返回一个"路由标签"(Pass/Fail)
def check_punchline(state: State):
    if "?" in state["joke"] or "!" in state["joke"]:
        return "Pass"
    return "Fail"

def improve_joke(state: State):
    msg = llm.invoke(f"Make this joke funnier by adding wordplay: {state['joke']}")
    return {"improved_joke": msg.content}

def polish_joke(state: State):
    msg = llm.invoke(f"Add a surprising twist to this joke: {state['improved_joke']}")
    return {"final_joke": msg.content}

# ④ 建图
workflow = StateGraph(State)

# 注册节点
workflow.add_node("generate_joke", generate_joke)
workflow.add_node("improve_joke", improve_joke)
workflow.add_node("polish_joke", polish_joke)

# 普通边(固定跳转)
workflow.add_edge(START, "generate_joke")
# 条件边:执行 check_punchline,按其返回值查表决定去哪个节点
workflow.add_conditional_edges(
    "generate_joke", check_punchline, {"Fail": "improve_joke", "Pass": END}
)
workflow.add_edge("improve_joke", "polish_joke")
workflow.add_edge("polish_joke", END)

# ⑤ 编译成可执行链,然后像函数一样 invoke
chain = workflow.compile()
state = chain.invoke({"topic": "cats"})
```

**这段代码覆盖的图概念:**

| 概念             | 对应写法                                            |
| ---------------- | --------------------------------------------------- |
| 节点             | `add_node("名字", 函数)` —— 三个函数即三个节点      |
| 普通边(固定跳转) | `add_edge(A, B)` —— START→…→END 的线性链路          |
| 条件边(动态分流) | `add_conditional_edges(源, 门控函数, {标签: 目标})` |
| 共享 State       | `TypedDict`,节点返回增量字段来更新                  |
| 编译 + 执行      | `compile()` → `invoke(初始state)`                   |

**执行链路:** `START → generate_joke →`(有笑点?)`→ Pass 直接 END` / `Fail → improve_joke → polish_joke → END`。

> 进阶提示:只要把某条边**指回前面的节点**,就得到了「回环边(cycle)」——这正是 Evaluator-optimizer 和 Agent 里"反复迭代/工具循环"的实现方式。

## 六、一页速记

- **工作流 = 固定路径**;**智能体 = 动态自主**。
- 工作流 5 模式记忆法:
  - **串**(Prompt Chaining)
  - **并**(Parallelization)
  - **分**(Routing)
  - **拆**(Orchestrator–Worker)
  - **评**(Evaluator–Optimizer)
- 分不清用工作流还是智能体?**先问:步骤能否事先确定?** 能→工作流;不能→智能体。
