## 一、KV Cache 产生的背景
LLM 的自注意力机制需要将用户的输入拆分为 Q（查询内容）、K（键代表有什么标签）、V（值代表实际内容）。并且每次都需要重新计算自身与其他位置 Token 的相关程度

## 二、KV Cache 的步骤
KV Cache 的核心思路一句话：**把前面所有 token 的 K 和 V 矩阵缓存起来，每次新 token 只算自己的部分**。

**详细步骤**
- 新 Token 只是一个 Q（它在「问」前面所有 token）
- 它做点积的对象 K 和加权求和的对象 V，**都来自前面所有 token**
- 但前面所有 token 的 K 和 V 是固定的，不会随新 Token 而变
- 所以**前面所有 token 的 K 和 V 完全可以缓存**，每次只算新 token 自己的 Q、K、V，然后跟缓存的 K/V 拼起来做 attention
## 三、KV Cache 和 Prompt Cache：同一机制的扩展

- **KV Cache** 是「**单次推理内**」的优化
- **Prompt Cache** 是「**跨请求**」的优化。复用 KV Cache 逻辑，将「单次推理内」扩展到「不同请求之间」。如果两个请求Prompt 前缀完全相同，第一个请求算完的 KV Cache 在 API 服务器上保留下来，第二个请求遇到相同前缀直接跳过计算、复用 KV Cache，只计算新增部分

## 四、主流 API Prompt Cache
#### 4.1 Claude ：显示标记缓存断点

由用户在调用 API 时，通过 `cache_control` 标记期望被缓存的内容，建立缓存约有 1.25 X 倍的写入费用

#### 4.2 OpenAI 自动缓存

只要请求中的 Prompt 前缀超过一定长度（1024 Token），系统会自动尝试缓存。命中时不需要额外操作，API 响应里会说明有多少 Token 命中了缓存

## 五、常见缓存工程陷阱

- 前缀必须字符级一致，才能命中缓存
- 缓存时效性，Claude 默认 5 分钟缓存有效，假设低流量应用（几小时一次请求）会频繁失效，反而构建缓存导致成本更高
