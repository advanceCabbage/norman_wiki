
## 一、uv 对比 npm 学习

| npm / Node.js       | uv / Python       | 作用              |
| ------------------- | ----------------- | --------------- |
| `package.json`      | `pyproject.toml`  | 项目元信息、依赖声明、工具配置 |
| `package-lock.json` | `uv.lock`         | 锁定依赖的具体版本       |
| `node_modules/`     | `.venv/`          | 项目依赖所在的位置，但结构不同 |
| `engines.node`      | `requires-python` | 声明支持的运行时版本      |
| `.nvmrc`            | `.python-version` | 指定开发时使用的运行时版本   |
## 二、常用命令对比
| 目的          | npm                     | uv                  |
| ----------- | ----------------------- | ------------------- |
| 初始化项目       | `npm init -y`           | `uv init`           |
| 安装项目依赖      | `npm install`           | `uv sync`           |
| 严格按锁文件安装    | `npm ci`                | `uv sync --locked`  |
| 添加正式依赖      | `npm install axios`     | `uv add httpx`      |
| 添加开发依赖      | `npm install -D eslint` | `uv add --dev ruff` |
| 删除依赖        | `npm uninstall axios`   | `uv remove httpx`   |
| 查看依赖树       | `npm ls`                | `uv tree`           |
| 临时运行工具      | `npx …`                 | `uvx …`             |
| 安装长期使用的 CLI | `npm install -g …`      | `uv tool install …` |
| 运行程序        | `npm run dev`           | `uv run main.py`    |
`uv sync`  与 ` uv sync --locked` 关键差异在于：**依赖声明与锁文件不一致时，是否允许自动更新锁文件**
举例：
```
pyproject.toml：      axios 要求 ^1.7.0
uv.lock： 			  axios 仍锁定 1.6.2
```
使用 `uv sync` 则会正常安装并更新 uv.lock；使用 ` uv sync --locked` 则验证匹配校验，不允许安装并报错；**uv sync 会默认安装 `[dependency-groups]` 中的 `dev` 组，但不会自动安装所有组**，可选 `[project.optional-dependencies]` 不会默认安装

`uv run XXX` 会自动激活虚拟环境即.venv 文件无需单独激活

## 三、pyproject.toml 文件配置介绍--基础

##### 3.1 `[project]` ：项目元信息和运行依赖

```toml
[project]
name = "my-app" 
version = "0.1.0" 
description = "An example Python application." // 项目介绍
readme = "README.md"
requires-python = ">=3.10"
authors = [{ name = "Example Team", email = "team@example.com" }]
maintainers = [{ name = "Maintainer" }]
keywords = ["agent", "chatbot"]
classifiers = [
    "Programming Language :: Python :: 3",
]
dependencies = [
    "httpx>=0.27,<1",
]
```

| 字段                | 含义                       |
| ----------------- | ------------------------ |
| `name`            | 发行包名称，打包、安装、卸载都是使用的该名称   |
| `version`         | 项目版本，安装包时用于指定安装特定版本      |
| `description`     | 项目简介                     |
| `readme`          | 项目详细介绍的文件或文本             |
| `requires-python` | 支持的 Python 版本范围          |
| `authors`         | 作者列表，条目支持 `name`、`email` |
| `maintainers`     | 维护者列表                    |
| `keywords`        | 搜索关键词                    |
| `classifiers`     | Python 包索引使用的标准分类标签      |
| `dependencies`    | 运行依赖及版本条件                |

##### 3.2 `[project.optional-dependencies]`：可选功能依赖

```toml
[project.optional-dependencies]
excel = ["openpyxl>=3.1"]
postgres = ["psycopg[binary]>=3"
```
使用 `uv sync` 不会自动安装可选依赖，当我用到可选依赖时就会出现报错；因此可选依赖的设计需要分清楚使用情况

##### 3.3 `[dependency-groups]` 仅在开发阶段所需安装的依赖

```toml
[dependency-groups]
test = ["pytest>=7.4"]
lint = ["ruff"]
docs = ["mkdocs"]

dev = [
    { include-group = "test" },
    { include-group = "lint" },
]
```

##### 3.4 `[build-system]` 构建工具和接口

```toml
[build-system]
requires = ["setuptools>=64", "wheel"]
build-backend = "setuptools.build_meta"
```

| 字段              | 含义                     |
| --------------- | ---------------------- |
| `requires`      | 构建后端运行所需的 Python 包     |
| `build-backend` | 构建后端的模块或对象引用           |
| `backend-path`  | 项目内自定义构建后端所在的相对目录，高级用法 |

##### 3.5 `[tool.setuptools]` setuptools 打包规则


```toml
[tool.setuptools]
packages = ["app", "app.services"]
py-modules = ["helper"]
include-package-data = true
```

只有选用了 setuptools 构建后端，这部分才有相应作用。

| 字段                     | 作用                          |
| ---------------------- | --------------------------- |
| `packages`             | 显式列出要包含的 Python 包           |
| `py-modules`           | 列出独立 Python 模块，不包含 `.py` 后缀 |
| `package-dir`          | 指定包与源码目录的映射                 |
| `include-package-data` | 是否纳入按相关规则发现的包内资源文件          |
| `ext-modules`          | 声明 C/C++ 等扩展模块，属于高级构建配置     |

##### 3.6 `[project-scripts]` 声明命令用于执行 python 入口

```toml
[project]
name = "my-demo"
version = "0.1.0"

[project.scripts]
my-demo = "demo.cli:main"
```

并且配置了构建后端、能正常安装项目，那么在项目根目录执行
```
uv run my-demo
```



## 四、打包构建特别篇
> 之前没有接触过打包构建这块，因此先建立一个初步的印象

**两种产物的区别**

| 产物                | 用途                  | 内容特点               |
| ----------------- | ------------------- | ------------------ |
| `.whl`            | 直接安装到 Python 环境     | Python 代码、资源、安装元数据 |
| `.tar.gz`，即 sdist | 分发源码、供重新构建、不会压缩合并源码 | 可额外包含测试、文档、构建配置    |

**打包源码如何被收集**，当 `packages = ["app"]` 时
- `packages = ["app"]` 会收集 `app/__init__.py` 和 `app` 下直接的 Python 模块
- 不会自动递归包含 `app.services`、`app.ui` 等子包
- 不会从 `__init__.py` 出发追踪 `import`；被引用的文件不会因此自动加入
- 提示词 `.txt` 等非 Python 资源，需要另外核对资源打包规则

**打包成功不代表运行成功**
- 构建过程不保证所有运行需要的文件都已包含
- 缺少内部模块时，运行到相关导入通常会报 `ModuleNotFoundError`
- 从源码目录运行可能掩盖遗漏；验证安装包应在脱离源码目录的干净环境中进行

**验证打包后文件可运行的可靠方法**：最快且可靠的方法：新建干净环境 → 安装 wheel → 脱离源码检查导入 → 执行一个真实功能
