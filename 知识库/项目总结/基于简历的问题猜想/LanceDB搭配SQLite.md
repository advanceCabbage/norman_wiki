
## 一、背景介绍
Continue 在向量检索和全文检索方面同时使用了 SQLite 和 LanceDB。SQLite 和 LanceDB 均能独立实现向量检索和全文检索，因此本文需要讨论 SQLite 和 LanceDB 搭配使用的优势

## 二、SQLite 和 LanceDB 同时使用的优势

#### 1.**使用各自更成熟的专用能力**
LanceDB 直接提供向量索引和近邻搜索，SQLite 直接提供事务、关系表和 FTS 5。组合方案减少自研和验证成本。
####  2.在保留现有 SQLite 索引系统的基础上增加向量能力
Continue 的文件目录、Chunk、FTS、符号和增量状态已经建立在 SQLite 上。引入 LanceDB 只需增加向量搜索层，不必把整个索引系统迁移到新数据库。

#### 3.向量索引与文本索引可以独立重建
Embedding 模型或向量维度变化时，可以重建 LanceDB，而保留 SQLite 中的 FTS、Chunk、符号和索引状态。反过来，FTS 出现问题时，也不必重新计算 embedding。

#### 4. 隔离两类差异明显的工作负载
- LanceDB 处理高维向量写入、距离计算和 Top-K 搜索；
- SQLite 处理事务、小规模更新、关系查询和 BM 25
分离后，两类索引不会被迫共享同一种存储结构和优化方式。

#### 5.降低 SQLite 向量扩展的集成风险
单 SQLite 方案需要引入向量扩展，并处理原生二进制、ABI、Electron/Node.js、操作系统和 CPU 架构兼容问题。LanceDB 提供了现成的向量能力。


**面试回答**：内容寻址、跨分支复用和分支隔离都可以在单数据库中实现，因此它们不是双数据库独有优势。Continue 组合 SQLite 和 LanceDB 的核心价值，是在保留成熟 SQLite 索引系统的同时引入专业向量引擎，使文本索引与向量索引能够独立演进、独立重建，并避免自行维护 SQLite 向量扩展

## 三、仅使用一个数据库如何实现
#### 3.1 如果只使用 LanceDB
技术上可行，但需要解决：
- **用 LanceDB 重写 FTS 5/BM 25 查询；**
- 重写文件哈希、增量索引目录和 branch tag 管理；
- 重写代码符号、Chunk 关系和迁移逻辑；
- 跨分支复用向量时，需要建立全局缓存表；
- LanceDB 不可用时，全文检索和索引管理也一起失效；
- **原本适合关系数据库的数据被迫放入向量数据库。**
核心问题不是 LanceDB 做不到，而是大量关系型控制逻辑并不是它最自然的使用场景
#### 3.2 如果只使用 SQLite + Vector 扩展
这同样可行，而且对中小型仓库可能更简单，优势是：
- 单数据库；
- 单事务边界；
- 不需要 UUID 跨库回表；
- 避免向量和原文重复存储；
- 备份、迁移和一致性管理更简单。

但需要承担：
- SQLite 向量扩展的跨平台分发；
- **向量索引性能和内存验证；**
- **大规模向量数据下的性能风险；**
- embedding 维度或模型变化后的 schema/index 管理；
- 原生扩展兼容性维护
