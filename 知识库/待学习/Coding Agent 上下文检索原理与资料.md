# Coding Agent 上下文检索原理与资料

调研日期：2026-09-06。用途：TRAE / AI 编辑器面试准备，连接「API 文档与代码一致性智能检测工具」的项目经验。

本文先记录第一方资料能直接支持的结论，再给出面试中的设计推论。公开产品文档用于说明方法，不代表 TRAE 的内部架构；当前文档也不能证明项目实施时使用的 Serena 版本具备同样的工具。

## 1. 先分清“找候选”和“取得事实”

**来源事实：** Sourcegraph 官方把导航分为两类：Search-based 使用文本搜索和语法层面的启发式；Precise 使用编译期信息。后者需要生成、上传对应语言的 SCIP 索引，没有精确索引时可回退到搜索。由此可见，搜索命中和语义解析结果并不等价。[Code Navigation](https://sourcegraph.com/docs/code-navigation)、[Precise Code Navigation](https://sourcegraph.com/docs/code-navigation/precise-code-navigation)

**设计推论：** 上下文获取最好分成两个动作：先确定可能相关的文件或符号，再读取足以支持当前决策的原始代码及相关证据。自然语言相似、文件名匹配、结构图的重要性都可以帮助找入口，但不能单独证明默认值、实际分支条件或调用副作用。

以下是面试设计建议，不是某个产品的固定管线：

| 手段 | 适合回答的问题 | 需要注意的边界 |
|---|---|---|
| 文件名、目录、精确文本、正则 | 已知符号、错误字符串、配置 key、路由、注册表在哪里？ | 同名命中不一定是同一个符号；搜索词也可能遗漏别名 |
| 向量检索 | 不知道实现名，如何从“登录后刷新凭证”这样的意图找到候选模块？ | 相似度不等于调用关系，更不等于行为正确；需回读源码验证 |
| 语法树 / 结构提取 | 函数、类的边界在哪里？如何形成符号概览、结构化切块？ | 仅有语法结构不能保证跨文件名称解析或类型推断 |
| 语言服务器 / 编译器语义 | 这个位置的符号定义、引用、实现是什么？ | 依赖语言支持、构建配置和文档同步；静态结果不能覆盖所有动态行为 |
| Repo map | 一个陌生仓库有哪些关键模块和接口，下一步该读哪里？ | 是导航材料；具体修改或行为判断仍可能需要完整函数体 |
| 原文、配置、测试、运行结果 | 真实实现与约束是什么，变更如何验证？ | 要保留来源和版本；运行结果只证明实际覆盖的场景 |

这里的“语义”有两种不同含义：embedding 的语义偏向意图或内容相似；编译器的语义偏向符号绑定、类型和语言规则。两者可以配合，不能混称成同一种精确性。

## 2. LSP、语法树与 Serena 的层次

**来源事实：** VS Code 官方说明，LSP 将编辑器客户端与独立的语言服务器连接起来；语言服务器可以提供补全、引用查找和定义跳转。LSP 是通信接口，具体语言功能由服务器实现。[Language Server Extension Guide](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide)

**来源事实：** Tree-sitter 官方称其为增量解析库，生成的是 concrete syntax tree（具体语法树），能够在编辑时增量更新，也力求在存在语法错误时提供可用结构。不要把 Tree-sitter 本身说成完整编译器或类型检查器。[Tree-sitter Introduction](https://tree-sitter.github.io/tree-sitter/)

**来源事实：** Serena 的 LSP 后端接入各语言服务器，并提供符号查询、概览及引用工具。当前能力表也明确列出限制：LSP 后端的 declaration 查询通常不适用于外部依赖，implementation 查询只对部分语言可用。Serena 还提供文本搜索和读文件能力，并非只允许符号检索。[Serena Features](https://oraios.github.io/serena/01-about/025_features.html)

**来源事实：** LSP 的 `textDocument/definition` 响应允许 `Location`、`Location[]`、`LocationLink[]` 或 `null`。协议本身没有保证只能返回一个定义位置。[LSP 3.17 definition 规范源码](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/language/definition.md)

**面试中的准确表达：**

> 我利用 Serena 接入语言服务器提供的符号导航能力，降低纯文本检索的同名歧义，并按符号边界获取上下文。但导航返回的是静态分析结果，实际行为仍要结合实现、调用路径、配置及测试判断；对于动态注册、字符串路由或能力不支持的情况，我会补充文本检索与源码阅读。

不要说“LSP 找到唯一权威定义，因此默认值和错误码就一定找全”。例如默认值可能在入口之外的参数解析层赋值，错误码可能在被调用函数生成，再由桥接层改写。这里描述的是应如何调查的示例，不是对 MSI 实际实现的断言。

## 3. Repo map 是结构导航，不能替代所有代码

**来源事实：** Aider 的 repo map 展示文件及重要类、函数、签名和关键代码行；系统用文件依赖图上的排序挑选内容，并在 token 预算中动态决定展示范围。如果模型还需要实现细节，可据此确定应进一步查看的文件。[Aider Repository map](https://aider.chat/docs/repomap.html)

**来源事实：** Aider 的 2023 年技术文章介绍用 Tree-sitter 提取定义与引用以构建 map。这说明它如何获取结构，但不能据此声称所有图边都经过完整类型分析，或者把旧文章中的交互行为当作所有现行版本的行为。[Building a better repository map with tree sitter](https://aider.chat/2023/10/22/repomap.html)

**设计推论：** 对陌生仓库，先传小型结构概览有助于模型选择阅读方向；对“修改某函数的边界条件”，应该加载完整相关分支和所需依赖，而不是只给函数签名。对于巨大函数，再按问题定位控制流片段，并确保没有截掉决定语义的前置条件。

## 4. 编辑器上下文有版本，磁盘不是唯一来源

**来源事实：** VS Code `TextDocument` 有 `isDirty`、`version` 和 `getText()`；`isDirty` 表示有未持久化改动，`version` 在每次改变后递增，包括撤销和重做。VS Code 还暴露当前文档集合、工作区文件夹与文档改变事件。[VS Code API：TextDocument](https://code.visualstudio.com/api/references/vscode-api#TextDocument)、[VS Code API：workspace](https://code.visualstudio.com/api/references/vscode-api#workspace)

**设计推论：** AI 编辑器应该明确“本次推理依据的代码快照”。对于已打开且修改中的文件，相关上下文应能读取编辑器 buffer；不能只检查 Git commit 或磁盘索引。一个可行的设计如下：

- 每个片段记录仓库 / 工作区、文件 URI、符号或行范围、内容 hash、文档 version（如果存在）及检索来源。
- 索引用于定位候选，正式组装上下文时重新取得当前内容；旧索引中行号可能已偏移，需要验证或重新定位符号。
- 监听保存、编辑、重命名、删除、切换分支等事件，对相应缓存失效；大仓库可增量更新，但要明确后台索引可能暂时落后。
- 模型准备应用编辑时再次校验目标内容或版本；有冲突就重新读取和计算补丁，避免覆盖用户在推理期间的新编辑。

上述是设计选择，不是说只加一个 `version` 就自动解决并发冲突。也不能把一次会话中的文档版本号当作跨重启、跨仓库通用版本。

## 5. Serena memory、onboarding 与索引预热是不同工作

**来源事实：** Serena memories 是人可读的 Markdown。Agent 得到 memory 名称列表并按需读取；首次 onboarding 会探索项目结构、构建和测试方式，形成 memories；已有项目 memories 时会跳过首次 onboarding。[Serena Memories & Onboarding](https://oraios.github.io/serena/02-usage/045_memories.html)

**来源事实：** Serena 另有 `serena project index`，预缓存语言服务器提供的符号信息，以减少首次符号调用延迟；官方文档将索引与创建 memories 的 onboarding 分成不同步骤。[Serena Project Workflow](https://oraios.github.io/serena/02-usage/040_workflow.html)

**设计推论：** 简历的“预初始化记忆文件降低首次请求耗时”应该解释省掉的是项目探索，还是另有索引预热。两者可以同时做，但应分别记录耗时，不能从一个改动推断另一个环节更快。

Memory 适合记录架构入口、约定、常用命令和可靠链接。易变事实（某函数当前参数、某默认值）应回源核对；memory 的旧结论不应压过当前代码证据。

## 6. 使用产品例子时避免过度推断

**来源事实：** 调研时 Cursor 的旧 `semantic-search` 与 `codebase-indexing` 文档地址重定向到当前 Search 页面，页面描述精确匹配搜索及 Explore subagent。可以据此说明文本检索仍是产品中的重要能力；不宜据此推断 Cursor 的所有检索都已不用 embedding，或声称整个产品只依赖某一种检索。[Cursor Search](https://cursor.com/docs/agent/tools/search)

**设计推论：** 面试回答可以说“我的设计会结合精确文本、符号导航和必要的语义检索，根据任务选择工具”。不必把所有检索都并行调用，也不必承诺先建立完整向量索引才能开始工作。已知错误字符串时直接查文本，已知符号位置时查语义关系，缺入口时再扩大搜索面，比较容易解释每一次调用的价值。

## 7. 与 MSI 项目连接的准备题

这些问题需要用真实实现作答，不能把本笔记中的建议改写成已经完成的功能：

1. API 名如何对应到三端代码入口？如果名称来自字符串注册，符号查询前用什么方式定位？
2. 找到定义以后，如何知道还缺哪些证据？参数解析、校验、默认值补齐和错误码转换是否跨文件？
3. 使用过哪些 Serena 工具？三端分别使用什么语言服务器，有什么能力缺失？
4. 空结果如何区分“确实没有”“语言服务器尚未就绪”“依赖未解析”“权限过滤”“工具不支持”？
5. 三端和文档比较的版本如何确定？报告能否回溯到对应文件和代码版本？
6. 首次请求的时间花在哪些环节？预置 memories 与符号缓存分别减少了什么工作？

## 面试综合方案：如何给 Coding Agent 找上下文

以下是结合一手资料提出的系统设计建议，不是 TRAE 内部实现，也不表示简历项目已经实现所有能力。场景假设是能跨文件修改、调用工具并验证结果的 Coding Agent。

### 可口述的答案

我会把上下文获取设计成围绕任务持续更新的过程。先收集用户目标、明确引用的文件、当前编辑状态和项目约定，确定初始搜索范围；再按线索选择工具：文件名、符号名、错误字符串用精确搜索，自然语言功能描述可以用语义检索找入口，找到符号后通过 LSP 的定义、引用和实现导航补充关系，并读取原始代码核对。模型每发现一个影响决策的信息缺口，就进一步查询；工具负责真实读取、版本和权限校验，编排层负责预算、去重和停止控制。进入模型的片段带路径、位置、版本与来源，关键实现保留原文，长日志和历史按需读取。修改或测试产生新信息后继续补充。最后用关键证据覆盖率、任务成功率、延迟和 token 成本评估效果。

### 一、上下文覆盖什么

- 用户意图：目标、验收条件、约束，以及用户明确引用的文件和符号。
- 编辑器状态：当前选择、活动文件、未保存 buffer、诊断、相关 diff。
- 仓库事实：入口、实现、类型、调用方、配置、测试、构建和依赖版本。
- 任务过程：已确认事实、已排除假设、最新失败输出、剩余问题。
- 外部资料：仅在需要时读对应依赖版本的官方文档或有权限的内部资料。

这些类别需要按当前任务选择。打开过的文件只是相关性信号，不自动等于本次任务必读文件。VS Code 对上下文来源及逐轮工具结果的说明见 [Context](https://code.visualstudio.com/docs/agents/concepts/context)。

### 二、后台准备与前台检索分工

后台可维护文件清单、按函数/类边界组织的片段、词法或向量索引、语言服务器及缓存。每条索引项至少关联仓库、文件路径、符号/片段位置、内容版本。大函数需要受限拆分并携带所属类、函数签名等信息。Tree-sitter 能提供语法结构；完整跨文件符号解析仍需要额外分析能力。

前台以当前任务确定搜索范围和读取次序。小项目或明确指定的小文件可以直接读。向量索引未完成时，文本搜索和语言导航可以先工作。VS Code 官方列出了语义、文本、文件和 usages 等工具及无语义索引时的回退路径：[Workspace context](https://code.visualstudio.com/docs/agents/reference/workspace-context)。

### 三、选择工具的依据

| 已知线索 | 首选方法 | 后续工作 |
| --- | --- | --- |
| 文件路径或报错行号 | 读取相应范围 | 补所属函数、调用点、依赖 |
| 确切 API 名、标识符、错误字符串 | 文件搜索、精确或正则文本检索 | 排除同名实现、测试样例等歧义 |
| 功能描述，暂不知道代码如何命名 | 语义检索，或目录探索加术语搜索 | 读取候选实现，核对是否承担目标功能 |
| 已定位符号，需要知道定义、实现、调用方 | LSP/语言智能工具 | 检查服务能力与返回覆盖范围，读实际实现 |
| 新失败的测试、编译或运行输出 | 读取失败信息、堆栈、对应测试 | 据此补查代码，而非继续泛化搜索 |

“Agentic search”描述模型根据中间结果决定下一步查询；向量、文本、LSP 是可供调用的方法。二者可以组合。RAG 也不等于必须使用向量数据库。检索侧需要召回候选，推理侧仍须核对真实代码。

Cursor 在 2025-11-06 公布过 grep 与语义搜索组合的实验：[Improving agent with semantic search](https://cursor.com/blog/semsearch)。这是特定产品与评测中的一手结果，不证明每个任务都必须增加向量检索。Anthropic 在 2025-09-29 讨论按需读取和多轮探索：[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

### 四、以缺失证据驱动扩展

下面为教学虚构例子，不是美团实际 API。任务是核对 uploadImage 的 quality 默认值。

1. 从 API 名查注册表或入口映射，确认仓库、平台、导出接口。
2. 定位真实实现并读取参数解析；发现 quality 缺失时引用 DEFAULT_QUALITY。
3. 找常量定义、配置覆盖与下游转换，确认默认值在哪些条件下成立。
4. 检查调用方是否提前填入默认值、下游是否缩放单位，以及 null 与未传是否分别处理。
5. 看测试和文档，记录证据与未知项；三端分别完成后才对齐。
6. 若不能确认运行时注入的值，输出条件化结论或待核实项，不用猜测补齐。

结果可包含“字段、未传时行为、显式 null 行为、生效条件、平台、源码位置、仓库版本、未知项”。重要的不是展开最多代码，而是补齐能改变判定的缺失事实。

“查到了函数定义”只能证明定位到了一个程序元素。LSP 不负责自动证明该 API 的全部业务行为。限制依赖展开层数和扇出只是工程预算；如果因预算未覆盖关键路径，必须记录未确认，不能宣称完整。

### 五、排序和组装

候选集合可能来自多次搜索，需要合并重叠范围、去重，并按当前任务的重要性选取：直接修改目标、解释行为的必要依赖、接口约束、验证资料优先。可选 reranker 应通过实验确认收益，不把不同检索器的原始分数直接当成同一尺度。重复但相似的文件不能挤掉关键类型或测试。

每个片段建议携带：
- 仓库和文件路径；
- 符号与行范围；
- commit/content hash 或文档版本；
- 原文与简短的选入理由；
- 读取或检索来源，以及是否截断。

检索片段预算应扣除指令、工具定义、历史、输出预留及后续工具结果空间。不要把固定 top-k 或窗口填满比例当成通用最优值。关键条件和默认值保留原文；摘要需保留原始位置，不能因压缩丢掉“仅某平台/某分支”。

工具要支持范围读取、过滤、分页，并明确输出截断和错误。参见 [Anthropic 工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)。长日志、历史等可保存在可再次查询的位置；Cursor 公开介绍过这种按需读取做法：[Dynamic context discovery](https://cursor.com/blog/dynamic-context-discovery)。

### 六、工作区一致性与边界

同一文件可能存在仓库提交、磁盘工作区、未保存编辑器 buffer 三个版本。对活动文档的当前分析应优先采用该任务对应的 buffer，并让 LSP 和读取工具看见相容状态；分支、worktree 和内容版本应进入缓存校验。旧索引命中可以用来定位，但做判断或应用修改前应重读当前内容。后台增量更新索引，前台补查未索引的变更，避免“重读了旧命中，但新文件仍完全漏召回”。

应用补丁前检查版本；版本变化则重读或重新计算，不能沿用过时的行号。文本索引变化不等于语言分析已更新，跨文件依赖也可能使分析缓存失效。

检索和读取执行层要落实仓库授权与文件访问控制；只读、排除目录和防止越权是不同约束。代码注释、日志和网页中的文字按资料处理，不能提升为 Agent 指令。索引排除规则不替代访问控制。

### 七、停止与评估

停止读取的工程条件可以是：下一步操作依赖的关键事实已得到支持，主要歧义已排除，知道如何验证。若预算耗尽仍有关键缺口，应标记无法确认或请求必要信息，不能把预算用完等同于分析完成。

执行后继续读取最新诊断、测试或运行输出；测试只覆盖其实际检查的行为，不证明没有其他问题。

评估至少分三层：
1. 检索：在固定 token/时间预算下，关键证据片段是否被找到、是否进入最终上下文、是否覆盖跨文件依赖；检索失败、索引过期、排名截断分别统计。
2. 任务：修复目标是否通过适当验证、是否引入回归；对文档核对分别算字段正确率、差异精确率和召回率。
3. 成本：端到端耗时、工具与模型调用、token、重复阅读与失败重试。减少搜索轮数不一定改善任务成功率。

使用固定代码快照、相同模型/提示词/预算比较文本检索基线与增加语义、LSP、动态补查后的变化，重复运行并区分任务类型。人工校验的证据集可能不完整；修复补丁涉及的文件也不等于解决任务所需全部上下文。改动结果和运行轨迹需要一起看。[Anthropic Agent 评估](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

### 八、与你的项目如何连接

项目提供了 API 名这个强入口，适合先定位注册和符号，再沿代码证据确认默认值、必填性、类型和错误码。可以用它证明你理解检索策略应匹配任务形态。扩展到通用 Coding Agent 时，用户可能只描述症状，因此入口发现、实时工作区状态、修改后的反馈循环更重要。

面试表达应区分实际实现、Serena 自带能力和现在提出的设计改进。不要把未来设计说成已完成，也不要将“记忆文件帮助减少初次探索”说成“加速了语言服务器索引”。
